# App Atelier production release contract

Contents: 1 feasibility, 2 release model, 3 exact recipes, 4 external effects and recovery, 5 evidence.
Read cross-domain-core and the current workflow, acceptance, budget, data, and evidence references. `assets/app-depth.templates.json` supplies a release packet template. Verify current personal prerequisites against primary sources at the dependent decision.

Use the [app system model](app-system-contract.md) for cross-cutting contracts. It owns requirements and state authority.

## 1. Establish early feasibility and coverage

Before significant build, identify required operations: Android build, package, install and distribution, iOS archive, sign, export, install and submission, web build, hosting, domain and TLS, backend and data migration, support, billing and entitlement, listings and privacy, diagnostics and monitoring. Choose conditional services and expenses according to need. Record missing SDK or account capability as blocked.

For each operation record exact target, platform, region and channel, host and toolchain, account owner and organization, permissions, recurring, one-time and variable costs, data flows, mandatory testing and legal prerequisites, output and consumer, and appropriate proof. Verify the actual Mac and Xcode route, signing capability, accepted package type, and return from remote builds. Verify the operation beyond the cloud or plugin description.

Compare any ban on human trials, no-spend limits, platform and geography with current store requirements before significant commitment. Record conflicts and feasible alternatives. Preserve the Android, iOS, and web scope until the owner changes it, and use human participation where the platform requires it. Carry forward valid approval and clarify material unresolved choices.

## 2. Pin the release assembly

Bind exact client, backend, support, data and config versions, build artifacts and hashes, resources and knowledge base, environment, product IDs, and current QA to the candidate. Record source commit, build number, artifact hash, and deployment ID separately. Align every consumer's API, schema, entitlement, and policy versions. Verify all scoped clients individually.

For state, API, and schema fields, define owner, version and compatibility, secret reference, migration, downgrade and recovery limits, deletion and revocation fences, and retention. Agree roll-forward and rollback before dispatch. Verify whether restoring a binary can recover the data schema, external purchases, or deletion. Where rollback is incompatible, define a forward repair or restore with concrete limits.

Listings, screenshots, previews, support and privacy links, and review instructions describe the accepted candidate. Use screenshots from actual product states and derive SDK, privacy, billing, and content declarations from dependencies and data flows. Verify current countries, commercial terms, taxes and fees from current sources. A generic statement such as «ми нічого не збираємо» requires proof.

## 3. Bind and verify recipes

Use distinct recipes for clean build, native package, sign, export and install, submission, hosting and deploy, schema migration, post-release smoke, and rollback. Bind source, lockfiles, assets and config hashes, pinned toolchain, target, account and channel, permissions, cost and expected outputs. Use exact argument arrays, API fields, or numbered GUI steps. Block only dependent work when a critical placeholder is unresolved.

Record the Android AAB, APK, or split package and matching distribution and installation route. Distinguish Apple archive, export, install, TestFlight, and App Store. Verify web origin, config, CSP, cache, service worker, and API binding at the actual URL, including the core flow. Test native callbacks, permissions, billing, and restoration in the required runtime.

Verify descriptor, schema and catalog, actual support, and parameter consumption. Keep signing credentials in the host's approved secret facility. Use references and setup instructions in packets. Isolate test and production so debug credentials, sandbox endpoints, and sample data stay outside the final candidate.

Record output hashes, logs, symbols, diagnostics mappings, receipts, and read-back with actual author, observer, and environment. Preserve editable masters, source provenance, and licenses. Track byte and reference validation separately from store approval and availability.

## 4. Execute and recover external effects

Verify candidate hashes, parameters, target, cost, and current authority before dispatch. Record a pending local attempt with a stable key, invoke the real tool, save the actual request, job, submission, or deploy ID, reconcile status, output and cost, and complete the receipt and read-back. Actual publication needs evidence beyond queuing.

Keep timeout or lost session outcomes unknown until an authoritative check. Locate the submission, deploy, or job first. Reconcile uploads, payments, and migrations before retrying. Verify provider idempotency, retain the local ledger as a local record, and check actual cancellation. Reserve unknown cost against the cap until resolved.

Changes to artifact, SDK, store prerequisite, account, terms, permission, or target reopen dependent QA and authority. Reuse valid authority. After two failures under the same hypothesis, change diagnosis or route.

For personal MFA, signature, legal, or physical actions, complete available preparation and give an exact launch and return path, verified URL, artifact hashes, minimum action, expected receipt, and return verification. Keep secrets out of chat.

## 5. Verify availability and hand off to operations

Track authored, built, signed, installed and device verified, submitted, approved, released, available externally, and observed useful use independently. Verify store status and regional or channel availability through official read-back, web through actual URL, health, version and core action, and support through real channels, auth, and fallback. Keep unverified claims open even after a successful command.

Run `fresh install/open → input → useful result → persistence → restart/resume → support` and conditional purchase or restore within authorized scope. Avoid live effects solely for QA. Check cold start, denied permission, outage, old client against new backend, and upgrades with existing data. Physical properties need appropriate device evidence.

Hand off exact source, build, deploy, config and data versions, signals and alerts, symbols, migration, recovery and rollback, caps, provider references, support and knowledge state, risks, and retirement obligations. Verify actual scheduler or service and alert operation before claiming active monitoring. Test actual restore before claiming recoverability.

## Visible result and proportionality

Apply the [adaptive workflow](adaptive-work.md). Show exact artifact readiness, release route, current authority, receipts, and actual availability. Distinguish completed work, inherited decisions, and future results with due gates. Scale depth and roles to uncertainty, consequence, and coupling. Use a local repair for a local change.

For material gaps, use the relevant [research, synthesis, or reconciliation mode](research-and-synthesis.md). Verify readiness separately from authority, current platform and account conditions, migration and rollback, and external read-back. Inspect raw inputs for omissions. Verify reviewer competence beyond actor ID and keep structural checks at their actual evidence level. Preserve context, approvals, and unaffected results.
