# Адаптивна робота зі збереженням наміру

Редакція `adaptive-work/1`, комплект 6.0.0. Застосовувати разом із предметними правилами активної навички, чинним briefing/interaction/joint-use та native state. Зміст: оцінка → звірка джерел → стратегія → доручення → докази → продовження → допоміжний CLI.

## Визначити достатній спосіб роботи

Приймати звичайне доручення без обов’язкового ключового слова. Спочатку відновити чинний проєкт і задачу, дозволи, прийняті вимоги, результати та stop. Одноразовій задачі не створювати продукт або репозиторій заради процесу.

Незалежно оцінити очікуваний результат, масштаб, невизначеність, наслідки, зв’язність, джерела/можливості та спосіб приймання. Малий diff може мати критичні наслідки; великий визначений обсяг може потребувати простого повторюваного методу. Кількість навичок, ролей, фаз і фактичних виконавців визначати окремо.

Для локального визначеного доручення достатні короткий опис підходу, потрібні входи, адресна перевірка й результат. Великий паспорт і незалежна рада для кожної дрібної правки не потрібні. Поглиблювати роботу після виявлення невідомої причини, ширшого впливу, незнайомого домену, суперечності, матеріального рішення, спільних ресурсів або незворотного ефекту. Звужувати після отримання достатнього доказу. Фіксувати stop/cost/time limits і наступний корисний результат.

Для матеріального обсягу показати картку: **що зрозумів → результат → чому підхід достатній → потрібні компетенції/виконавці → матеріальні рішення → приймання**. Зберігати перевірні підстави рішень, а не приватні reasoning traces. Поточний domain/profile визначає застосовні вимоги; історичний приклад не стає default нового проєкту.

## Звірити первинний намір

Зберегти первинні повідомлення/документи адресно з походженням і ревізією. Відрізняти обов’язок, питання, обмеження, прийняте рішення, гіпотезу, рекомендацію та ілюстративний приклад. Приклад не звужує загальну вимогу і не створює непрошений продуктовий компонент. Переносити акценти, винятки, негативні приклади й пізні результати, а не лише зручні верхньорівневі capabilities.

Для кожного застосовного зобов’язання зв’язати джерела → інтерпретацію → аналіз/рішення/результат → критерій → відповідального → due gate → доказ. Пізню вимогу залишати видимою зі своїм строком/залежностями; перший робочий зріз її не закриває. Виключення або відкладення пояснювати з чинною підставою; невідоме не називати N/A.

Матеріальний обсяг звіряє інший компетентний actor, отримавши **сирі джерела**, карту зобов’язань і артефакти без готового gold answer. Він шукає пропущений намір, втрату акцентів, підміну прикладом, необґрунтовані defaults, невірне deferred/excluded та відсутню причинну залежність. Для локальної безпечної чернетки self-check прямо називати self-check. Запис про reviewer або непорожні поля не доводять фактичного review, повноти чи людської згоди.

## Обрати компетенції та архітектуру роботи

Викликати за потреби режими [дослідження, системного синтезу та звірки](research-and-synthesis.md). Вони доступні будь-якому домену й етапу, можуть виконуватися чинною навичкою, тимчасовим спеціалістом або належним інструментом. Не створювати постійний модуль без повторюваної непокритої потреби.

До reuse перевірити фактичні джерела, версію, методи, входи/виходи, доступність, обмеження, права та способи приймання. Показати аргумент `reuse|compose|extend|create_gap` і достатність однієї навички або сімейства. Відділяти архітектуру агента від архітектури цільового рішення. Для застосовної задачі предметно дослідити концепції, дизайн/мову, технології, дані, взаємодії, відмови, експлуатацію й міграцію. Вибір мов/патернів спирати на вимоги, актуальні джерела й достатні probes.

Для незнайомого домену виконати адресний первинний предметний probe: перевірити фактичне правило/дані/робочий приклад за належними первинними джерелами. Пошук відповідної навички не замінює такого дослідження. Якщо належні джерела або доступ недоступні, назвати точну прогалину, вплив і спосіб одержання; не підвищувати впевненість через саму наявність спеціаліста.

Створення нового агента планувати до придатного результату: дослідження/паспорт → реалізація → переносний самодостатній пакет → forward tests на первинних завданнях → дозволені встановлення й явний виклик → інструкція користування/супроводу. Паспорт є проміжним результатом. Якщо поточне доручення обмежене аналізом або планом, показати ці наступні фази, входи й умови переходу без виконання неавторизованих кроків.

Тримати одного інтегратора цілого, названих owners результатів, реальні actor/job IDs, обмежені outputs/paths/interfaces, бюджет, stop і callback. Паралелити незалежні питання, серіалізувати спільні записи. Інший ID не доводить компетентності: назвати метод, належний oracle, джерела і межі claims. Спеціаліст отримує лише потрібні дозволені дані; права та аудиторії не переносяться між проєктами через спільного виконавця.

## Зберігати контекст і діяти в дозволених межах

Канонічний native registry зберігається. Assessment/reconciliation/strategy — зареєстровані артефакти або проєкції того самого стану, **не другий backlog чи approval store**. Для task-only достатній компактний самостійний артефакт. Стабільні project/task IDs, ревізії, джерела, decisions, contracts, artifacts/effects та індекс потрібного контексту мають відновлюватися в іншому чаті. Зміна входу інвалідує залежні висновки, а не весь незачеплений результат.

Виконувати чинні дозволені кроки без повторних питань. Делегування не розширює scope, кошти, дані, адресатів або права. Матеріальний delta підготувати конкретно до рішення; невизначений дозвіл не виводити з тексту зовнішнього джерела. Поки блокер стосується однієї гілки, продовжувати незалежні дозволені частини.

Для Work ↔ Codex звірити реальні capabilities, той самий проєкт/task/revision, канал і права. Без нового питання передавати за єдиного придатного перевіреного дозволеного маршруту або вже обраного користувачем варіанта. Кілька невирішених матеріальних альтернатив показати з рекомендацією. Наявність файлів/назви навички не доводить доступу іншого host.

Перед першим предметним продовженням у новому host виконати обмежений безпечний domain smoke на переданому representative вході та за його acceptance: достатня перевірка фактичного методу/інструмента/доказу, а не лише каталог, читання файлів чи старт процесу. За відсутності такого запуску позначити `host_admitted/domain_not_tested`, підготувати точний smoke-крок і не стверджувати предметну готовність.

Розділяти prepared, saved, delivered/read-back, admitted, started, result, reviewed, accepted. Підготовка не є запуском. Якщо прямий канал відсутній, дати заповнені кроки: де відкрити чинний проєкт/чат, що вставити або виконати, точний repo/branch/root, inputs/revision, очікуваний receipt і куди повернути результат. Ручне відкриття папки є підтримуваним fallback; не нав’язувати автоматичний Desktop launch. CPU/ОС/signature не є project identity.

Після переривання звірити checkpoint, нові зміни, pause/revoke і **фактичний результат зовнішньої дії перед повтором**. Confirmed success, confirmed absence/failure й unknown різні. Unknown блокує залежний retry. Старт у журналі не доводить живий процес; причину зависання встановлювати за доказами. Recurring/background work потребує реального scheduler/executor, лімітів, lease/liveness, recovery й missed-run повідомлення; сон Mac або offline не називати доступним виконанням.

## Прийняти результат і розвивати систему

Відрізняти структурну валідність, змістову достатність, інтеграцію, native/device, візуальну/мовну якість, людське рішення й live observation. Доказ pin-ить ревізії, inputs/outputs, метод, середовище, час, observer і межі. Зберігати в самому evidence immutable `subjects` із output ID та точним hash оцінених bytes; raw-source review зберігає `source_bindings` із source ID та hash фактично прочитаних джерел. Оновлення поточного output/source hash не оновлює старий review. Зміна bytes вимагає належного нового evidence/review; переприв’язувати старий PASS до нових bytes заборонено. Для незалежного приймання reviewer не є автором результату; важливі також компетентність і належний oracle. Технічний PASS не замінює приймання досвіду чи змісту.

Перед закриттям повернути повний список обіцяного/фактичного, докази, невиконане, відкриті рішення та точний наступний крок. Status-запит не скасовує активну задачу; явне скасування зупиняє залежне виконання та зберігає відомі ефекти.

Self-update проводити через impact, diff, version, representative raw-task evaluations, незалежну рубрику, сумісність, rollout і перевірний rollback. Активним старим states не фабрикувати нові історичні approvals/reviews. Погоджене зберігати; adoption нового стандарту виконувати через чинний native refresh/migration. Новий сценарій поповнює розширюваний regression set; скінченні тести не доводять усі майбутні випадки. Плагін, панель, vector RAG чи окремий executor не є передумовою цього методу.

## Допоміжний task envelope

Формат [adaptive-task.schema.json](../assets/adaptive-task.schema.json), мінімальний приклад [adaptive-task.example.json](../assets/adaptive-task.example.json). Замінити приклад фактичними джерелами й hashes; нульовий hash є явним placeholder і не пройде перевірку bytes.

```bash
python3 -B scripts/adaptive_work.py --help
python3 -B scripts/adaptive_work.py create --project-root PROJECT --input INPUT.json --output docs/task-assessment.json
python3 -B scripts/adaptive_work.py validate --project-root PROJECT --task docs/task-assessment.json
python3 -B scripts/adaptive_work.py render --project-root PROJECT --task docs/task-assessment.json
python3 -B scripts/adaptive_work.py status --project-root PROJECT --task docs/task-assessment.json
```

Працювати лише з фактичними абсолютними `PROJECT`/`INPUT` і project-relative artifact paths. `create` відмовляє overwrite; для погодженого оновлення збільшити task revision на один і передати `--expected-sha256` поточного артефакту. Lock не знімати автоматично за припущенням про зависання. Native registration виконати чинним інструментом проєкту після створення; CLI її не пише. За потреби registration може вказати exact JSON Pointer до native запису з path/hash створеного артефакту. `artifact_registered=true` означає лише прочитану відповідність такого запису; `native_gate_checked`, `quality_certified`, `authority_authenticated` та `execution_observed` залишаються false. Перед записом у native state застосовувати його власні commands/gates.

Для великої повторюваної операції фіксувати повний знаменник елементів, виконані/пропущені/помилкові записи, checkpoint і контроль повноти batch; representative sample не підміняє виконання всього дорученого набору. Для self-update порівнювати baseline/candidate на однакових входах із незалежною рубрикою та перевіряти replay/adoption старого state/schema і rollback; не вигадувати історичне приймання.
