# Conditional AI, data and production work

Use only the sections needed for the actual task. These seven profiles are responsibilities inside the existing agent system, not seven new skills, processes or permanent team members. Keep the current project integrator, native requirements, accepted identity, permissions and deferred work. A specialist receives the same original outcome and a bounded work package; changing the specialist does not restart the brief.

Begin with the business or user decision, the useful result and its real consumer. Find the existing sufficient route before adding a framework, model, index or worker. A small repair can stay small. A full product keeps its agreed backend, interface, operations, quality and release scope; an initial working slice does not finish that larger result.

## Choose an existing owner

| Profile | Activate for | Existing route first |
| --- | --- | --- |
| DATA | API/export imports, permitted collection, document ingestion, dataset quality and lineage | Current integrator with integrations, backend or knowledge competence |
| ANALYSIS | Extraction/classification, feedback themes, clustering, segments and trends | Current research/growth/knowledge owner with data work and independent evaluation |
| LLM | A useful generation, retrieval, tool or agent function in a product | Current product owner with knowledge, integrations and implementation competence |
| PREDICTION | A decision supported by a validated forecast, score or ranking | Current implementation owner with actual ML, architecture and cost competence |
| ADAPTATION | A measured base-model gap that may justify optimization or training | Current implementation/reliability owner with model, privacy and evaluation competence |
| MEDIA | A material set of text, images, vector/3D assets, audio, video, documents or interfaces | Existing App experience, ChatBot media or Game assets owner |
| EVALUATION | Adoption, prototype productionization, changed models/media or a system update | Current family QA and competent independent reviewers for the claims involved |

Select actual actors by the work and their available tools. A declared profile is not a running subagent or evidence of professional history. Assign owned files, inputs and hashes, interfaces, resource/effect bounds, observable acceptance and return destination. One owner integrates the product; one writer owns each mutable boundary. Parallelize independent work. Preserve the original outcome when creating an agent and then using it for the original task.

## DATA: source to dependable dataset

Establish the allowed source, acquisition and reuse/transfer scope, fields, schema, sampling, coverage, privacy/retention, consumer and request/byte/retry limits. Public viewing is not automatically permission for every collection, reuse or transfer. Prefer an adequate API/export; use static parsing for static content and a browser when actual rendering or interaction requires it. Check the current operation schema, entitlement, rate and cost before use.

Preserve permitted raw observations with exact source/time/version pins. Normalize IDs, types, units, currencies, nulls and event/observation/availability times. Deduplicate without erasing independent events; quarantine invalid rows with reasons. Keep received, accepted, duplicate, quarantined and excluded counts. A login page, repeated cursor, schema drift, missing page or unexpected empty result cannot become complete success. The consumer must see partial data.

Write data and cursor/watermark progress with explicit crash/replay semantics. Test 429, late events, repeated pages and failure after data write but before checkpoint. Bind downstream caches, embeddings and features to source/transform/privacy versions; revoke or invalidate dependent material with explicit restore limits. Emit `SourceContract` and `DatasetManifest`, actual adapter/transform sources, raw/normalized references, run receipts and the useful consuming result. The helper below checks declared invariants; it does not collect data or establish source rights.

## ANALYSIS: evidence to an actionable finding

Define the unit of analysis, decision, sampling window, languages, label guide and error costs. Inspect real permitted records. Establish a transparent baseline before selecting a candidate. Rules, SQL, structured extraction, embeddings and clustering are alternatives; use the sufficient one and measure its limitations. Do not add embeddings merely because they are available.

Preserve every required record, evidence link, membership and noise/outlier. Account for repeated authors, duplicated reports, languages, bots and changing source coverage. Distinguish reported problems, verified causes and inferred needs. For classification, reserve appropriate labels or a separately reviewed sample; independent AI agreement is not human ground truth. For clustering, inspect useful meanings, stability and sensitivity as well as geometry. Similarity does not prove importance, truth, independence or causality.

A trend needs comparable coverage, time semantics and denominators. A newest-page convenience sample is not population prevalence or a market-demand estimate. Deliver a readable source-linked conclusion, exact corpus/method/output versions, disagreements, uncertainty and a real next action. An executable refresh path needs its own scheduling, limits and receipts; writing the recipe does not start background monitoring.

## LLM: a bounded function through its consumer

Define the real user journey, provider-neutral request/output semantics, permitted tools, abstention, fallback, privacy, latency and cost. Check actual provider/model fields and output consumption. Version prompts, adapters, cases and tool contracts. Keep authorization and domain transitions in deterministic code. Validate output meaning as well as structure; a valid JSON response can still be false.

Use current source reads/search/SQL when sufficient. Native task status, current decisions, exact revisions, permissions and receipts come from their authoritative files or supported interfaces. A semantic index does not replace them. Use RAG only for a demonstrated corpus-retrieval need, with scoped source/tenant/ACL/version/deletion controls and separate retrieval and answer evaluation. No global index of all projects/chats is implied.

Use ordinary code or existing orchestration first. A durable graph framework is justified by actual branching, state and recovery needs; it does not make an external effect exactly once. Record intent before dispatch, stable effect/request/job IDs and unknown outcomes. Reconcile a lost acknowledgement before retry. Test injected instructions in data, wrong tenant, revoked/cache sources, refusal, empty/malformed output, partial work and restart.

Integrate the function into the actual backend and interface with understandable progress, correction, retry/cancel and failure states. Existing coding assistants may help development when truly available. Their login and native permissions are not interchangeable, and a developer's Codex/ChatGPT login is not automatically the production credential for the product's users. Production needs the appropriate API account or operated local model, server-side secrets, user/tenant controls, quotas and an operational owner.

## PREDICTION: honest forecasts and decisions

Define target, units, horizon, decision, prediction-time information, label maturity, population and error costs. Preserve source/dataset/feature versions. Freeze group/time splits and protected holdout before tuning; fit preprocessing only on training rows. Compare a simple baseline with suitable candidates under declared time/memory/experiment/cost limits. A language, library or model family is a choice, not a promised winner.

Check that each feature was available at prediction time and each training/selection label was available at its declared cutoff. Separate creative families, users/campaigns or other dependent groups where relevant. Check chronology and an appropriate embargo. Report subgroup errors, uncertainty, calibration where applicable, distribution limits and abstention. Package preprocessing, schema, model and inference together; test actual train/serving parity, fallback, monitoring and compatible rollback.

For pre-launch CPA, name acquisition, currency, attribution window and horizon. Do not use post-launch spend/clicks/conversions as pre-launch features. Zero acquisitions do not have an ordinary finite CPA and cannot simply disappear from the population. Image appearance alone cannot establish exact CPA across campaign/audience/auction contexts. A justified range, ranking, abstention or insufficient-data result is preferable to invented accuracy. A predictive association is not a causal improvement.

## ADAPTATION: justify and deliver the changed model

First measure the base/prompt/retrieval limitation. Establish suitable rights and training data, contamination/dedup controls, protected evaluation, base/tokenizer/template revisions, license, device/backend, memory/storage/time/cost and real serving requirements. Changing facts may need retrieval rather than training. Check actual compatibility; a documented GPU recipe or somebody else's Mac benchmark does not qualify this host.

A bounded recipe pins data, code, environment, method, seeds, precision and recovery. LoRA additionally needs actual target modules, rank/config and the exact base. Run only authorized training; record actual checkpoints, usage, failures and metrics. Evaluate base versus adapter, and merged/quantized/exported forms separately where their bytes or behavior change. Deliver an exact load/signature bundle and actual serving comparison. A recipe, dummy file, CPU proxy or successful hash is not training or inference proof.

Loading weights is an execution/security boundary. Review formats, provenance and loaders; do not execute untrusted pickle/joblib/custom remote code. The helper deliberately never loads models and refuses executable serialization in its bounded admission route. A separately reviewed native loading route needs its own exact authority and evidence; this utility does not remove that existing capability or validate it. Downloads, hosted compute, publication and new spending need their actual scoped decisions.

## MEDIA: preserve identity through real delivery

Restore the full brief, actual references and their status, approved originals/editable masters, permitted adaptations, item/variant matrix, locales, formats and destination. Extract defining composition, relative scale, information density, typography/material, motion/voice and interaction/function. A matching palette or label is insufficient. Use the relevant production-quality and medium profile; creative freedom does not authorize identity drift or generic simplification.

Choose generation, deterministic editing and specialist tools by the required operation, control/editability, available access, cost and actual consumer. Prove a representative slice on the real medium before batch production. Retain masters and exact source→derivative→export→import lineage. A raster concept is not an editable vector, native document or 3D asset. A still image does not prove animation, actual listening, timing or haptics. Check the required format, alpha/geometry/rig/codec/loop and target integration as applicable.

Plan the full set, then reconcile actual responses by item/variant ID, including out-of-order, partial, rejected, cancelled, missing and uncertain outputs. Retain all attempts and provider receipts. Retry only known safe failed work; reconcile unknown potentially paid effects. Include generation, rejected variants, repair, export/import, editing and QA in accepted-unit cost. Unknown charges are unknown, not zero. Check every required item and its actual craft/consumer acceptance, not only the best sample. `BatchPlan`, `ItemManifest` and `GenerationBatch` keep this accounting; the existing media owner still performs production and review.

## EVALUATION: prove the useful result and preserve what works

Trace the original task and every applicable existing invariant to observable acceptance. Freeze baseline/candidate, inputs, source/build/master/model/tool pins, task-specific rubric, held-out cases and resource envelope before comparison. Check source, function, craft, runtime/device, independent review and owner acceptance separately. Use genuine negative controls and inspect raw output in the real consumer.

Any demonstrated loss of an accepted function, quality, identity, setting, permission boundary or deferred obligation rejects the affected candidate. An average score, new feature or lower price cannot compensate. Unknown required proof stays open. Newly found working behavior joins the preservation denominator; a known defect is compared with its accepted contract rather than preserved as intended behavior.

For a prototype, inspect actual data/buttons/jobs, manual dependencies, auth/state gaps, secrets and failure behavior. Complete a useful nontechnical user path through input, progress, result, correction, restart/recovery and permitted operation. Establish appropriate persistence/backups, observability, queues/cost controls, support, health and rollback. A notebook, source folder, mock-provider test or connected adapter does not establish production readiness or a deployment.

Use `EvaluationPlan` and `EvaluationReport` for the applicable comparison and proof types. An author cannot supply independent review of their own work. A different string in a reviewer field does not prove identity, competence or independence: record the actual assignment and raw evidence in the native project. The helper checks only declared consistency.

## Thirteen optional artifact types

These are typed derived artifacts referenced from the native project ledger. Instantiate only applicable records and their actual dependencies. Do not replace the project's state format, create a competing backlog or manufacture a record to fill an irrelevant checklist.

| Type | What it records | Implemented declaration check |
| --- | --- | --- |
| `SourceContract` | Source/operation, rights/privacy/schema references, consumer, rate and resource bounds | Required fields and actual local reference pins |
| `DatasetManifest` | Sources, retained IDs, transform, full counts, quarantine and coverage | Unique retained IDs, complete count accounting and no complete claim with remaining rows/cursor/gaps |
| `SplitManifest` | Dataset membership, excluded IDs, group/time strategy, row availability and label cutoffs | Complete disjoint membership, declared group separation, chronology/embargo and feature/label availability between consecutive populated partitions, including train→test with empty validation |
| `FeatureManifest` | Feature sources and per-row availability; preprocessing fit IDs | Exact dataset/split relation, training-only fit and no declared future feature |
| `PredictionContract` | Decision, target/unit/horizon, forbidden inputs and CPA semantics | Feature exclusions, required CPA currency/attribution and zero-acquisition policy |
| `WorkflowRun` | Actual declared nodes/attempts, explicit completion IDs, effects and receipts | No order-based completion or hidden unfinished effect; retry only for a known failure under a pinned bounded policy, never in-flight/unknown/successful work |
| `EvaluationPlan` | All cases/musts, baseline/candidate/rubric, author, proof types and independence requirement | Nonempty case denominator, unique IDs and must coverage |
| `EvaluationReport` | Exact canonical plan digest, consumed plan pins, reviewer, all verdicts and observations | No changed plan/rubric/baseline/candidate rebound to an unchanged report; no omitted cases, missing pass evidence, declared self-review or failure/unknown hidden by a pass conclusion |
| `TrainingRecipe` | Data/split, base/tokenizer/license/template, measured gap, method/config and bounds | Consistent nonempty training split; LoRA requires rank/targets/config |
| `ModelBundle` | Actual files, weights/tokenizer/adapter/signature members, revisions, evaluation and serving records | Complete delivered component membership, matching revisions, narrow safe utility route, evaluation bound to current files/adapter/signature/serving proof and an explicit serving observation |
| `BatchPlan` | Full item/variant matrix, recipe, masters, consumer and cost cap | Unique requested pairs and pinned references |
| `ItemManifest` | One requested variant, master, actual exports and declared review/consumer records | Planned pair/master continuity and current output/master pins in its passing evaluation |
| `GenerationBatch` | All attempts, item outcomes, costs and editing/export/import/QA overheads | Exact whole denominator, successful attempt/output relation, unknown/cancel accounting, currency/cap and cost per accepted item |

## Use the bounded helper

Read the actual helper's `--help`. In a copied skill bundle the files are `scripts/ai_production.py` and `assets/ai-production.schema.json`; in the source repository they live together under `standards/`. The JSON Schema is generated by the helper's fixed thirteen-type contract, not a remotely loaded schema. The helper does not install anything or depend on a neighboring constructor.

```sh
python3 scripts/ai_production.py --help
python3 scripts/ai_production.py schema
python3 scripts/ai_production.py digest --root /absolute/canonical/project --input evaluation-plan.json
python3 scripts/ai_production.py check --root /absolute/canonical/project --input source.json --input dataset.json
```

Each record has `schema_version: "atelier.ai-production/1"`, `kind`, stable `id`, `project_id`, the exact canonical `project_root`, `owner`, `inputs` and typed `payload`. `inputs` lists consumed local `{path, sha256, bytes?}` pins. Every payload field ending `_ref` must point to one of those pinned files. Cross-record IDs resolve only against the explicitly supplied records from the same project; supply the referenced dependencies too. Native domain additions can live under `extensions` but are not interpreted by this checker. The schema exposes every supported field and required shape.

The commands are read-only. Nonfinite JSON is rejected, including numeric overflow such as `1e999` and nonfinite values nested under `extensions` or supplied to the direct Python API. The checker also rejects unsafe/linked/credential paths, missing or changed files, wrong project roots and conflicting versions at the same path. Artifact JSON is limited to 2 MiB per file and 16 MiB per command; arrays have declared bounds. Local input hashing is streamed and defaults to 64 MiB per file. An explicit `--max-pin-bytes` can raise that hashing limit up to 64 GiB without loading or executing a model. These are utility bounds, not permission or a smaller product scope. For larger native datasets use a capable data/query workflow and retain the complete required denominator; do not truncate IDs to obtain a PASS.

An `EvaluationReport` must set `payload.plan_sha256` to the digest command's `canonical_sha256` for the entire current `EvaluationPlan` record, including its owner, scope fields, inputs, rubric/baseline/candidate references and extensions. Canonical identity uses UTF-8 JSON with sorted keys, compact separators and finite numbers; whitespace/key-order changes alone do not change this identity. The report must also consume every current plan input path/hash. `digest` establishes record identity and shape only; it does not check source pins, dependencies, permission or quality. Any material plan/input change needs a new review/report, not replacement content under the old plan ID.

A retry declaration is accepted only for `WorkflowRun` effects in `known_failure`, or `GenerationBatch` attempts in `failed`/`rejected`. It needs a failure receipt and `retry_policy` containing `mode: "known-failure-only"`, a pinned `basis_ref`, and a positive `retry_number` no greater than `max_retries`. Planned, dispatched, unknown and successful effects cannot request retry; a closed run cannot retain requested retry work. This is a declared policy check, not authenticated operational safety or permission to execute a network effect. The actual native controller still reconciles the result and enforces scope, identity/idempotency and budgets.

No record set requires all thirteen types. A source-contract check can run alone. A dataset needs its source contracts; a model or accepted media item needs its actual data/plan/evaluation dependencies. Native state formats and the twelve existing inherited operating resources remain intact. Adding this resource to a generated bundle requires the constructor's reviewed self-contained packaging, not a cross-directory runtime link.

For a `ModelBundle`, weights, tokenizer and signature references must name actual delivered file members; a LoRA adapter must also be a member. Consumed input pins alone do not establish this delivery closure. Its passing evaluation must consume the same file hashes and pinned adapter/signature/serving records; a nonempty `serving_proof_ref` alone is insufficient without an explicit serving observation. This verifies declared evidence binding, not the authenticity or adequacy of that observation. A PyTorch `weights_only` or other separately reviewed native format is not globally forbidden: if it is outside this utility's supported file route, retain its adequate native loader/admission contract and record the utility boundary rather than renaming or converting the artifact to obtain a PASS.

The report returns performed checks, exact artifact hashes and applicable batch accounting. `cost_per_accepted_item` includes recorded retries/rejections and recorded overheads; it is null with no accepted items or unknown costs. `declared_costs_complete` describes the provided cost entries, not authenticated billing. Closed processing with rejected items is not full delivery: `all_requested_delivered` remains false. A recorded pass is a review declaration, not authority granted by this tool.

Keep `quality_certified=false`, `authority_authenticated=false` and `actual_execution_authenticated=false`. Structure and hashes cannot establish source completeness, legal rights, factual accuracy, causal effect, actual training, valid model internals, artistic quality, playback, device behavior, consumer success or owner acceptance. Perform those checks through the actual applicable operation, competent review and native project evidence. On changed inputs, produce a new artifact revision and rerun the affected dependency closure; never relabel the old proof.
