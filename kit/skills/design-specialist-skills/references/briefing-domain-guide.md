# Адаптивний БРИФ / ВІДНОВИ: Конструктор спеціалізованих навичок

Каталог [тем](../assets/briefing-topics.json) — карта відомих застосовних питань, а не анкета для послідовного зачитування та не універсальна обіцянка вичерпності. Спільні теми з’єднуються з темами поточного етапу й ранніми downstream залежностями. Для кожної теми вести project-owned запис: applicability/причина, відповіді та точні джерела, unknown/conflict, owner, affected IDs, due gate і спосіб закриття. Нову суттєву тему, якої немає в каталозі, додати до цього реєстру зі стабільним ID і такими самими полями; за потреби доповнити catalog extension. Відсутність доступу означає blocked, а не N/A.

Спочатку прочитати фактичний запит, current state, accepted originals, джерела/версії/хеші, рішення й надані пакети. Передзаповнювати відповіді з provenance та межами застосовності; не перепитувати чинне. ВІДНОВИ звіряє freshness, unresolved effects, active stop і змінені залежності, зберігає прийняте та відкриває лише зачеплені питання. Для локального ремонту не перезапускати весь цикл.

Визначити повну ціль, окремі launch/probe scope та неприйнятні спрощення. Порядок виробництва не зменшує амбіцію автоматично. Не призначати від себе ліміт годин, кількість функцій, спосіб вводу, платформу, monetization чи upgrade route. Розрив ресурсів і бажаної якості має досліджені альтернативи та конкретне матеріальне рішення.

Вибирати найближче невирішене питання, яке змінює ціль, поведінку, архітектуру, права, витрати, ризик або приймання; спочатку його передумови, потім залежні деталі. Перед кожною користувацькою розвилкою підготувати доречні реальні варіанти, наслідки й рекомендацію за критеріями цього проєкту. Не вигадувати ринкові дані, попит, можливості, актуальні тарифи чи права. Вільна відповідь і «не знаю» допустимі. «Не знаю» означає дослідження експертом, порівняння, рекомендацію та контраргумент; невідомість не перетворюється на згоду. Технічний фахівець закриває встановлювані факти в погоджених межах, користувач визначає намір і матеріальні компроміси; явне делегування не розширює authority.

Після кожної відповіді оновити applicability і залежності, прибрати вже закриті питання й додати нові матеріальні наслідки. Обсяг раунду визначає зв’язність рішень та здатність людини відповісти, а не фіксовані вісім рядків чи стеля тем. Майбутня тема має бути відкрита зараз, якщо її відповідь змінить поточний вибір. Каталог може бути великим; конкретний бриф містить тільки релевантні питання.

`criticality` допомагає впорядкувати роботу: material — істотний вибір; technical — експертне опрацювання; future — пізніший параметр або доказ. Ця ознака не звільняє від аналізу матеріальних наслідків. `answer_owner` відрізняє намір користувача від експертної відповіді; delegated потребує фактичного доручення й поверненого результату. Питання про приймання не є approval саме по собі.

До затвердження сценарію виконання закрити всі відомі застосовні матеріальні unknowns поточного scope й ранні downstream наслідки. На C1 визначити архітектуру, обіцянку й основну поведінку. Числовий T tuning чи майбутні конкретні inputs можна відкласти лише з baseline/range або інваріантом, owner, методом/experiment, exact due gate, acceptance, affected IDs та reopen умовою. Невідоме основне правило не є tuneable parameter. Перед залежним виконанням споживач має достатні точні правила; майбутній device/human/production proof лишається pending до свого рубежу. Структурний PASS не доводить предметну якість, права, установку або live outcome.

Selectors `intake`, `research`, `architecture`, `blueprint`, `build`, `verify`, `install`, `refine`, `resume` усі відповідають stable skill `design-specialist-skills`. Це режими роботи конструктора; вони не задають кількість фаз, children або ролей майбутньої спеціалізації. Її власний stage DAG виводиться з outputs і consumers.

Відновити реальний процес, користувача/оператора/адміністратора/власника даних, raw inputs, desired output і ціну помилки. Порівняти чинний метод, deterministic automation, reuse/refine існуючої навички, агента або app. Не успадковувати предмет попереднього проєкту. За прийнятим Foundry handoff зберегти parent intent/IDs/authority; незмінне discovery та exact approval не повторювати.

Предметний аналіз визначає сутності, vocabulary/units, правила, state/commands/events, allowed writers, calculations/order/tolerance, uncertainty/abstention, failure/retry/recovery, data/rights і causal edges. Scenario grammar та variant matrix охоплюють лише застосовні normal/boundary/peak/failure/change/cold-return/end-of-service класи. Нову сутність чи суттєвий сценарій додати до брифу, не посилатися на відсутність у каталозі.

Архітектура однієї навички чи сімейства спирається на різні компетенції, stable artifacts, доступи, довгі цикли й незалежне повторне використання. Одна skill може мати багато фаз. Кожний edge має точні input maturity, output, consumer validation, failure/return і carry-forward. Команда пропорційна фактичним outputs; один writer на shared resource, реальні техліди-виконавці, незалежний reviewer для material acceptance, рада лише за потребою. Не створювати фіксованої армії ролей.

До build показати complete versioned blueprint зі складом sources/resources, методами, requirements/negative cases, inherited IDs, production recipes, actual capabilities/rights/costs/bridges, evidence і stop. C1 закриває trigger, правила, склад та materially important behavior; T налаштовує вже визначений метод у погоджених межах. Погодження стосується конкретної конструкції, exact target changes та чинного scope.

Кожний child отримує self-contained manifest, предметний workflow, потрібні bundled common resources, точні cases/oracles й return upstream. Посилання на parent без доступного вмісту не є спадкуванням; неперевірена назва tool не є production recipe. Verify поєднує quick_validate/consistency та доречні independent raw forward cases; структурний PASS не сертифікує предметну компетентність. Install/read-back/first useful use мають exact version і окремі факти. Refinement робить semantic delta, preserve map, dependency invalidation, targeted regression, supported save та rollback; не перепогоджує routine repair у чинних межах.
