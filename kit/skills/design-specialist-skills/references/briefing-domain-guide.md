# Adaptive briefing and resumption for Design Specialist Skills

The [topic catalogue](../assets/briefing-topics.json) maps known applicable questions. Select shared topics, active-stage topics, and early downstream dependencies. For each topic, keep a project-owned record of applicability and rationale, answers and exact sources, unknowns and conflicts, owner, affected IDs, due gate, and closure method. Add a missing material topic with a stable ID and the same fields. Extend the catalogue where needed. Mark unavailable access as blocked.

Read the actual request, current state, accepted originals, sources, versions and hashes, decisions, and supplied packages. Prefill answers with their provenance and applicability. Carry valid answers forward. On RESUME (`ВІДНОВИ`), check freshness, unresolved effects, the active stopping point, and changed dependencies. Retain accepted work and reopen affected questions. Use the local repair path when it suffices.

Define the full goal, separate launch and probe scopes, and rejected simplifications. Keep ambition separate from sequence. Let the evidence and the owner establish time limits, feature scope, input method, platform, monetization, and upgrade path. Research alternatives and bring any consequential gap between resources and quality to a concrete decision.

Select the earliest unresolved question that materially changes the goal, behavior, architecture, permissions, cost, risk, or acceptance. Resolve prerequisites first. Present feasible choices, consequences, and a recommendation based on project criteria. Verify market, demand, capability, pricing, and authority claims. Accept free-form answers and “I don't know.” An unknown answer delegates research, comparison, recommendation, and a counterargument. Preserve the existing authorization. Specialists establish technical facts within the agreed scope. The owner determines intent and material trade-offs.

After every answer, update applicability and dependencies, retire resolved questions, and include new material consequences. Group questions according to their relationships and the owner's ability to answer. Open a future topic now when its answer changes a current choice. A particular brief includes only relevant questions.

Use `criticality` to order work. `material` marks an important choice, `technical` work normally belongs to a specialist, and `future` marks a later parameter or proof. Consider material effects of all three. `answer_owner` distinguishes owner intent from specialist judgment. A `delegated` answer requires an actual assignment and returned result. Capture an actual acceptance decision separately from the request for it.

Before accepting an execution scenario, resolve all known applicable material questions in its current scope and their early downstream effects. Establish the architecture, promise, and core behavior by C1. Defer numeric T tuning or specific future inputs only with a baseline and range or invariant, owner, method or experiment, exact due gate, acceptance, affected IDs, and reopening condition. Resolve core rules before downstream work. Future device, human, and production evidence remains pending until observed. Keep structural validation, domain quality, permissions, installation, and live outcomes separate.

The selectors `intake`, `research`, `architecture`, `blueprint`, `build`, `verify`, `install`, `refine`, and `resume` all map to stable skill `design-specialist-skills`. These select constructor operations. Derive the future specialization's own stage graph from its outputs and consumers.

Recover the actual process, user, operator, administrator, data owner, raw inputs, desired outcome, and cost of errors. Compare the existing process, deterministic automation, reuse or refinement of a skill, an agent, and an app. Derive the domain from current sources. An accepted Foundry handoff carries parent intent, IDs, and authority. Reuse unchanged discovery and exact approval.

Domain analysis defines entities, vocabulary and units, rules, states, commands and events, authorized writers, calculations and ordering and tolerances, uncertainty and abstention, failure and recovery, data and rights, and causal dependencies. Scenario grammar and variant matrices cover applicable normal, boundary, peak, failure, change, cold return, and end-of-service cases. Add new entities and material scenarios when found.

Choose a single skill or a family according to distinct competences, stable artifacts, permissions, lengthy cycles, and independent reuse. A single skill can have many phases. Specify each handoff's input maturity, output, consumer validation, failure and return, and what carries forward. Size the team to actual outputs. Use one writer per shared resource, hands-on technical leads, an independent reviewer for material acceptance, and a decision group when needed.

Before building, show the complete versioned blueprint with sources and resources, methods, requirements and negative cases, inherited IDs, production recipes, actual capabilities, permissions, costs, bridges, evidence, and stopping point. C1 establishes trigger, rules, structure, and material behavior. T tunes the defined method within accepted bounds. Bind approval to the exact design, target changes, and scope.

Give every child a self-contained manifest, domain workflow, bundled common resources, exact cases and oracles, and an upstream return path. Bundle the inherited material it needs and verify real tool operations for recipes. Combine `quick_validate` and consistency with relevant independent tests using raw task inputs. Track actual install, read-back, and first useful use against the exact version. Refinement reviews semantic changes, maps preserved behavior, invalidates affected dependencies, runs targeted regression, and uses supported save and rollback. Carry forward authorization for routine repairs within the existing scope.
