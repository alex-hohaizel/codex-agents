# Production quality and reference fidelity

Use this contract when producing, selecting, changing or accepting an artifact. Apply only the relevant medium profile in `assets/production-profiles.json`. A narrow repair uses the accepted project profile; it does not restart discovery. The user's explicit scope, references and creative freedom decide the result. A simple composition can be excellent; generic simplification that loses the requested substance cannot satisfy the brief.

## Establish the actual target

Read the original task and the actual references before selecting tools or a shared renderer. Separate reference status: supplied inspiration, selected direction, approved master, rejected output. For every material reference property, record the role it plays: composition and relative scale, information density, visual mechanism, typography/material/light, interactions and motion, functional depth, content and first useful action. Preserve these properties or explain an intentional adaptation. Matching a palette or retaining the names of objects is not reference fidelity.

The production brief names audience/use, required outcome, exact source pins, acceptance criteria, editable master, target formats/environments, tool operation and parameter support, owner, resource bounds and repair stop. Do not infer missing behavior from decorative artwork. A platform illustration is a reference to translate into usable controls, real data and clear system states; it is not permission to fake those capabilities.

## Make the defining mechanism work first

Before batch production, implement one representative slice with real applicable content/state and the defining visual, auditory, narrative or interaction mechanism at the agreed level. Inspect it on the actual target medium, alongside the reference. The reviewer must answer what retained the character, what changed, and whether the useful task still works. Scale only after that benchmark is accepted for its scope.

Separate semantic reuse from presentation reuse during exploration. Shared data/time/auth rules do not require every concept to use the same cards, scene, voice, transitions or template. Conversely, once an identity is accepted, novelty or a model change does not authorize redesign. Do not repeatedly ask for preferences when the user already delegated creative decisions.

## Preserve identity and deliver usable output

Pin approved originals/editable masters, relevant tokens/rules, voice/persona, layout/motion grammar, recipes and allowed adaptations. A derivative records its master, transformation, intentional losses, export/import and consumer. Test identity at the integrated destination, not only at generation. Raster mockups, vectors, models, slides, audio and working interfaces are distinct output contracts.

Native object identity matters: edit an existing document in place through the supported route unless conversion/replacement was requested. Deliver the actual requested file type and editability, not a tool's default viewer. Check all relevant pages/slides/states/time ranges. For audio/motion, actual playback is required for claims about sound/timing; metadata and still images cannot establish those properties.

## Choose and verify operations

Select tools for the required operation, target quality, controllability/editability, continuity, rights, actual availability, cost, latency and maintenance. Prefer an existing sufficient route. Check current primary documentation and the actual host schema where facts can change. Bind material requirements to supported fields and verify consumption. A prompt asking for a property is not proof the tool supports it. Missing required capability is a gap with an exact bridge, not permission to lower quality silently.

Use `references/tool-compatibility.md` for known composition conflicts. Its guards apply when actually loaded. Direct vendor entry outside this bundle needs a verified host instruction route; a file or optional dashboard does not enforce every other chat. Never modify a vendor cache to manufacture a policy fix.

## Accept the right evidence

Keep functional, craft, source, runtime/integration, accessibility/device, independent review and owner acceptance separate. A test suite, screenshot count, role count or structural PASS does not certify artistic quality. Review actual output against the original intent, accepted benchmark and medium-specific oracle. Authors self-check; independent review requires a different actual actor with raw inputs and artifacts.

Repair the failed property with a changed hypothesis/variable and a bounded comparison. After repeated unchanged failures, change the diagnosis/tool/production method. Do not ask the user to accept a weaker output because time or tooling was spent. Retain useful functional behavior and already accepted corrections while repairing craft.

For a release, compare the unchanged baseline and candidate on the same raw tasks, tools and frozen rubric, plus holdout cases. Record model/tool/version changes and variability. Do not infer universal superiority or absence of all future regressions. Record unobserved qualities as unknown with the exact next verification.
