# Існуючий TatterJack: current intake 3.0 і історичні джерела

На початку фактичного продовження знайти поточний прийнятий studio package, exact master, їхні hashes та scope відповіді користувача. Для проекту Game of 2027 у R6 передано прийняті R10 originals; коли актуальний пакет/approval це підтверджує, саме вони є current identity. Назва TatterJack зберігається. Оновлення агента не дає дозволу на новий неймінг, redraw, зміну accepted reference, вибір гри або production.

Зіставити `accepted_studio`/manifest/master/approval refs із поточним registry; не вважати назву файла, останній переказ чату чи дату ZIP достатньою authority. Byte-identical master передавати з тим самим hash; матеріальний derivative має власний ID, recipe та review. Знак студії не погоджує повне тіло персонажа, костюми, лор або один art style усіх ігор. Ці рішення лишаються game-specific proposals, доки явно не прийняті.

До Game Model передавати studio envelope/usage/source IDs і відомі constraints, не дублювати невідомі legal/service values. Відсутній historical original або review позначати unavailable з next resolver step, а не відновленим зі спогаду. Історичний матеріал нижче корисний для діагностики drift, але не замінює current R10 master.

## Історичний аудит R8

Контекст прикладу перевірений 01.11.2026 за наданим `TatterJack_R8_Studio_Launch_UA.zip`. Цей reference — історичний кейс, а не live current project state. При фактичному запуску знайти й прочитати актуальний архів; його назва/версія може змінитися.

Назва TatterJack вже обрана користувачем. Не запускати неймінг заново. У перевіреному пакеті `01_BRAND/reference/Selected_R7_Application.png` — первинний selected image, тоді як `01_BRAND/brand_board.png` та generated SVG/PNG — інше виробниче відтворення. Root visual inspection зафіксував різницю між складним фактурним образом і спрощеним кутовим знаком/перемальованими літерами. `01_BRAND/source/README_UA.md` чесно каже, що reference PNG не вбудовується в логотипи, а геометрія задана полігонами/path-даними.

Тому назва файла `Primary`/`Master`, наявність source script або статус попереднього archive самі не доводять identity equivalence. Не називати існуючий пакет уже виправленим цією навичкою. Перш ніж ремонтувати: з'ясувати exact approved visual master, показати original/derivative/delta й обрати faithful reuse/extraction або явно погоджений redraw. User вибір назви не є автоматичним вибором нового lettering.

Originals/історичні hashes не змінювати. Створити successor work copy, visible gap register, exact target і current acceptance. Наступним навичкам передавати лише прийняті variant IDs; якщо потрібна variant pending — відповідний UI/store use лишається blocked, незалежна робота триває.
