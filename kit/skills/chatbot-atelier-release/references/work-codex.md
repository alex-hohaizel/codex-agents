# Work, Codex та перенесення

Одна поточна семантична специфікація для обох середовищ; різниця — фактичні capabilities, доступи й target evidence, а не спрощена методика. На початку скласти capability snapshot: tools/connectors, local executor, network, private repo, DB sandbox, runtime/media/device interfaces, costs/authorization. «Є навичка» не означає встановлений framework, доступ до Telegram, сервер чи право читати чат.

Work придатний до discovery, актуального research, UX/діалогових сценаріїв, аналізу наданих артефактів, генерації дозволених матеріалів, connector audits й виконання коду там, де доступний executor. Codex у checkout придатний до source changes/build/tests/migrations/CI за доступом. Обидва можуть виконувати частину іншого; рішення за перевіреною операцією, не назвою середовища.

Handoff містить intent/requirements IDs, full domain rules, primary source map, exact artifacts/hashes, selected architecture/alternatives, applicability й unresolved questions, operation passports/recipes, attempts/job IDs, evidence limits, authorizations, commands, environment selectors без secrets, locks/ownership, receiver, next action/acceptance/return-upstream. Cold receiver повинен продовжити без історії чату. Повернутий код/asset/звіт перевіряти проти input snapshot і current state before merge.

Для встановлення skill assets самодостатні, без прихованої залежності на sibling director. Optional custom roles активуються лише коли підтримані; policy/schema верифікувати за актуальною офіційною документацією й локальною конфігурацією. Функції історичних ролей збережені в stage/team контрактах; їх початкові файли є в окремому архіві джерел і не встановлюються автоматично.

Підтримувати лише поточні output formats за protocols.md. Старий агентський dossier не є передумовою: відновити авторитетні вимоги, фактичний repo/state й сформувати поточний запис. Runtime/toolchain, тести, каталог матеріалів і hosting перевіряти по конкретному проєкту; дані/поведінку чинного бота зберігати за його продуктовими контрактами.
