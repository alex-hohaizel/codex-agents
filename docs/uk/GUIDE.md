# Agent System — повна інструкція зі спільної роботи Work + Codex

[English](../en/GUIDE.md) · [Українська](../uk/GUIDE.md) · [Deutsch](../de/GUIDE.md) · [Italiano](../it/GUIDE.md) · [Español](../es/GUIDE.md) · [Français](../fr/GUIDE.md) · [中文](../zh-CN/GUIDE.md)

**Базова версія інструкції:** Agent System 6.0.0, 9 листопада 2026 року. **Багаторазовий комплект:** 33 навички. Ця інструкція охоплює нове встановлення, щоденну роботу, спільне ведення проєкту в Work і Codex та оновлення наявного проєкту. Документація репозиторію та редакції пакетів можуть змінюватися без зміни базової версії навичок; перед оновленням прочитайте запис про реліз.


**Поточний реліз:** комплект 6.0.0, репозиторій 1.2.2, додатковий Atelier Orchestrator 1.0.1 і локальний Agent Atelier 0.1.1. Перед оновленням прочитайте [точну міграцію 6.0](../../releases/migrations/6.0.0.md). Попередня кампанія 1.1.0 збережена без змін: [англійська реклама](../../marketing/campaign/README.md) та [українська реклама](../../marketing/campaign/README.uk.md), по десять матеріалів кожною мовою. Реклама доступна EN/UK; посібники й інтерфейс сервісу охоплюють усі сім заявлених мов. Фактичний аудит, оновлення, встановлення й керування WORK залишаються окремою задачею відповідного середовища; архів джерел або підключення репозиторію не є квитанцією встановлення.

## 0. Оновлення до 6.0 і запуск локального робочого простору

1. Оберіть точний перевірений commit релізу. Збережіть поточні джерела 33 навичок, файли іконок, їхні прив’язки/кольори/класи, локальні зміни та записи належності. Збережіть предметні вимоги проєкту, прийняту ідентичність/персону, рішення, дозволи, незавершені завдання й невизначені зовнішні результати. Установлення не мігрує продукт.
2. Із `kit/` прочитайте довідку переносної програми оновлення, потім перевірте точного кандидата. До застосування перегляньте всі 33 записи, конфлікти й збереження ідентичності. Тримайте плани та резервні копії поза каталогами виявлення навичок.

```bash
python3 portable/update_skill_suite.py --help
python3 portable/update_skill_suite.py audit --kit . --plan /absolute/agent-system-plan.json
python3 portable/update_skill_suite.py apply --plan /absolute/agent-system-plan.json
python3 portable/update_skill_suite.py verify --kit . --journal /actual/apply/journal.json
```

3. Замість умовного шляху журналу використайте лише фактичний шлях, повернений apply. Невідомі відмінності потрібно з’ясувати; не примушуйте перезапис. Окремо перевірте фактичне виявлення/завантаження джерела й одне обмежене завдання. Чинні іконки та сторонні навички зберігаються.
4. Окремо перевірте профіль середовища Codex із кореня репозиторію: `python3 scripts/install_host_profile.py audit --plan /absolute/host-plan.json`. Застосуйте через `apply --plan /absolute/host-plan.json --journal /absolute/host-journal.json`, потім `verify --journal /absolute/host-journal.json`. Керований блок зберігає наявні глобальні інструкції; дванадцять обмежених ролей зберігають моделі й заборони зовнішніх ефектів. Завантаження в реальному середовищі перевіряється окремо.
5. Установіть додатковий `atelier-orchestrator` штатним менеджером навичок із `optional-skills/atelier-orchestrator` обраного commit. Він окремий від програми оновлення 33 базових навичок; наявність джерела не доводить установлення чи успішне виконання. Чинна навичка супроводу також залишається окремою необов’язковою складовою.

Atelier Orchestrator — додаткова координаційна навичка: відновлює контекст, добирає доступних спеціалістів, узгоджує їхні результати й може використовувати локальний сервіс для погоджених завдань. Agent Atelier 0.1.1 — окремий локальний застосунок/сервер, який відкривається через власну програму запуску; це не запис у переліку навичок. Їхні версії незалежні. Orchestrator 1.0.1 узгоджує основні інструкції, відображуваний текст і стартовий запит з українським оформленням базових навичок та підключає PNG-відтворення незміненого SVG значка для сумісності. Дивіться [адресне оновлення й відкат](../../releases/migrations/repository-1.2.2.md). Наявність джерел не доводить установлення у WORK.

6. Для складання локального сервісу з джерела використайте зафіксований файл блокування версій залежностей з Node.js 24.22.2 або підтримуваною новішою версією. Із `apps/agent-atelier/` виконайте наведене нижче. Перше встановлення залежностей потребує мережі; нова платна послуга цим не передбачається.

```bash
npm ci --ignore-scripts
npm run build
node launcher/atelier.mjs start
node launcher/atelier.mjs status
node launcher/atelier.mjs doctor
node launcher/atelier.mjs stop
```

7. На Mac після складання подвійний клік `apps/agent-atelier/launcher/Agent Atelier.command` запускає сервіс. Запускач відкриває локальну адресу loopback, використовує свій уже запущений екземпляр й не вмикає автозапуск під час входу. Оберіть і попередньо перевірте конкретний корінь проєкту, потім прив’яжіть його. Прив’язка — це виявлення проєкту лише читання, а не прийняття нових правил продуктом чи дозвіл на всі майбутні завдання. Режим демонстрації містить вигадані дані й не виконує команд.
8. Підготуйте завдання з точними обсягом, входами, прийманням і межами, потім запустіть підтримуваним адаптером Codex. Джерело, художня якість, інтеграція, пристрій, незалежна перевірка й приймання власником мають різні стани. Переривання підтверджується лише фактичним результатом середовища. Наявні чати потребують точної ідентичності/cwd та передачі в стані спокою; lease сервісу не блокує стороннього desktop writer. Перед повтором звірте невизначений зовнішній результат. Під час підготовки завдання сервіс фіксує точні джерела керівних інструкцій AGENTS, порядок їхньої пріоритетності або підтверджену відсутність, а також налаштування завантаження інструкцій у самому Codex. Він звіряє ці записи з фактично завантаженими джерелами інструкцій і повторно перевіряє їх перед викликом моделі. Якщо ці входи змінилися або старіше завдання не має таких записів, завдання потрібно підготувати знову; його історія й нативні файли продукту зберігаються.
9. Чинні сесії Foundry використовують `suite-update-plan` і перевірений запис `refresh --accept-suite-update` з точними відбитками вихідного стану/цілі. App state/1 не потребує міграції формату через версію інструментарію. Для інтегрованих доказів Chat потрібні актуальні відбитки предметного контракту й справжнє нове спостереження; старі докази не доповнюють заднім числом. Game використовує підтримуване оновлення робочого процесу 5→6, зберігаючи runtime2/model4/handoff1. Створені агенти потребують порівняння джерело→ціль і відновлення без історії чату; жодний проєкт не скидається.
10. Резервування/відновлення сервісу стосується лише його власного стану: попередньо перевірте точну копію, звірте роботи і збережіть відкликані дозволи; це не відновлює продуктові БД чи зовнішні ефекти. Відкат навичок використовує фактичний журнал програми оновлення; відкат профілю середовища — власний журнал і відхиляє пізніші відмінності. Фактичні встановлення/керування WORK відкладені. Прочитайте [докладну міграцію](../../releases/migrations/6.0.0.md) та [інструкцію сервісу](../../apps/agent-atelier/README.md) щодо відновлення й підтримуваних меж.

## 1. Що ви отримуєте

Опишіть потрібний результат звичайною мовою. Система допоможе перетворити його на конкретну задачу, залучить доречні спеціалізації, збереже разом рішення та вимоги й перевірить результат щодо погодженої мети.

Наприклад, «Допоможи знизити навантаження на базу даних у цьому бекенді» може перетворитися на предметне дослідження запитів, меж транзакцій, кешування, вимірювання продуктивності та перевірену зміну. «Створи мобільний застосунок для цієї аудиторії» потребує ширшого маршруту: дослідження, вибору продуктового напряму, дизайну, архітектури, реалізації, перевірок якості, підготовки випуску та експлуатації. Невелике виправлення має залишатися невеликим виправленням. Цілісний продукт має зберігати весь набір вимог, зокрема частини, заплановані після першої робочої версії.

**Навичка** — це багаторазовий набір робочих інструкцій, довідкових матеріалів та інколи скриптів. **Агент** застосовує роль і ці інструкції до задачі. **Директор** координує продуктове сімейство. **Конструктор** проєктує спеціалізованого агента або багаторазовий набір навичок, коли наявні сімейства не покривають роботу. Вони працюють через ChatGPT або Codex та інструменти, фактично доступні в цьому середовищі. Встановлення інструкцій не створює запущеного сервера, не купує послуг, не надає прав до репозиторію й не запускає постійний фоновий процес.

Цінність полягає в організованому процесі: спільний бриф, явні вимоги, доречні спеціалісти, збережені рішення, перевірні передачі роботи та можливість її відновити. Репозиторій не заявляє виміряну перевагу, гарантований дохід, гарантоване схвалення магазином або автоматичну готовність до production.

У Work звична форма — `@skill-name`; у Codex — `$skill-name`. Доступні селектори та відображувані назви можуть відрізнятися між версіями середовища. ```

Концептуальне зображення не може довести анімацію, сенсорне керування, продуктивність або відновлення збережень. Ігровий процес роботи має пов’язувати обрану візуальну обіцянку з редагованими оригіналами асетів і показовим ігровим зрізом до створення повного набору матеріалів.

## 8. Work і Codex в одному проєкті

Work корисний там, де доступні потрібні джерела, інструменти дослідження, дизайну й підключені сервіси. Codex корисний там, де доступні робоча копія джерел, середовище виконання, інструменти збірки та пристрої або локальні інтеграції. Кожен режим може робити більше за наявності потрібних можливостей. Обирайте за фактичним доступом і доказами, а не закріплюйте всі розумові задачі за одним режимом, а весь код — за іншим.

Створіть одну ідентичність продукту. Назви на кшталт `My Product [WORK]` і `My Product [CODEX]` полегшують навігацію, але не доводять, що два проєкти містять один продукт. Зафіксуйте репозиторій, гілку, підкаталог, ідентифікатори проєкту й джерела checkpoints. Новий чат має залишатися всередині цього наявного проєкту.

### Зберігайте невеликий спільний контекст

Використовуйте шаблон контексту проєкту з репозиторію або наявний рівнозначний файл у вашому продукті. Зафіксуйте щонайменше: ідентифікатор проєкту; репозиторій і гілку; поточний повний commit SHA; ідентифікатор задачі; поточний етап; робочу мову й мови продукту; версію комплекту та квитанцію встановлення; прийняті рішення; повне джерело вимог; джерело дизайнерських еталонів; надані повноваження; поточний checkpoint; невирішені наслідки або рішення; наступну дію. Не включайте до цього запису облікові дані доступу.

### Work → локальний Codex, покроково

1. Попросіть Work: «Продовж цей етап у Codex. Підготуй передачу роботи для цього наявного проєкту».
2. Work має визначити точний наступний результат і докази, потрібні для його приймання. Він має зберегти або надати відповідні вимоги, рішення, джерела й checkpoint.
3. Якщо доступний дозволений спільний канал, Work може зберегти передачу й перевірити збережену ревізію. Збереження файлу не доводить запуск іншої сесії Codex.
4. Відкрийте наявну локальну робочу копію. Якщо локальної копії немає, клонуйте підтверджений репозиторій і гілку в обрану папку. Для приватних репозиторіїв пройдіть локальну автентифікацію.
5. Перш ніж оновлювати робочу копію, перевірте її:

```bash
git remote get-url origin
git branch --show-current
git rev-parse HEAD
git status --short
```

6. Якщо робоче дерево чисте й потрібне оновлення цієї гілки, використайте `git pull --ff-only origin <confirmed-branch>` зі справжньою назвою гілки. Підтвердьте отриманий повний SHA. Якщо є локальні зміни або розбіжна історія, збережіть їх і усуньте розбіжність до залежної роботи.
7. Відкрийте точну папку в інтерфейсі проєктів Codex. Для наявного продукту використовуйте його наявний проєкт; за потреби додайте папку через доступний інтерфейс редагування проєкту.
8. Вставте заповнений блок передачі нижче. Codex спочатку підтвердить ідентичність репозиторію, ревізію, локальні зміни, повноваження й checkpoint, а потім працюватиме над визначеною дією.
9. Збережіть його звіт про результат, посилання на commit/збірку й докази тестів для зворотної передачі.

### Codex → Work, покроково

1. Попросіть Codex підготувати передачу результату або нової задачі для того самого наявного проєкту.
2. Включіть фактично змінені файли, повний SHA або ревізію артефакту, проведені перевірки, обмеження, відкриті рішення й наступну дію. Вкажіть, чи зміни локальні, закомічені або опубліковані.
3. Якщо публікацію погоджених змін до вказаної гілки дозволено, опублікуйте лише ці межі та перевірте віддалену ревізію. Інакше надайте контрольований артефакт через доступний канал. Локальний шлях Mac автоматично не стає доступним для читання з Work.
4. Відкрийте наявний проєкт Work, підключіть відповідний репозиторій або прикріпіть точний артефакт і вставте передачу.
5. Work прочитає фактичні джерела й перевірить вхідну ревізію до рев’ю або продовження. Він має явно повідомити про недоступні файли.
6. Фіксуйте приймання окремо від доставки й виконання. Звіт про наявність збірки не дорівнює прийманню продукту.

### Блок передачі для копіювання

Перед використанням замініть кожне поле в дужках:

```text

Розрізняй підготовлену передачу, перевірену доставку, отримання, виконання,
результат і приймання. Продовжуй дозволену роботу, яка фактично можлива.
```

## 9. Відновіть роботу після перерваного чату

Відкрийте новий чат у тому самому проєкті й попросіть відновити останній перевірений checkpoint. Надайте його джерело, якщо воно ще недоступне. До продовження агент має узгодити задачу, вимоги, ревізію джерел, поточні файли й фактичні зовнішні результати.

```text
Віднови цю наявну задачу з останнього перевіреного checkpoint і фактичних джерел.
Збережи вимоги, рішення, повноваження, завершені результати та невизначені
зовнішні наслідки. Перевір поточну ревізію й відповідального за наступну дію.
Перед повторним розгортанням, платежем, повідомленням або іншою зовнішньою дією
перевір, чи попередня спроба фактично завершилася. Продовжуй доступну дозволену
роботу й запиши новий checkpoint.
```

Зависла розмова не доводить невдачу останньої операції. Перед повтором дії, яка може виконатися двічі, відновлення має перевірити реальний результат.

## 10. Оновлюйте версії без втрати наявного проєкту

### Спочатку прочитайте запис про реліз

Кожен реліз має пояснювати зміни, кого вони стосуються, передумови, кроки встановлення, кроки прийняття в проєкті, перевірку, відомі обмеження й відкат. Загальна інструкція також має змінюватися, коли змінюється звичайний процес. Не покладайтеся лише на номер версії.

Реліз 6.0.0 зберігає 33 стабільні назви й ідентичність іконок, посилюючи перевірку доказів, залежностей джерел, читання JSON і запису стану. Він додає самодостатні виробничі/контекстні профілі та явну відповідність референсам. Історичні номери протоколів і предметних схем виконання залишаються окремими; перейменування старої схеми на номер комплекту без міграції порушує сумісність.

### Наявні проєкти Agent Systems 2.3 / Game 4.3

1. Збережіть поточний checkpoint проєкту, прийняті вимоги, рішення, дизайнерські оригінали, ревізію джерел, версію комплекту й відомі зовнішні наслідки.
2. Зафіксуйте, звідки фактично завантажується кожна навичка або проєктний агент. Проведіть інвентаризацію персональних і локальних проєктних копій; не припускайте, що зміна одного глобального каталогу змінює кожен проєкт.
3. Установіть цільовий комплект відповідним маршрутом Work або Codex вище. Збережіть версію джерела й квитанцію встановлення.
4. Повторно відкрийте наявний проєкт і проведіть read-only перевірку сумісності до наступної залежної дії.
5. Попросіть його директора або конструктора порівняти поточний стан проєкту з новим процесом. Визначте явне оновлення native-стану або workflow лише там, де це потрібно. Збережіть поведінку продукту, прийняті рішення й невідомі наслідки.
6. Попередньо перегляньте точні зміни. Якщо потрібна міграція стану, використовуйте підтримуваний інструмент і фактичний `--help`; прив’яжіть preview до хешу вихідного стану, хешу цільового комплекту й джерела повноважень. Застосуйте дозволений перевірений план замість вигадування історичного погодження.
7. Повторно перевірте кожну зачеплену вимогу та критерії приймання поточного етапу. Виконайте невелику реальну задачу продовження й збережіть докази.
8. Запишіть прийняту версію комплекту в checkpoint продукту. Збережіть запис міграції, щоб наступний чат міг пояснити перехід.

Game6.0.0 містить маршрут перевіреного workflow-upgrade для проєктів 4.2.0/4.3.0/5.0.0 зі збереженням runtime schema 2.0.0. Його застосування залежить від фактичного стану проєкту й підтримуваних входів інструмента. Проєкти App і ChatBot так само потребують власної перевірки стану та сумісності; їх не можна пропускати через ігрову міграцію лише тому, що комплект має одну спільну версію.

### Агенти, раніше створені конструктором

Оновлення конструктора не переписує агентів, яких він створив раніше. Ці агенти можуть містити проєктні правила, інструменти, знання й візуальну ідентичність. Проведіть їх інвентаризацію у власних проєктах. Порівняйте старе джерело, локальні зміни й запропоноване нове джерело. Збережіть оригінальні докази власника та встановлення. Якщо їх немає, підготуйте явне порівняння й план прийняття; не вигадуйте стару квитанцію. Виконайте регресійні сценарії для фактичних обов’язків агента й окремо зафіксуйте прийняту версію.

Багаторазовий репозиторій не містить приватних пакетів джерел продуктових агентів. Оновлення окремого проєкту належить до контрольованих джерел і запису міграції цього проєкту, а не до глобального встановлення навичок для всіх.

### Зберігайте візуальну ідентичність

Наявні іконки Codex, шляхи до них, колір і байти іконок мають переживати звичайні оновлення. Нова версія не є дорученням переробити дизайн наявної навички або продукту. Нові навички без ідентичності можуть отримати відповідний системний або проєктний стиль. Work може сам керувати службовим аватаром; відділяйте його поведінку відображення від переносної ідентичності Codex. Зберігайте обрані оригінали дизайну продуктів та ігор, а не лише їх словесний опис.

### Відкочуйте обережно

Для встановлення комплекту Codex використовуйте точний журнал встановлення:

```bash
python3 kit/portable/update_skill_suite.py rollback --journal /absolute/path/from-apply/journal.json
```

Відкат перевіряє резервні копії й захищає пізніші невідомі зміни. Він скасовує встановлення навичок, представлене цим журналом. Він не скасовує міграцію даних продукту, розгортання, повідомлення, покупку або іншу зовнішню дію. Відновлення Work має використовувати підтримуваний маршрут керування навичками й збережене попереднє джерело. Для відкату стану продукту потрібна власна перевірена процедура відновлення.

## 11. Зберігайте повноту майбутніх оновлень

Для кожної майбутньої зміни комплекту оновлюйте цей репозиторій канонічними джерелами, зачепленими вимогами, вмістом пакетів, записом версії, кроками міграції, доказами перевірки й необхідними змінами інструкцій або перекладів. Зберігайте записи попередніх релізів. Перебудовуйте пакети й метадані цілісності з перевірених джерел; уникайте публікації архіву, зібраного із застарілого кешу середовища.

Виконуйте команди перевірки й пакування репозиторію відповідно до їх поточного `--help` і документації супроводу. Після публікації підтверджуйте віддалений commit. «Збережено локально», «закомічено», «опубліковано», «встановлено», «завантажено» й «прийнято проєктом» — окремі статуси. Якщо доступ перешкоджає публікації, збережіть завершену роботу й повідомте точну несинхронізовану ревізію.

Правило репозиторію діє, коли майбутній агент його читає в середовищі з потрібним доступом. Це не глобальний слухач усіх інших чатів і комп’ютерів. Починайте майбутню задачу керування навичками з підключення цього репозиторію та читання його `AGENTS.md`, вимог і останнього запису релізу. Окремий сервіс планової синхронізації потребуватиме власного реального середовища виконання й дозволу; комплект не створює його непомітно.

## 13. Офіційна документація та межі доказів

Інтерфейси середовища й доступність облікових записів можуть змінюватися. При встановленні або підключенні сервісів звіряйтеся з фактичним інтерфейсом і поточною офіційною документацією. Посилання щодо поведінки продуктів перевірено для цієї інструкції 7 листопада 2026 року:

- [Build skills — ChatGPT Learn](https://learn.chatgpt.com/docs/build-skills): структура багаторазових навичок, принципи локального виявлення й встановлення.
- [Plugins — ChatGPT Learn](https://learn.chatgpt.com/docs/plugins): каталог плагінів, принципи підключення й розповсюдження.

Цей репозиторій розповсюджує багаторазовий комплект і його контрольований процес встановлення. Публічний плагін маркетплейсу, комерційна ліцензія, постійне хостингове середовище, сторонні платні інструменти й облікові дані — окремі результати, якщо конкретний реліз явно їх не надає й не перевіряє. Маркетингові концепції ілюструють процеси та передбачені застосування; фінальні рекламні твердження мають відповідати перевіреним можливостям і доказам.
