# Proposed AI, data, ML and creative capabilities

**Passport `ai-data-production-evolution/0.2` — proposal for approval; documentation revision only.** Researched 10 November 2026 against repository 1.3.0, core 6.0.0, optional Orchestrator 1.1.0 and Agent Atelier 0.2.0 at `8951398b38a9610854823302ea612cb3844d52e6`. This document does not create or install skills, roles, frameworks, trained models, vendor integrations or a deployed product. Source/runtime implementation requires its own exact approval; the current authorization covers revising and publishing the proposal.

For each capability below, the user gets a useful product result and the next person gets understandable, editable sources, a launch procedure, checks and known limits. Technology names are options. They do not become compulsory dependencies, new spending or permission to alter an existing product. [Dated primary sources and source anchors](SOURCES.json) record what informed the proposal.

## C00. What exists and what is proposed

The current system already describes full application, chatbot and game development, proportionate architecture, API contracts, permission boundaries, durable effects, media identity, QA, release and recovery. Its knowledge skill already covers conditional RAG, corpus preparation, retrieval evaluation, access control, deletion of derived embeddings/caches and restore limits. Growth already separates correlation, attribution and causal effect. These foundations should be reused rather than replaced. See [application contracts](../../../kit/skills/app-atelier-specification/references/app-system-contract.md), [knowledge](../../../kit/skills/chatbot-atelier-knowledge/SKILL.md), [integration](../../../kit/skills/chatbot-atelier-integrations/SKILL.md), [growth](../../../kit/skills/app-atelier-growth/SKILL.md) and [quality](../../../governance/QUALITY_MODEL.md).

What is missing from the reviewed reusable sources is a sufficiently explicit, testable data/ML lifecycle: source collection, dataset/feature versions, leakage-safe training and evaluation, model delivery, prediction uncertainty, adaptation, batch accounting and operational adoption. Existing validators check important structures; they are not trained models, extraction services or media-generation workers. This research did not run a crawler, call a paid generation API, download weights, train, benchmark the owner's Mac or deploy a product.

The seven entries below are **conditional competence profiles and recipes inside the existing 35 reusable sources and 12 host roles**. They are implementation guidance, not installed skills, selectors, processes or additional mandatory roles. Existing product directors, constructors, knowledge, media and QA owners are used first. The nine audit responsibilities and all 17 requested capabilities remain in scope; context continuity, professional design and a genuinely working source-backed panel have implementation priority. Lower priority does not remove or defer any capability from the agreed complete scope.

| Conditional profile | Responsibilities | Useful result | Existing route first |
|---|---|---|---|
| DATA | D1 acquisition; D2 quality, versions and lineage | A dependable, restartable source-to-dataset pipeline | Current product integrator + build/integrations/knowledge |
| ANALYSIS | D3 NLP, clustering and trends | Evidence-linked findings a team can act on | Current product/research/knowledge + relevant engineering and QA |
| LLM | D4 LLM, retrieval and agent workflows | A bounded AI function integrated into the product | Current product director + knowledge/integrations/build |
| PREDICTION | D5 predictive ML; D6 honest pre-launch CPA | A validated forecast, ranking or an explained data gap | Current product integrator + architecture/backend/cost + independent QA |
| ADAPTATION | D7 open models, LoRA and deployment bundles | A justified, evaluated model adaptation | Current product integrator + existing engineering/reliability/privacy/QA |
| MEDIA | D8 batch text, image, audio, video and other assets | Consistent, editable materials delivered into their actual consumer | Existing App experience, ChatBot media or Game assets owner |
| EVALUATION | D9 productionization acceptance; evaluation across D1–D8 | Independent evidence that the integrated result meets its brief | Existing family QA, independent reviewer/judge and current integrator |

A separate skill, independently packaged competence module or host role may be extracted only after a real task demonstrates a reusable distinct output, measurable benefit over the existing route and preservation of the complete baseline. Any resulting addition changes the exact composition and needs a revised, explicit composition approval. A new name, instruction wrapper or role count is not evidence of added competence.

## C01. Shared execution and evidence

Every substantial recipe starts from the accepted outcome, current project owner, actual source revision, identity references, existing settings, unfinished requirements and valid authorization. A specialist receives only its work package, owned paths, input hashes, interfaces, cost/effect limits, acceptance and return destination. It reports the actual outcome and unresolved dependencies back to the same product owner. A brief is not restarted because a different specialist joins.

Use the current project ledger for authority and task state. Dataset, model, prompt, run, batch and proof records are typed artifacts referenced from that ledger, not a competing mutable truth store. The proposed 13 common records are `SourceContract`, `DatasetManifest`, `SplitManifest`, `FeatureManifest`, `PredictionContract`, `WorkflowRun`, `EvaluationPlan`, `EvaluationReport`, `TrainingRecipe`, `ModelBundle`, `BatchPlan`, `ItemManifest` and `GenerationBatch`. Their schemas/helpers still need approved implementation. Instantiate only the records applicable to the work package; do not impose all 13 on a narrow task. A required missing record remains a gap. A template becomes a project record only after its inputs, owner and consumer are bound.

`WorkflowRun` records actual execution: bound recipe/inputs, owner, environment, node/attempt states, checkpoints, effect identities, external IDs and unresolved outcomes. `EvaluationPlan` specifies cases, metrics and acceptance before the check; `EvaluationReport` records what was checked, by whom, against which exact bytes, with results and limits. `BatchPlan` specifies the intended set, recipe, constraints and budget; `ItemManifest` identifies each requested item/variant and its lineage; `GenerationBatch` accounts for an actual batch's attempts, item outcomes, outputs, rejections, unknowns and costs. A plan or manifest alone cannot acquire an executed status.

Terms used below: a **baseline** is the initial method a new candidate must improve on; **holdout** is protected data not used to choose the model; **features** are inputs available at prediction time; **lineage** links an output to its sources and transformations; a **manifest** lists exact items/versions; a **hash** detects changed bytes; a **fixture** is a controlled test input; **serving** is running the selected model for the product; **rollback** restores a known compatible version. None of these labels alone establishes quality or trust.

Record stages separately: **specified**, **structurally checked**, **executed**, **evaluated**, **integrated**, **observed on the actual target**, and **accepted by the owner**. A file or package installation proves none of the later stages. A reviewer must name the exact artifact/revision, environment, procedure, result and limitation. A new actor ID alone is not proof of expertise or independence.

Before an external operation, verify its actual schema, endpoint/model availability, rights, credential scope, rate and resource limits, cost, retention and supported output. Record the operation before dispatch; preserve actual request/job IDs, receipts, usage and uncertain outcomes. Reconcile a lost acknowledgement before retrying a potentially paid or irreversible effect. Public documentation does not prove account entitlement or local availability. Old proof does not transfer to changed data, prompts, weights, exports or runtime bytes.

**Mandatory real-task comparison and nonregression.** Before adopting an update, run the current and candidate routes on an authorized real task with the same accepted scope, inputs, references, rights, relevant environment and resource envelope. Declare the intended improvement and acceptance before the comparison. Check original intent/context, functional depth, craft and identity, correctness, privacy, reliability, user control, resource/cost behavior and maintainability, including dependent paths. Reject every demonstrated regression in a preserved property or agreed limit; improvement elsewhere cannot compensate. Missing proof keeps the affected gate open. Synthetic fixtures remain useful negative controls but do not replace this comparison. Retain exact baseline/candidate bytes, observed results, competent independent review and rollback evidence. New capabilities without a comparable old output need their own real useful-output proof as well as unchanged-path checks.

**Development login and production authentication are separate.** Owner-authorized local Codex execution may use the supported authenticated Codex bridge. A product serving its own users needs the appropriate production API/provider account or an explicitly operated local model service, server-side secret handling, user/tenant authorization, quotas and operational ownership. The owner's ChatGPT/Codex login is not automatically a commercial product backend credential. A bridge connection is not deployment proof. [Codex App Server](https://learn.chatgpt.com/docs/app-server).

## C02. DATA — collect reliable, usable data

**Activation and inputs.** Use for recurring API imports, document ingestion, crawling, exports or datasets feeding analytics, training or generation. A one-off page read needs proportionate handling. Establish the decision served, sources, access and reuse/transfer rights, fields, scope, frequency, expected coverage, privacy/retention, consumer, budget and stop conditions. Viewing a public page, automating collection, reusing its contents and sending them to a model are different permissions.

**Recipe.** (1) Choose a supported API/export when sufficient; static HTTP parsing for static content; browser automation when rendering/interaction is necessary. (2) Bind actual source/schema/auth/rate behavior. (3) Preserve permitted raw observations or explain retention limits. (4) Normalize types, units, currency, nulls, identifiers and event/observation/availability times. (5) Validate, deduplicate and quarantine invalid records. (6) Commit data and progress with explicit restart semantics. (7) Emit a versioned manifest, coverage and lineage report. (8) Prove replay and the consuming product path.

**Artifacts.** Connector and transformations; `SourceContract`; schema/fixtures; raw/normalized references; `DatasetManifest`; rejected records with reasons; cursor/watermark state; job/run/input/output links; counts, gaps and recovery runbook. Preserve the whole denominator. A successful HTTP status with a login page, repeated cursor or unexpectedly empty body must not quietly become a complete dataset.

**Acceptance and failures.** Exercise repeated pages, duplicates, missing pages, late events, schema/unit/timezone changes, 429, timeouts and crash after writing data but before checkpoint. Verify revoke/delete through derivatives, stale-cache invalidation and restore limits. Declared lineage and observed runs remain distinct. Scrapy persistence can help resume a crawl; it is not an atomic dataset commit. AutoThrottle is not permission or a guaranteed hard quota. [Scrapy jobs](https://docs.scrapy.org/en/latest/topics/jobs.html), [throttling](https://docs.scrapy.org/en/latest/topics/autothrottle.html).

**Cost and choice.** Bound requests, bytes, concurrency, retries, storage and browser time. Use browser automation only for the required behavior; maintain API/static alternatives where useful. Playwright supports network observation and fixtures, not source rights. A small versioned manifest may suffice; OpenLineage's separate Job/Run/Dataset concepts help larger integrations without making a lineage server mandatory. [Playwright](https://playwright.dev/python/docs/network), [OpenLineage](https://openlineage.io/docs/spec/object-model/).

## C03. ANALYSIS — turn feedback and signals into findings

**Activation and inputs.** Use for reviews, support messages, topic discovery, segmentation, classifications and trends. Decide what action the analysis informs, the unit of analysis, languages, sampling, labels/rubric, time windows, source coverage and sensitive-data handling. Retrieval for an answer, classification, unsupervised clustering and a causal business conclusion are different tasks.

**Recipe.** (1) Inspect a representative authorized sample. (2) Establish a simple measurable baseline. (3) Normalize languages, duplicates, author/bot weighting and relevant time fields without erasing meaningful differences. (4) Choose rules, a classifier, embeddings/clustering or structured LLM extraction where it improves the task. (5) Preserve membership, noise/outliers and source evidence. (6) Evaluate labels or cluster stability and inspect errors. (7) Compare time periods with stable coverage. (8) Deliver a readable, source-linked result and the executable update job.

**Artifacts.** Corpus/version and sampling report; label guide and reviewed examples; extraction/analysis code; typed output; topic/cluster assignments including noise; evidence links/quotes; changes over time; error/stability report; update/failure procedure. An attractive chart without its corpus, denominators and method is incomplete.

**Acceptance and failures.** Test duplicate domination, small language groups, mixed sentiment, unsupported claims, outliers, seed/sample/embedding changes and collection gaps. For classification, use appropriate held-out labels and disagreement analysis. For clustering, evaluate useful, stable meanings as well as suitable geometric measures: silhouette is not a business-quality oracle and favors some shapes. Distinguish actual topic change from changed sources, delayed ingestion or sampling. [Clustering evaluation](https://scikit-learn.org/stable/modules/clustering.html).

**Cost and choice.** Cache unchanged transformations and embeddings with source/model/privacy versions; use bounded samples for exploration and the complete required set for final production. A deterministic count or SQL query can be better than an LLM. Embedding similarity does not establish truth, importance or permission to expose a source.

## C04. LLM — build bounded AI functions and workflows

**Activation and inputs.** Use when a product needs generation, extraction, question answering, retrieval, tool use or stateful agent work. Preserve current native orchestration when sufficient. Define user journeys, allowed tools/actions, corpus rights, output semantics, abstention/fallback, privacy, quality cases, latency and cost before choosing a framework.

**RAG only after a demonstrated retrieval need.** Exact operational facts—accepted decisions, current native state, task/job status, source revisions, rights and receipts—come from the authoritative native files or supported host/service interfaces with exact bindings and freshness checks. They are not reconstructed from a semantic index or model summary. Do not create a separate global index of the owner's projects/chats for this integration or treat a derived index as a new authority store. For an authorized document corpus where retrieval is justified, use a scoped, derived index with source/tenant/ACL/version/deletion controls and separate retrieval/answer evaluation. Simple current-source reads, search or SQL remain valid choices.

**Recipe.** (1) Bind a provider-neutral request/output contract and actual provider/model capability. (2) Create versioned prompts and representative/adversarial cases. (3) Add retrieval only when a measured need justifies it. (4) Validate structured results semantically. (5) Keep deterministic authorization and domain transitions outside model discretion. (6) Make tool effects idempotent or explicitly reconcile uncertainty. (7) Evaluate output, grounding, access boundaries, latency and cost separately. (8) Integrate actual UI/consumer states and a safe prompt/model rollback.

**Artifacts.** Prompt/operation versions; typed adapters; tool/rights contracts; corpus/parser/chunker/index/ACL references when relevant; state/recovery graph if needed; `EvaluationPlan` and cases; traces without secrets; consumer code; fallback and adoption/rollback instructions. Structured output can still be wrong; schema compliance is not factuality or business correctness. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

**Acceptance and failures.** Test irrelevant inputs, refusal/empty/unknown, prompt injection in source material, wrong tenant/actor, revoked/cached sources, late workers, hallucinated tool arguments, timeouts after effects, interrupted/resumed/duplicate runs and quality regressions. Retrieval precision/recall, answer attribution, useful task completion, human judgment and operational cost remain separate measurements. Use task-specific cases and calibrate automated scoring where human assessment matters. [Evaluation practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

**Cost and choice.** Use ordinary code/SDKs for deterministic work and native orchestration for sufficient coordination. LangChain is an option for useful agent/integration abstractions; LangGraph for justified durable state, explicit graph control and interruptions; LlamaIndex for justified document ingestion/retrieval. These are not compulsory together. LlamaIndex caching/dedup does not establish current ACL or correct answers. A LangGraph checkpoint does not guarantee one remote effect: external idempotency and unknown-outcome reconciliation still apply. Use a persistent backend if restart survival is required. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance), [LlamaIndex ingestion](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/).

## C05. PREDICTION — forecast business outcomes honestly

**Activation and inputs.** Use for classification, regression, rankings, time series or risk estimates when there are lawful data and a meaningful target. Specify the business decision, costs of errors, target/units/horizon, prediction-time information, label maturity, sample/selection coverage, groups/time, intended serving environment and budget. A justified finding that data are insufficient is a valid result; an invented accuracy score is not.

**Recipe.** (1) Write `PredictionContract` and availability cutoffs. (2) Freeze versioned dataset, group/time splits and leakage checks. (3) Fit preprocessing only on training data. (4) Establish an honest baseline. (5) Compare suitable candidates within a tuning budget. (6) Evaluate once on protected holdout after selection, including subgroup errors and uncertainty. (7) Package model, preprocessing and schema together. (8) Prove inference parity, monitoring triggers, fallback and compatible rollback.

**Artifacts.** Target/data/split/feature manifests; executable train/eval code; baseline/candidate reports; environment/dependency pins; final holdout report; model/signature and preprocessing; uncertainty/OOD limits; serving interface; operational and rollback runbook. XGBoost, LightGBM, linear/tree/neural models and forecasting methods are candidates, not promised winners. Select by measured fitness, data, maintainability and resources. [XGBoost tuning](https://xgboost.readthedocs.io/en/stable/tutorials/param_tuning.html).

**Acceptance and failures.** Deliberately introduce a future feature and duplicate group across splits; the process must reveal them. Check train-only fit, time/group separation, immature labels, missing units/categories, stale versions and inference parity. TimeSeriesSplit addresses chronology with its own assumptions, including equal spacing for comparable durations; it does not solve campaign/family overlap. Probabilistic calibration and discrimination need distinct inspection; Brier alone is not pure calibration. [Leakage](https://scikit-learn.org/stable/common_pitfalls.html), [time splits](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html), [calibration](https://scikit-learn.org/stable/modules/calibration.html).

**Cost and choice.** Limit experiments, training time, memory and feature computation; compare the cost of a useful decision, not just model size. Preserve missing/zero/category semantics between training and serving. A versioned model bundle can suffice initially; MLflow registry is an option when versions/lineage/aliases justify it, not deployment proof. [LightGBM semantics](https://lightgbm.readthedocs.io/en/stable/Advanced-Topics.html), [MLflow](https://mlflow.org/docs/latest/ml/model-registry/).

**CPA example.** Before-launch CPA must name acquisition, currency, attribution window and prediction horizon. Campaign context, audience, objective, bidding/budget, placement, season and auction can influence the outcome; an image alone is not an exact CPA oracle. Excluding zero-conversion campaigns changes the population, and `cost/acquisitions` is not a finite ordinary CPA when acquisitions are zero. Post-launch clicks/spend/conversions cannot become pre-launch features. These are modeling requirements to inspect on actual data, not findings about a particular account.

A useful initial output may be conditional ranking, a risk/range or abstention outside supported contexts. Protect temporal and creative-family/campaign holdouts; inspect uncertainty and segment errors. A predictive association is not proof that the creative causes a CPA reduction. Causal claims need explicit assumptions, identification and suitable evidence; no library removes confounding by its presence. No campaign spend or human experiment follows from this proposal. [DoWhy primary paper](https://arxiv.org/abs/2011.04216).

## C06. ADAPTATION — improve an open model when justified

**Activation and inputs.** Use when measured prompt/retrieval/baseline limitations justify training and there are suitable data, licenses, evaluation cases, serving requirements and resources. Changing facts may be better served by retrieval; fine-tuning is not automatically a truth store. Establish the base/tokenizer revision, data rights, exact task, independent holdout, device/backend, memory/time/storage, privacy and budget.

**Recipe.** (1) Compare the non-training baseline. (2) Audit labels, contamination, deduplication and chat/template formatting. (3) Choose a compatible backend/model and bounded resource preflight. (4) Pin training data, configuration, code and environment. (5) Run only authorized training with checkpoints and stop limits. (6) Compare candidate and baseline on protected cases. (7) Validate adapter, optional merge/quantization and the actual serving export separately. (8) Adopt or reject with exact evidence and rollback.

**Artifacts.** `TrainingRecipe`; dataset/split hashes; base/tokenizer/license and adapter target/rank/config; prompt/chat template; precision/quantization; hyperparameters/seeds; checkpoint/recovery records; actual metrics/resource/cost; `ModelBundle` with load/signature and lineage `base→adapter→merged→quantized→serving`. Seeds and pins improve reproducibility but do not promise identical bytes across all hardware.

**Acceptance and failures.** Test wrong base/tokenizer/template, contaminated holdout, missing data rights, budget/OOM/interruption/resume, regressions, relevant privacy/memorization concerns and incompatible export. A passed adapter evaluation does not certify changed merged/quantized weights. LoRA reduces trained parameter count; quantization reduces representation memory but does not make every model fit any Mac. [PEFT LoRA](https://huggingface.co/docs/peft/developer_guides/lora), [quantization](https://huggingface.co/docs/peft/developer_guides/quantization).

**Cost and choice.** For an actual compatible Apple-silicon Mac, MLX/MLX-LM is a local candidate; it supports low-rank/full fine-tuning and supported quantized models. Transformers/PEFT is another candidate when its architecture, backend and serving requirements fit. Do not assume a CUDA quantization recipe works on Metal/CPU. Check the actual device/model first; batch, sequence length, selected layers and checkpointing have memory/speed/quality tradeoffs. A documented benchmark on somebody else's device is not this Mac's proof. Hosted GPU, model downloads, publishing and new spending need their own actual authority. No training or hardware probe was done for this proposal. [MLX](https://ml-explore.github.io/mlx/build/html/index.html), [MLX-LM](https://github.com/ml-explore/mlx-lm), [LoRA guide](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md).

**Safe model admission.** Specify approved formats/loaders and trusted provenance before loading a model or adapter. Pickle/joblib-based persistence can execute code when loading untrusted artifacts; a familiar filename or hash is not a trust decision. Remote custom model code stays disabled unless separately reviewed and explicitly admitted. Validate manifests/paths and bound file size, allocation, memory and execution in the supported isolation boundary. Include hostile serialized artifacts, path traversal and excessive-allocation cases without running unreviewed code on the owner's host. Format checks do not prove model quality or a complete sandbox. [scikit-learn persistence](https://scikit-learn.org/stable/model_persistence.html), [Transformers model loading](https://huggingface.co/docs/transformers/en/models).

## C07. MEDIA — produce consistent materials at useful scale

**Activation and inputs.** Use for substantial or repeated idea/text/media/asset production. Establish the full brief, purpose, channel, audience/locales, approved references and editable masters, identity boundaries, item/variant matrix, formats, consumer/runtime, rights, quality gate and budget. A simple reversible text edit should remain simple.

**Recipe.** (1) Read real references and extract composition, scale, mechanism, behavior and functional depth. (2) Plan the complete item set and source/derivative relationships. (3) Bind actual generation/design/edit/export/import operations separately. (4) Prove one representative slice on the actual medium. (5) Run bounded production with cached unchanged steps and inexpensive candidates only where quality remains sufficient. (6) Review craft, functional requirements and identity separately. (7) Integrate into the actual consumer. (8) Deliver editable masters, usable exports, full item accounting and continuation instructions.

| Material | Necessary production handoff and proof |
|---|---|
| Ideas, copy and multilingual content | Claim/source/locale rules, editorial structure, variant purpose, factual and linguistic review; a different label is not a meaningful concept |
| Raster, vector, UI and presentations/documents | Composition, typography/layout, semantic structure and native editable source as required; raster concept does not silently become vector/layered/native output; actual render and interaction where claimed |
| 3D models, materials and game assets | Editable master and rights, scale/axes, topology/UV/material/LOD/collision/rig/animation requirements when applicable, exact export/import and actual engine/device inspection; a rendered view is not a validated runtime asset |
| Voice, music, sound and haptics | Voice/rights/identity, stems or editable sources as required, loudness/channel/loop/trigger specifications, actual listening and device playback; audio and haptic effects require their own implementation |
| Video, animation and compositing | Shot/timeline/editable sources, identity/motion continuity, sound/subtitles/aspect/runtime/export requirements, full playback and consumer proof; a keyframe does not prove the sequence |

These are conditional medium contracts, not an instruction to add sound, animation or 3D to every task. Product art direction and final integration stay with the existing App/Game/Chat owners. Optional specialist advice does not redesign an accepted identity.

**Artifacts.** `BatchPlan`/`ItemManifest`; accepted representative proof; actual provider/operation/parameters and receipts; item statuses including rejected/missing/uncertain; master/variant/derivative hashes; editable files and exports; actual-medium QA; delivery/import report and unresolved gates. Missing generation, export or delivery capability remains a gap; it cannot be hidden by a quality score.

**Acceptance and failures.** Check every required item, not only a sample; test duplicate/out-of-order/missing IDs, partial output, malformed files, stale masters/caches, cancellation around dispatch, cost caps, timeout after provider success and failed quality. Retry only known safe failed items; reconcile unknown paid jobs. Validate actual playback/render/import/use. Keep source availability, media craft, integration, runtime/device proof, independent review and owner acceptance separate.

**Cost and choice.** Measure cost per accepted useful unit including rejected variants, retries, generation, editing, export/import and QA. Compare latency and craft as well as price. Use deterministic editing/design/3D/audio tools when they fit the medium; choose generation where it helps. Current OpenAI Batch offers asynchronous discounted processing for supported operations with a completion window, ID-based reconciliation and partial-result accounting. Verify endpoint/model terms at use; do not extend them to every audio/video vendor. Cancellation is not proof that no in-flight work was charged. [Batch API](https://developers.openai.com/api/docs/guides/batch).

## C08. EVALUATION — establish actual usefulness and readiness

**Activation and inputs.** Use for material AI/data/model/media adoption, system self-updates and prototype-to-product work. A narrow low-impact repair needs proportionate checks. Start with original requirements/references, baseline/candidate, source/build/data/model pins, current product constraints, critical failure modes, acceptance thresholds and required target. Thresholds come from the decision and evidence, not copied tutorial numbers.

**Recipe.** (1) Trace the complete brief to observable acceptance. (2) Identify deterministic, statistical, perceptual, platform and business claims separately. (3) Freeze representative normal/edge/adversarial cases and protect test independence. (4) Run meaningful negative controls and compare baseline/candidate. (5) Inspect raw artifacts, not just summaries. (6) Exercise one integrated actual user journey including failure/recovery. (7) Obtain the distinct independent/device/human/owner evidence actually required. (8) Report pass/fail/unknown, adoption/rollback conditions and remaining work.

**Artifacts.** `EvaluationPlan`; case/split/rubric versions; exact run and observer/reviewer; metrics, error slices and raw evidence references; coverage of all must requirements; cost/latency/craft conclusions; unresolved gates; reproducible launch/recovery and cold handoff. Evaluator-written tests do not automatically establish independence; the critical claim needs a suitably competent different reviewer where independence is required.

**Acceptance and failures.** A synthetic fixture proves its boundary, not provider operation or real-user value. A schema PASS is not a natural conversation, good design, causal effect, deployment or successful payment. Keep old-state adoption and rollback tests when evolving existing tools; preserve historical accepted evidence with its original bytes. Critical access, false-success or missing required capability failures cannot disappear in an average score. Maintain verified case evidence rather than fictional human work experience.

**Productionization and cost.** Audit the actual prototype for fake data/buttons/jobs, manual steps, hidden secrets, access/state gaps and missing dependencies. Prove a nontechnical user can submit authorized input, understand progress/result/limits, recover/retry/cancel correctly and use/export the result. Establish real auth, bounded queues/cost, observability, persistence/backup, outage fallback, support, deploy/health readback and rollback where required. Existing build/release/operations owners implement those changes. This proposal contains no deployment evidence and does not turn a notebook, mock-provider test or panel button into a production service.

## C09. Teams, integration and practical activation

The universal entry should recover context, identify the current product owner and activate only the required competence profiles within existing sources and the 12 host roles. A small extraction repair may use one executor and focused review. A predictive-media product may need product/domain, data, AI/ML, creative/UX, backend/client, privacy/cost and independent QA competence; those work packages do not require new installed skills or a permanently fixed team. No mandatory new role or framework is proposed. A justified later extraction follows the real-task benefit, baseline-preservation and revised-composition approval gate in C00. Real subagents require supported host execution; unavailable delegation must be reported honestly.

Codex, Cursor and Claude Code are normal development aids when actually available, with different native instructions, tools, state and permission rules. Preserve those settings; hand off a scoped source-bound task instead of copying credentials or assuming equal approval semantics. A documented feature or executable on PATH does not prove login, entitlement or a completed operation. The delivered product's agent workflow is a different runtime from its developer's coding assistant. [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Codex platform](https://developers.openai.com/blog/codex-as-a-platform), [Cursor Agent](https://cursor.com/help/ai-features/agent), [Cursor rules](https://cursor.com/docs/rules), [Cursor cloud agents](https://cursor.com/docs/cloud-agent), [Claude Code configuration](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more).

Use one writer per shared source/state/account and explicit producer/consumer contracts. Parallelize independent owned work; keep dependent edits, approvals, measurements and shared mutable resources ordered. Reviews return evidence and findings to one integrator. The existing agent/constructor can receive newly justified competencies while preserving persona, visual identity, settings, permissions, accepted behavior and deferred tasks. No update grants itself permission to rewrite every project.

Examples after approved implementation: “Collect authorized reviews and show recurring problems” activates DATA→ANALYSIS→EVALUATION under the product owner; “Estimate creative performance before launch” activates DATA→PREDICTION with the CPA limits; “Build a support assistant” activates the existing Chat owner with LLM and conditional retrieval; “Produce a consistent asset set” activates the existing art/product owner with MEDIA; “Improve the local model” activates ADAPTATION only after a measured gap and resource decision. The user should not have to memorize profile or skill names.

The local panel may expose only supported, source-backed jobs and controllers: linked accepted result, work packages, data/model/media versions, actual runs, receipts, next actions and gaps. It must distinguish a proposed job, delivered dispatch and actual execution. It must not suggest all Codex chats, arbitrary training jobs or cloud services are controlled unless actual discovery, access and a working controller prove that scope.
