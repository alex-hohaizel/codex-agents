## 0. 升级到6.1并打开本地工作台

以下命令说明支持的流程。只有在保留性检查后，才可应用针对目标范围获准的准确候选版本；准备好的来源并不表示应替换正在使用的安装或服务。

1. 选择准确且经过验证的发行 commit。保留当前33项技能的来源、图标文件/绑定/颜色/类别、本地修改及归属证明。保存项目原有需求、已接受的标识/角色、决策、权限、待办任务和结果不明的外部操作。安装不会迁移产品。
2. 在 `kit/` 中阅读便携更新工具的帮助，再审计准确的候选版本。应用前检查全部33条记录、冲突和视觉标识保留情况。计划和备份应保存在技能发现目录之外。

```bash
python3 portable/update_skill_suite.py --help
python3 portable/update_skill_suite.py audit --kit . --plan /absolute/agent-system-plan.json
python3 portable/update_skill_suite.py apply --plan /absolute/agent-system-plan.json
python3 portable/update_skill_suite.py verify --kit . --journal /actual/apply/journal.json
```

3. 只能用 apply 实际返回的路径替换日志占位路径。未知差异必须核对，不要强制覆盖。分别验证实际发现/来源加载和一项范围明确的任务。现有图标及不相关技能保持不变。
4. 在仓库根目录单独审计 Codex 环境配置：`python3 scripts/install_host_profile.py audit --plan /absolute/host-plan.json`。使用 `apply --plan /absolute/host-plan.json --journal /absolute/host-journal.json` 应用，再用 `verify --journal /absolute/host-journal.json` 验证。受管理的区块会保留现有全局指令；十二种受限角色保留其模型和外部影响限制。实际环境是否加载该配置需要单独检查。
5. 通过支持的技能管理器，从选定 commit 的 `optional-skills/atelier-orchestrator` 安装可选的 `atelier-orchestrator`。它独立于33项核心技能更新工具；存在来源不代表已安装或执行成功。现有维护技能也仍为单独的可选组件。

Atelier Orchestrator 1.2.0 是可选的统一入口：描述一次所需结果，它会选择直接执行、现有专家、项目智能体、领域负责人、组件协调或 Foundry。简单请求保持简单。工作沿用同一份需求说明和现有授权。项目智能体创建、验证并被运行环境发现后，协调器会建议通过该智能体继续工作；再次向协调器提问时，也会保留这一关联。创建智能体与原始产品任务分别验收；智能体安装包不能代表所需产品已经完成。

改进或重写协调器本身、技能、构建器、技能家族或现有智能体的请求，会进入维护流程：读取实际来源和设置，检查影响与差异，保留身份和本地修改，保存更改前副本，并验证实际保存的结果。路径预览和可选的路由检查器不能证明专业适用性、真实用户授权、执行成功或质量。现有技能仍可直接调用。

Agent Atelier 0.5.0是独立本地应用程序/服务器的来源候选版本，通过自身启动器打开。技能不是后台进程，应用程序也不是技能列表中的条目。版本独立管理。原始SVG、PNG绑定和品牌颜色保持不变。核心6.1.0增加兼容方法，不会重置产品或自动在项目中采用新规则。请阅读[6.1更新与回退说明](../../releases/migrations/6.1.0.md)。通过status/doctor核对实际运行版本；现有实例可保持旧版本，直到经过验证的替换完成。

6. 从来源构建本地服务时，使用已固定的 lockfile，以及 Node.js 24.22.2 或受支持的更新运行时。在 `apps/agent-atelier/` 中执行以下命令。首次安装依赖需要网络访问，但不意味着启用新的付费服务。

```bash
npm ci --ignore-scripts
npm run build
node launcher/atelier.mjs start
node launcher/atelier.mjs status
node launcher/atelier.mjs doctor
node launcher/atelier.mjs stop
```

7. 在 Mac 上，构建完成后可双击 `apps/agent-atelier/launcher/Agent Atelier.command` 启动。启动器打开回环地址，复用自身已有的运行实例，不会启用登录自启动。选择并预览一个明确的项目根目录，再进行绑定。绑定只是只读发现项目，不代表产品已采用新流程，也不授权所有未来任务。演示模式使用虚构数据，不执行命令。

在工作台中发现可用的 Codex 工作，并查看所示历史覆盖范围。项目与工作根据实际原生历史和来源记录分组，也包含可访问的、直接在 Codex 中开始的工作；这并不扫描个人主目录，也不授予接管其他写入进程的权限。连接准确的项目文件夹后，才能查看上下文并继续工作。工作地图区分已收到的回复、来源中记录的结果和已验收的结果。目标及已有验收记录保留各自来源；建议不等于批准，提及技能不等于执行，规划中的智能体也不等于已安装。通过统一入口描述下一项结果，检查建议路径，然后准备并启动范围明确的任务。现有对话需要通过受支持的方式在非活动状态下移交；受保护的原生状态修改通过经过审查的控制器进行，而不是任意写入文件。

原生历史不是桌面应用中空项目的注册目录；没有可用历史的项目需要明确连接。对于已知的可选协调器或仓库维护技能，在技能目录中选择**检查此技能更新**，核对准确来源更改、保留检查、冲突及更改前副本计划，然后只应用已就绪且经过审查的更新。验证实际日志，并单独刷新运行环境发现。回退会恢复准确的托管更改前副本，并拒绝覆盖之后未知的更改。这些可选来源操作不会更新33项基础技能或迁移产品。

可以通过专用的只读历史访问路径，在项目总览中查看现有的 Codex 原生聊天。如果隔离执行器无法在自身环境中恢复某个空闲聊天已保存的上下文，就不能继续执行该聊天。此时，请根据已核查的来源准备一个范围明确的新项目任务，或在能够恢复其上下文的 Codex 原生环境中继续现有聊天。能够读取聊天元数据或历史，并不代表已经具备可用于执行的上下文。执行隔离保持不变；不会迁移原生数据库。

8. 准备包含准确范围、输入、验收和限制的任务，再通过支持的 Codex 适配器启动。来源、制作质量、集成、设备、独立审查和所有者验收是不同状态。只有得到环境的实际结果后，才能确认取消。现有聊天需要准确的标识/cwd，以及空闲状态下的移交；服务的持有锁无法限制另一个独立桌面客户端写入。重试前先核对结果不明的外部操作。 任务准备时，服务会记录管辖该任务的确切 AGENTS 来源、它们的优先顺序或已确认的缺失情况，以及 Codex 自身的指令加载设置。服务会核对这些记录是否与实际加载的指令来源一致，并在调用模型前再次检查。如果这些输入发生变化，或旧任务缺少此类记录，必须重新准备任务；任务历史和产品原生文件会予以保留。
9. 现有 Foundry 会话使用 `suite-update-plan`，以及已审查的 `refresh --accept-suite-update` 记录，其中包含准确的来源状态和目标摘要。App state/1 无需因 toolkit 更新而迁移格式。Chat 集成证据需要当前契约对象的固定引用，以及真实的新观察；不能事后为旧证据补填引用。Game 使用受支持的5→6工作流程升级，同时保留 runtime2/model4/handoff1。生成的智能体需要来源到目标的比较及无隐藏历史的继续执行；任何项目都不会被重置。
10. 服务备份/恢复只涉及服务自己的状态：预览并校验准确备份、核对工作、保留已撤销的权限；它不恢复产品数据库或外部影响。技能回滚使用更新工具实际生成的日志；环境配置回滚使用自己的日志，并拒绝后续差异。WORK 的实际安装/控制仍推迟处理。恢复方式和受支持的限制请参阅[详细迁移说明](../../releases/migrations/6.1.0.md)及[服务指南](../../apps/agent-atelier/README.md)。

## 0.1. 候选版本增加了什么及何时使用

上下文来自项目原生的需求、决策、标识和checkpoint。直接技能可使用便携助手编译明确投影；面板单独编译自己的JavaScript任务包。可选的`atelier.context-bindings/1`声明核对来源hash、项目标识、预期ID、必须需求和字面摘录。缺失或变更的必要来源会阻止依赖它的准备工作。没有声明的项目仍保留原有流程，并显示覆盖尚未验证。两条流程都不会自动保存每个字，也不提供全局embedding索引。RAG是为已证明的知识需求按需使用的检索，不是当前任务状态的权威。

只在现有负责人之下激活所需的DATA、ANALYSIS、LLM、PREDICTION、ADAPTATION、MEDIA或EVALUATION职责。没有七项新增安装技能、常驻worker或强制框架。十三种可选产物类型描述适用的数据、模型、运行、评估及批次记录。只读助手核对声明结构、本地绑定、泄漏/重试边界及核算，不会采集数据、训练模型、认证质量或启动提供方任务。请从仓库根目录先查看实际助手的帮助：

```bash
python3 -B standards/context_capsule.py --help
python3 -B standards/ai_production.py --help
```

新生成的6.1智能体包包含15项公共运行资源及七个本地参考链接。现有6.0包保留其准确的12项资源合同，5.x包保留八项；它们不会被追溯认证为6.1。更新现有智能体时应比较来源与目标，保留领域规则、标识、设置及未知修改，再验证无聊天历史的恢复和一项限定范围的原始任务。仅安装工具包不代表项目已采用。

面板显示可读需求、当前决策、延期工作及来源检查。“来源中的状态”保留记录原文，不会覆盖较新的当前决策。大型对话按独立且有界的turn/item页面读取，明确显示继续读取和未完整覆盖。加载与读取失败具有明确状态和恢复流程。已安装、被运行环境发现、已连接、已执行及所有者已验收是不同事实。详细[组件手册](../evolution/2026-11-10/IMPLEMENTED-COMPONENTS.en.md)与[真实反馈案例](../evolution/2026-11-10/REVIEW-STUDY.en.md)说明来源、触发方式、使用者与限制。


设计修订版的工作流程：普通项目默认打开已记录工作的地图，展示真实工作/结果、证据及下一步操作。选择一项工作后才打开对应检查面板；初始状态为关闭。“来源文档 / 比较更改”保留完整技术工作区、原始来源、diff及现有操作。原生历史按需读取，并显示覆盖范围。只有匹配的活动运行时job才能证明工作正在执行；任务中过时的dispatched状态不能证明。易懂的配置名称及全部七种语言保留，UI初始默认为乌克兰语，已保存的语言偏好优先。所有者接受了展示的revision6视觉基础：“Так, цю основу приймаю”。这仅验收该视觉基础；完整A26案例、全部29项案例、后续数据/助手逻辑及安装仍分别判断。旧渲染或CI不能认证变更后的字节；必须在准确修订版上检查全部11个视图、41条命令和48项API操作是否保留。

可选的`current_checkpoint`视图仅来自一个明确绑定、必需且通过字节核验、角色为`checkpoint`的来源。它显示来源中的`phase`、`completed`、`in_progress`和`next`，连同hash及`status: declared`；不会覆盖原生phase，也不证明已执行或已验收。输入缺失、歧义、变更或不受支持时，返回`null`及可见缺口，而不猜测当前阶段。派生视图缺口不会新增全局阻断；已有必需来源错误仍按原规则生效。记录的结果要结合证据理解；文件库存数量不等于已交付结果数量。


这次真实设计失败也改变了共享UI生产规则。创建或评审人机界面时，要证明目标用户能识别目标、真实工作/结果、需要关注的问题及有用的下一步；随后选择记录 → 阅读易懂的证据/结果 → 在正确范围内执行操作。应将参考图的工作机制转化为当前任务，复制代码面板、地图或外壳并不充分。规则与UI配置已复制到现有33个核心包和可选编排器。已加载指令不是质量证书或自动保证；仍须检查真实界面及代表性流程。


兼容更新预览不等于安装。若未变更的已知前版本被报为未知，应对照规范前版本记录核验准确发布字节与文件模式；不要强制覆盖，也不要改hash来掩盖差异。可选编排器经审查的1.1.0 → 1.2.0路线使用准确的40文件前版本基线。未安装的维护技能保持未安装，除非明确要求安装。限定的优先更新仅在相关不变量验证完毕后准入；这不等于验收全部能力或项目。

## 1. 这套系统能为你提供什么

用日常语言描述你想得到的结果。系统会帮助你把它转化为具体任务，调动相关专业能力，把决策与需求保存在一起，并根据约定的目标检查结果。

例如，“帮我降低这个后端的数据库负载”可以转化为对查询、事务边界、缓存、性能测量及经过测试的修改进行有针对性的调查。“为这类用户创建一个移动应用”则需要更广的流程：研究、产品选择、设计、架构、实现、质量检查、发布准备及运营。小修复应当保持为小修复。完整产品应当保留全部需求，包括安排在第一个可运行版本之后实现的部分。

**技能**是一组可复用的工作指令、参考资料，有时还包括脚本。**代理**将某个角色和这些指令应用于任务。**总监**协调一个产品家族。现有家族无法覆盖某项工作时，**构建器**会设计专用代理或一组可复用技能。它们通过 ChatGPT 或 Codex，以及该环境实际提供的工具来工作。安装指令并不会创建运行中的服务器、购买服务、授予仓库权限，或启动永久运行的后台进程。

其价值在于有组织的工作流程：共享简报、明确需求、相关专家、保留的决策、可核验的交接，以及恢复工作的方式。本仓库不宣称经过测量的优越性，不保证收入、应用商店审核通过或自动具备生产就绪状态。

### 想了解确切命令的用户可使用 Terminal

便携式更新器需要 Python 3.9 或更高版本，仅使用标准库。请从仓库根目录执行以下命令。audit 读取分发包和安装位置，并写入建议计划。apply 执行计划中的安装修改并记录日志。

```bash
python3 kit/portable/update_skill_suite.py --help
python3 kit/portable/update_skill_suite.py audit --kit kit --plan ../agent-system-plan.json
python3 kit/portable/update_skill_suite.py apply --plan ../agent-system-plan.json
```

读取 `apply` 的结果。将其确切 `journal` 路径复制到验证命令中：

```bash
python3 kit/portable/update_skill_suite.py verify --kit kit --journal /absolute/path/from-apply/journal.json
```

上方最后的路径是占位符。请替换它，不要原样执行。更新器默认目标为 `~/.agents/skills`，并检查旧根目录 `~/.codex/skills`。如果环境使用其他受支持的个人根目录，请始终显式提供 `--destination` 和 `--legacy-root` 参数。先查看 `audit --help`。添加 `--project-root /absolute/path/to/product` 可审计相关产品本地副本。更新器不会自动删除遮蔽个人技能的项目副本。

文件安装成功意味着：33 个来源在目标版本上通过验证，没有未解决的阻塞/失败/重复项，并且使用实际 apply 日志验证得到 `canonical_core_verified=true` 和 `visual_preservation_verified=true`。没有该日志的哈希检查，无法证明保留了现有图标。遇到冲突请停止并保留本地工作；不要通过强制替换让报告看起来正常。

```text
单独列明不可用的来源。
```

随后给出一项小型真实任务，提供已知输入和验收标准。例如，让应用总监根据现有需求审查单个界面的错误状态，或让构建器概述一个专用代理的职责。这样可以检查行为，但并不认证所有产品能力。请将文件安装、宿主加载、实际使用和产品验收作为不同结果保存。

## 7. 在真实任务中使用系统

### 范围较窄的工程任务

```text
调查这个 endpoint 中的重复数据库查询。保持其 API 和业务行为。
先阅读代码和现有测量结果。指出缺少哪些证据，提出最小有用调查，
并在当前分支中实施有依据的修复。验证正确性，
在环境允许时展示修改前后的测量结果。
```

这不需要新公司、新产品、新品牌或完整市场研究。如果希望将此流程长期保留为代理，构建器可以设计可复用调查代理；一次性任务则使用现有相关工具和指令。系统不应仅仅因为任务有技术性就制造一个新代理。

### 完整应用

```text
BRIEF：我想为 [用户群体] 创建解决 [问题] 的应用。
目标平台为 [平台]，预算为 [预算]，我的角色为 [角色]。
澄清未知事项，调查真实替代方案并准备完整选项。
在整个计划中持续展示我的全部需求，包括设计、语言、客服和变现。
不要在不说明的情况下替我选择概念。
```

团队应研究重要问题、比较方案，并在大规模开发前识别发布或账号障碍。选定概念后，保留选定设计参考及全部约定需求。早期可运行版本是计划中的一个检查点，不是放弃其余部分的许可。

### 移动游戏

```text
BRIEF：为 [用户/体验] 开发不同的移动游戏概念。
涵盖操作与反馈、相互作用的系统、敌人、有意义的成长、美术方向、
变现和可行的 Android/iOS 制作路线。展示可比较的视觉概念。
在资源和可玩实现中保留选定形象。定义真正的设备检查。
```

概念图无法证明动画、触摸操作、性能或存档恢复。游戏工作流程应当在制作全部资源之前，将选定的视觉承诺连接到可编辑源资源和具有代表性的可玩切片。

## 8. 在同一个项目中结合 Work 和 Codex

当所需来源、研究工具、设计工具及连接服务可用时，Work 很有用。当源代码工作副本、运行时、构建工具和设备或本地集成可用时，Codex 很有用。只要具备正确能力，两种模式都可以完成更多工作。请根据实际访问能力和证据选择，而不是把所有思考任务分配给一个模式、所有代码任务分配给另一个模式。

为产品建立唯一身份。`My Product [WORK]` 和 `My Product [CODEX]` 这样的名称便于导航，但不能证明两个项目包含相同产品。请记录仓库、分支、子目录、项目标识及检查点来源。新聊天应继续留在已有项目内。

### 保存简洁的共享上下文

使用仓库中的项目上下文模板，或产品已有的等效文件。至少记录：项目标识；仓库和分支；当前完整 commit SHA；任务标识；当前阶段；工作和产品语言；工具套件版本及安装凭证；已接受决策；完整需求来源；设计参考来源；授权范围；当前检查点；未解决影响或决策；下一步动作。不要在此记录中包含凭据。

### Work → 本地 Codex，逐步操作

1. 向 Work 提出：“在 Codex 中继续这个阶段。为现有项目准备交接。”
2. Work 应确定确切的下一个交付物及其验收所需证据，并保存或提供相关需求、决策、来源和检查点。
3. 如果存在获得授权的共享渠道，Work 可以保存交接并验证保存的修订。保存一个文件不能证明另一个 Codex 会话已经启动。
4. 打开现有本地工作副本。如果没有本地副本，请将已确认的仓库与分支克隆到选定文件夹。访问私有仓库时在本地认证。
5. 更新工作副本前先检查：

```bash
git remote get-url origin
git branch --show-current
git rev-parse HEAD
git status --short
```

6. 如果工作树干净且确实需要更新该分支，使用 `git pull --ff-only origin <confirmed-branch>`，并替换为真实分支名。确认得到的完整 SHA。如果存在本地修改或分叉历史，请保留它们，并在开始依赖这些内容的工作前解决差异。
7. 在 Codex 项目界面打开确切文件夹。已有产品应使用现有项目；必要时通过可用项目编辑界面添加文件夹。
8. 粘贴下方填好的交接文本。Codex 先确认仓库身份、修订、本地修改、权限和检查点，再执行限定范围内的动作。
9. 保存它的结果报告、commit/build 引用及测试证据，用于回传交接。

### Codex → Work，逐步操作

1. 让 Codex 为同一现有项目准备结果交接或新任务交接。
2. 包含实际修改的文件、完整 SHA 或产物修订、已执行检查、限制、待决事项和下一步动作。说明修改处于本地、已提交或已发布状态。
3. 如果已授权把约定修改发布到指定分支，则仅发布该范围并核验远端修订。否则，通过可用渠道提供受控产物。Work 并不能自动读取本地 Mac 路径。
4. 打开现有 Work 项目，连接相关仓库或附加确切产物，然后粘贴交接。
5. Work 在审查或继续之前读取实际来源并检查输入修订，并应明确报告无法访问的文件。
6. 单独记录验收，不要与交付及执行混为一谈。报告某个 build 已存在，并不等同于产品验收。

### 可复制的交接文本

使用前替换所有方括号字段：

```text
在 [Work/Codex] 中继续现有项目 [项目标识/名称]。
工作语言：[语言/代码]。产品语言：[语言]。
仓库：[URL]。分支/子目录：[分支/路径]。
输入修订：[完整 SHA 或确切产物修订]。
任务标识和阶段：[标识/阶段]。
检查点：[确切且可访问的来源]。
需求和已接受决策：[确切来源]。
设计参考与形象：[确切来源，如适用]。
预期交付物和验收：[具体结果/检查]。
授权范围：[允许修改或发布的内容]。
已完成工作和证据：[事实与引用]。
待决事项、阻塞或不确定外部影响：[详情/无]。
下一步动作：[一项具体动作]。

先核验项目身份、修订、可用工具及权限。保留每项已接受的需求和决策。
不要重新初始化产品。区分交接已准备、交付已验证、接收、执行、结果和验收。
继续实际可行且已获得授权的工作。
```

## 9. 聊天中断后恢复

在同一项目中新开聊天，让它恢复最后一个已验证检查点。如果尚无法访问，请提供检查点来源。继续前，应核对任务、需求、源修订、当前文件及实际外部结果。

```text
根据最后一个已验证检查点及实际来源，恢复这个已有任务。
保留需求、决策、权限、已完成结果及不确定外部影响。
核验当前修订及下一步动作的负责人。
重复部署、付款、消息或其他外部动作前，检查上一次尝试是否已经真正完成。
继续当前可执行且已获授权的工作，并记录新的检查点。
```

聊天卡住并不能证明它最后的操作失败。恢复时必须先检查真实结果，再重试可能造成重复的动作。

## 10. 更新版本时不丢失已有项目

### 先阅读版本记录

每个发布版本都应说明修改内容、受影响用户、前提条件、安装步骤、项目采用步骤、验证、已知限制和回滚方式。常规流程发生变化时，通用指南也必须更新。不要仅依赖一个版本号。

6.0.0版本保留33个稳定名称和图标标识，同时强化证据、来源依赖、JSON 输入检查和状态写入。它增加可独立使用的制作/上下文配置，以及明确的参考一致性要求。历史协议和项目原有运行时 schema 版本仍相互独立；不做迁移就将旧 schema 改为套件版本号，会破坏兼容性。

### 已有 Agent Systems 2.3 / Game 4.3 项目

1. 保存当前项目检查点、已接受需求、决策、设计母版、源修订、工具套件版本及已知外部影响。
2. 记录每项技能或项目代理实际从哪里加载。清点个人和项目本地副本；不要假定修改一个全局目录就会修改所有项目。
3. 使用前文适用的 Work 或 Codex 路线安装目标套件。保存来源版本和安装凭证。
4. 重新打开现有项目，在下一项依赖动作之前执行只读兼容性审查。
5. 让总监或构建器比较当前项目状态与新工作流程。仅在确有需要时明确提出原生状态刷新或工作流程升级。保留产品行为、已接受选择及未知影响。
6. 预览确切修改。如果需要状态迁移，使用受支持工具及其真实 `--help`；将预览绑定到源状态哈希、目标套件哈希和授权来源。应用已审查且获得授权的计划，不要编造历史批准。
7. 重新检查每项受影响需求及当前阶段的验收标准。执行一项小型真实延续任务，并保存证据。
8. 在产品检查点中记录已采用的工具套件版本。保留迁移记录，让下一次聊天能够解释这一过渡。

Game6.0.0 提供已审查的工作流程升级路线，用于 4.2.0/4.3.0/5.0.0 项目，同时保持运行时 schema 2.0.0。其使用取决于真实项目状态及工具支持的输入。App 和 ChatBot 项目同样需要审查各自状态和兼容性；不能仅因为套件共享一个版本，就把它们送入游戏迁移流程。

### 以前通过构建器创建的代理

更新构建器不会重写它以前创建的代理。这些代理可能包含项目专属规则、工具、知识和视觉形象。应在各自项目内进行清点，比较旧来源、本地修改及建议新来源。保留原始所有权和安装证据。如果缺少这些证据，请准备明确的采用对比及计划；不要伪造旧凭证。针对代理的实际职责执行回归案例，并单独记录已采用版本。

可复用仓库不包含私有产品代理源包。单个项目的更新应保存在该项目受控来源和迁移记录中，而不是安装到所有人的全局技能里。

### 保留视觉形象

现有 Codex 图标、图标路径、颜色和图标字节必须在常规更新中保留。新版本并不意味着要重新设计已有技能或产品。尚无形象的新技能可以获得适当的系统或项目风格。Work 可能自行管理服务头像；应将其宿主显示行为与便携 Codex 形象分开。保留已选产品及游戏设计的原始文件，而不仅是一段文字描述。

### 谨慎回滚

对于 Codex 套件安装，使用确切安装日志：

```bash
python3 kit/portable/update_skill_suite.py rollback --journal /absolute/path/from-apply/journal.json
```

回滚会检查备份并保护之后发生的未知修改。它只撤销该日志所代表的技能安装，不会撤销产品数据迁移、部署、消息、购买或其他外部动作。Work 恢复应使用受支持的技能管理路线及保存的旧来源。产品状态回滚需要单独经过审查的恢复程序。

## 11. 确保未来更新完整

每次工具套件变更时，都应更新本仓库中的规范来源、受影响需求、分发包内容、版本记录、迁移步骤、验证证据，以及所需指南和翻译修改。保留以前的版本记录。从已检查的来源重新构建分发包和完整性元数据；不要发布从过期宿主缓存组装的压缩包。

根据当前 `--help` 和维护文档运行仓库检查与打包命令。发布后确认远端 commit。“已保存到本地”“已提交”“已发布”“已安装”“已加载”和“已被项目采用”是不同状态。如果权限阻止发布，请保留已完成工作并报告未同步的确切修订。

仓库规则只有在未来代理于具备所需权限的环境中读取它时才会生效。它不是监听所有其他聊天和电脑的全局监听器。未来开始技能管理任务时，应先连接本仓库并读取其 `AGENTS.md`、需求及最新版本记录。单独的定时同步服务需要自己的真实运行时和授权；套件不会默默创建这项服务。

## 12. 故障排查

| 现象 | 接下来检查什么 |
| --- | --- |
| Work 无法读取仓库 | 核验 GitHub 账号、该确切私有仓库的授权及所选连接；让它读取一个已知文件。 |
| 本地克隆要求认证 | 使用平台凭据流程配置本地 Git 授权。Work 的连接与之独立。 |
| 保存后没有显示技能 | 刷新或重新打开 Skills 页面，然后使用新的项目聊天检查真实来源发现情况。 |
| 同一技能显示两个副本 | 审计个人和项目根目录中的稳定名称。保留本地修改并解决确切重复来源；不要删除无关技能。 |
| 更新器报告变更偏差或冲突 | 保存本地 diff，并将列出的文件与选定来源比较。使用经过审查的合并协调计划。 |
| 文件检查通过，但代理行为仍像以前 | 核验宿主实际加载的来源，然后运行一项小任务；仅有文件完整性还不够。 |
| Work 看不到 Mac 上修改的代码 | 发布获授权范围或附加确切产物；仅有本地路径不会赋予访问能力。 |
| 新聊天丢失了决策 | 继续前恢复检查点及完整需求来源，并更新保存的上下文。 |
| 第一个可运行版本省略了约定设计或语言 | 核对需求台账；在计划中保留这些需求，并列明其实现和验收步骤。 |
| 无法部署、提交商店或进行设备检查 | 说明确切缺少的账号、工具、设备或访问能力，并继续独立准备工作。不要声称无法执行的检查已经通过。 |
| 代理声称启动了另一个会话 | 要求提供已核验的启动/接收引用。交接文件只能证明实际观测到的状态。 |
| 想要持续运行的任务 | 确认存在真实调度器、执行器、凭据、存活检查及恢复路线。仅安装技能不会提供这些能力。 |

宿主界面及各账号可用能力可能变化。安装或连接服务时，请查阅实际界面及最新官方文档。本指南于 2026 年 11 月 7 日核对的产品行为参考如下：
