# Agent System — Work + Codex 完整指南

[English](../en/GUIDE.md) · [Українська](../uk/GUIDE.md) · [Deutsch](../de/GUIDE.md) · [Italiano](../it/GUIDE.md) · [Español](../es/GUIDE.md) · [Français](../fr/GUIDE.md) · [中文](../zh-CN/GUIDE.md)

**指南基线：** Agent System 5.0.0，2026 年 11 月 7 日。**可复用套件：** 33 项技能。本指南涵盖首次安装、日常使用、Work 与 Codex 之间的项目协作，以及现有项目的升级。仓库文档和分发包的修订可以独立于底层技能版本发生变化；升级前请查阅版本记录。

## 1. 这套系统能为你提供什么

用日常语言描述你想得到的结果。系统会帮助你把它转化为具体任务，调动相关专业能力，把决策与需求保存在一起，并根据约定的目标检查结果。

例如，“帮我降低这个后端的数据库负载”可以转化为对查询、事务边界、缓存、性能测量及经过测试的修改进行有针对性的调查。“为这类用户创建一个移动应用”则需要更广的流程：研究、产品选择、设计、架构、实现、质量检查、发布准备及运营。小修复应当保持为小修复。完整产品应当保留全部需求，包括安排在第一个可运行版本之后实现的部分。

**技能**是一组可复用的工作指令、参考资料，有时还包括脚本。**代理**将某个角色和这些指令应用于任务。**总监**协调一个产品家族。现有家族无法覆盖某项工作时，**构建器**会设计专用代理或一组可复用技能。它们通过 ChatGPT 或 Codex，以及该环境实际提供的工具来工作。安装指令并不会创建运行中的服务器、购买服务、授予仓库权限，或启动永久运行的后台进程。

其价值在于有组织的工作流程：共享简报、明确需求、相关专家、保留的决策、可核验的交接，以及恢复工作的方式。本仓库不宣称经过测量的优越性，不保证收入、应用商店审核通过或自动具备生产就绪状态。

## 2. 选择从哪里开始

| 你的情况 | 从这里开始 | 有用的首次请求 |
| --- | --- | --- |
| 希望获得适合某项重复工作的专用代理 | `agent-foundry` | “创建一个调查我们 Go 服务性能问题的代理。先明确它的职责、证据和访问权限。” |
| 希望获得一项可复用技能或协调工作的技能家族 | `design-specialist-skills` | “为我们的事件驱动集成设计可复用的审查流程，包括失败恢复。” |
| 希望开发应用或继续开发现有产品 | `app-atelier-director` | “从检查点继续这个应用。保留已接受的需求，并确定下一个有价值的交付物。” |
| 希望创建聊天机器人、客服机器人或对话伙伴 | `chatbot-atelier-director` | “为这些用户和渠道设计一个机器人，包括语言、记忆、动作和运营成本。” |
| 希望创建移动游戏或继续现有游戏 | `gamedev-director` | “围绕这种体验开发游戏概念，包含有意义的操作、成长机制及可行的制作路线。” |

你不必记住全部 33 个名称。产品项目使用总监，新专用工作流程使用构建器。也可以在宿主环境的技能选择器中显式选择技能。Work 中通常使用 `@skill-name`；Codex 中使用 `$skill-name`。不同宿主版本提供的选择器和显示名称可能不同。需要确认时，请让宿主说明实际加载的确切来源。

## 3. 安装前选择语言

通过上方链接打开翻译指南。没有提供偏好时，默认为英语。各语言指南覆盖相同步骤；代码、稳定技能名称、文件名和协议标识符保持不变，以确保命令一致有效。

在安装或项目开始时，粘贴以下内容并替换语言：

```text
我的工作语言是简体中文（zh-CN）。请使用它进行解释、提问、进度更新、
交接指导和面向我的报告。保持稳定技能名称、命令语法及技术标识符不变。
将此偏好记录在项目保存的上下文及交接中。
另行询问我们正在构建的产品使用什么语言。
```

文档语言、对话语言和产品语言是不同选择。例如，你可以阅读乌克兰语指南、使用乌克兰语与代理协作，并发布支持英语和德语的应用。相关时，请分别说明这三种选择。将偏好记录在项目上下文模板或已有等效文件中，并在每次交接时携带。只更改浏览器页面语言，不会设定另一个聊天的语言。

## 4. 准备账号和来源

1. 登录计划使用这套工具的 ChatGPT 或 Codex 账号。检查该账号或工作区是否确实提供所需模式和技能管理工具。
2. 打开 `https://github.com/alex-hohaizel/codex-agents`。仓库可见性目前由所有者控制。私有仓库需要获得授权的 GitHub 账号，以及能访问该确切仓库的连接。
3. 在 Work 中，通过可用的 Plugins/连接界面连接或选择 GitHub。如果仅允许访问所选仓库，请加入 `alex-hohaizel/codex-agents`。让 Work 读取 `README.md`，并报告它实际能访问的分支与修订。
4. 在本地 Codex 中，如果计划克隆私有仓库，请授权本地 Git 访问。Work 的 GitHub 连接并不能证明你电脑上的 Terminal 可以认证。
5. 安装时使用命名发布版本或确切 commit，并保存该标识。读取持续变化且未固定的 `main` 分支，可能混合不同版本。
6. 通过 GitHub 的 **Code → Download ZIP** 下载选定仓库修订，或使用 Git 克隆。安装前先解压下载的压缩包。应能看到 `kit/manifest.json`、`kit/portable/` 和 `kit/skills/`。
7. 不要把下载内容、计划或备份放入技能发现目录。普通文件夹，例如 Downloads，或专门的技能管理工作区都适合。

使用本地 Git 时，请选择已确认的分支，并使用一个不包含其他工作的全新目标位置：

```bash
git clone --branch main https://github.com/alex-hohaizel/codex-agents.git "codex-agents"
cd "codex-agents"
git rev-parse HEAD
git status --short
```

克隆 `main` 是获取源代码工作副本的便捷方式。应用更新前，确认其 SHA 与选定版本匹配。不要把访问令牌粘贴到聊天、项目文件、shell 命令或交接文档中。请使用平台的账号连接或凭据流程。

## 5. 从新账号开始在 Work 中安装

### 这条路线的作用

它通过宿主支持的技能管理流程，将 33 项可复用技能保存为个人技能。仅仅连接 GitHub、上传 ZIP、阅读本指南，或把仓库文件添加为项目来源，并不能证明某项技能已经安装或加载。

### 逐步操作

1. 打开 Work，创建或打开技能管理项目。你在这里管理工具套件，而不是之后要构建的产品。
2. 使用第 3 节的文本块选择语言。
3. 提供对选定仓库修订的访问。如果 Work 无法读取私有 GitHub 文件，请连接该仓库，或通过可用文件界面附加已整理的分发包。
4. 调用可用的 Skill Creator/技能管理能力。让它先检查分发包，再修改已安装记录。
5. 粘贴下方安装请求。该请求授权限定范围内的安装和必要验证。
6. 让 Work 根据稳定名称检查现有技能清单。新账号应创建缺失条目；已有账号应更新对应的个人条目，并保留无关技能。
7. 保存安装报告。报告必须列明全部 33 项技能的名称、版本、源修订、结果及未解决的失败。
8. 如果 Skills 页面显示过期，请刷新或重新打开。在目标产品项目中新开聊天，执行下方加载和实际使用检查。

```text
从 alex-hohaizel/codex-agents 所选且已验证的修订中，
使用 kit/manifest.json 和 kit/skills/ 安装 33 项可复用个人技能。
我的工作语言是简体中文（zh-CN）。

使用宿主支持的个人技能管理流程。根据稳定名称检查现有记录，验证分发包，
保留无关技能和现有视觉形象，并安装或更新匹配条目。
保留备份和准确来源信息。不要将项目专用代理安装到全局。
不要修改产品数据、生产服务或账号设置。

报告每个稳定名称、版本、源修订及 create/update/noop/failure 状态。
区分技能已保存、宿主已发现，以及实际用于任务这几个状态。
如果没有技能管理能力，说明确切缺失的能力；
不要把已上传或只读副本描述成已安装。
```

Work 支持的管理流程可能逐项保存技能。部分完成时，应列明已完成及待完成条目，以便安全继续，而不是重新开始。在云文件系统中执行便携式 Codex 更新器，并不能证明你的 Work 个人技能目录已更新。

## 6. 在 Codex 中安装或更新

### 最简单的路线：让 Codex 执行受控安装

1. 按前文所述下载或克隆选定修订。
2. 在已有技能管理工作区打开 Codex。首次安装可打开仓库副本或其他普通管理文件夹，无需创建新的产品仓库。
3. 向 Codex 提供仓库副本的确切路径。Mac 上，在 Finder 选中文件夹，按 **Option + Command + C** 复制完整路径。
4. 设置首选语言后，粘贴下方文本。
5. 检查最终安装报告，并保留其日志和备份位置。
6. 在真实产品项目中新开聊天，检查加载和实际使用情况。

```text
从这份 alex-hohaizel/codex-agents 工作副本中已验证的 kit/ 目录，
安装 33 项基础个人技能。使用所选发布修订。
我的工作语言是简体中文（zh-CN）。

这授权对本套件执行本地 audit → apply → verify、生成确切计划和备份。
读取 kit/manifest.json 及更新器的 --help。验证分发包完整性。
审计个人目录和所有已知项目副本。将计划与备份保存在技能发现根目录之外。
只应用已准备好的确切计划。保留未知本地修改，报告冲突文件；
不要绕过变更偏差检查。

保留现有 icon_small、icon_large、brand_color、图标路径及图标字节，
包括历史 ./assets/ 引用。使用 apply 返回的确切日志进行验证。
报告 canonical_core_verified、visual_preservation_verified、
updated/noop 数量、阻塞、失败及重复项。

不要修改产品、生产环境、插件或环境配置。
随后单独检查宿主是否发现两个构建器和 App、ChatBot、Game 总监。
不要将已安装文件当作实际用于任务的证明。
```

### 想了解确切命令的用户可使用 Terminal

便携式更新器需要 Python 3.9 或更高版本，仅使用标准库。请从仓库根目录执行以下命令。audit 读取分发包和安装位置，并写入建议计划。apply 执行计划中的安装修改并记录日志。

```bash
python3 kit/portable/update_skill_suite.py --help
python3 kit/portable/update_skill_suite.py audit --kit kit --plan ../agent-system-plan.json
python3 kit/portable/update_skill_suite.py apply --plan ../agent-system-plan.json
```

读取 `apply` 的结果。将其确切 `journal` 路径复制到验证命令中：

```bash
python3 kit/portable/update_skill_suite.py verify --kit kit --journal /absolute/path/from-apply/journal.json
```

上方最后的路径是占位符。请替换它，不要原样执行。更新器默认目标为 `~/.agents/skills`，并检查旧根目录 `~/.codex/skills`。如果环境使用其他受支持的个人根目录，请始终显式提供 `--destination` 和 `--legacy-root` 参数。先查看 `audit --help`。添加 `--project-root /absolute/path/to/product` 可审计相关产品本地副本。更新器不会自动删除遮蔽个人技能的项目副本。

文件安装成功意味着：33 个来源在目标版本上通过验证，没有未解决的阻塞/失败/重复项，并且使用实际 apply 日志验证得到 `canonical_core_verified=true` 和 `visual_preservation_verified=true`。没有该日志的哈希检查，无法证明保留了现有图标。遇到冲突请停止并保留本地工作；不要通过强制替换让报告看起来正常。

### 将加载检查与安装检查分开

在新的产品聊天中向 Codex 或 Work 提出：

```text
在修改任何内容之前，指出 agent-foundry、design-specialist-skills
和三个产品总监实际加载的确切来源与版本。
确认你实际读取了哪些自适应、研究、视觉形象及 Work↔Codex 指令。
单独列明不可用的来源。
```

随后给出一项小型真实任务，提供已知输入和验收标准。例如，让应用总监根据现有需求审查单个界面的错误状态，或让构建器概述一个专用代理的职责。这样可以检查行为，但并不认证所有产品能力。请将文件安装、宿主加载、实际使用和产品验收作为不同结果保存。

## 7. 在真实任务中使用系统

### 范围较窄的工程任务

```text
调查这个 endpoint 中的重复数据库查询。保持其 API 和业务行为。
先阅读代码和现有测量结果。指出缺少哪些证据，提出最小有用调查，
并在当前分支中实施有依据的修复。验证正确性，
在环境允许时展示修改前后的测量结果。
```

这不需要新公司、新产品、新品牌或完整市场研究。如果希望将此流程长期保留为代理，构建器可以设计可复用调查代理；一次性任务则使用现有相关工具和指令。系统不应仅仅因为任务有技术性就制造一个新代理。

### 完整应用

```text
BRIEF：我想为 [用户群体] 创建解决 [问题] 的应用。
目标平台为 [平台]，预算为 [预算]，我的角色为 [角色]。
澄清未知事项，调查真实替代方案并准备完整选项。
在整个计划中持续展示我的全部需求，包括设计、语言、客服和变现。
不要在不说明的情况下替我选择概念。
```

团队应研究重要问题、比较方案，并在大规模开发前识别发布或账号障碍。选定概念后，保留选定设计参考及全部约定需求。早期可运行版本是计划中的一个检查点，不是放弃其余部分的许可。

### 移动游戏

```text
BRIEF：为 [用户/体验] 开发不同的移动游戏概念。
涵盖操作与反馈、相互作用的系统、敌人、有意义的成长、美术方向、
变现和可行的 Android/iOS 制作路线。展示可比较的视觉概念。
在资源和可玩实现中保留选定形象。定义真正的设备检查。
```

概念图无法证明动画、触摸操作、性能或存档恢复。游戏工作流程应当在制作全部资源之前，将选定的视觉承诺连接到可编辑源资源和具有代表性的可玩切片。

## 8. 在同一个项目中结合 Work 和 Codex

当所需来源、研究工具、设计工具及连接服务可用时，Work 很有用。当源代码工作副本、运行时、构建工具和设备或本地集成可用时，Codex 很有用。只要具备正确能力，两种模式都可以完成更多工作。请根据实际访问能力和证据选择，而不是把所有思考任务分配给一个模式、所有代码任务分配给另一个模式。

为产品建立唯一身份。`My Product [WORK]` 和 `My Product [CODEX]` 这样的名称便于导航，但不能证明两个项目包含相同产品。请记录仓库、分支、子目录、项目标识及检查点来源。新聊天应继续留在已有项目内。

### 保存简洁的共享上下文

使用仓库中的项目上下文模板，或产品已有的等效文件。至少记录：项目标识；仓库和分支；当前完整 commit SHA；任务标识；当前阶段；工作和产品语言；工具套件版本及安装凭证；已接受决策；完整需求来源；设计参考来源；授权范围；当前检查点；未解决影响或决策；下一步动作。不要在此记录中包含凭据。

### Work → 本地 Codex，逐步操作

1. 向 Work 提出：“在 Codex 中继续这个阶段。为现有项目准备交接。”
2. Work 应确定确切的下一个交付物及其验收所需证据，并保存或提供相关需求、决策、来源和检查点。
3. 如果存在获得授权的共享渠道，Work 可以保存交接并验证保存的修订。保存一个文件不能证明另一个 Codex 会话已经启动。
4. 打开现有本地工作副本。如果没有本地副本，请将已确认的仓库与分支克隆到选定文件夹。访问私有仓库时在本地认证。
5. 更新工作副本前先检查：

```bash
git remote get-url origin
git branch --show-current
git rev-parse HEAD
git status --short
```

6. 如果工作树干净且确实需要更新该分支，使用 `git pull --ff-only origin <confirmed-branch>`，并替换为真实分支名。确认得到的完整 SHA。如果存在本地修改或分叉历史，请保留它们，并在开始依赖这些内容的工作前解决差异。
7. 在 Codex 项目界面打开确切文件夹。已有产品应使用现有项目；必要时通过可用项目编辑界面添加文件夹。
8. 粘贴下方填好的交接文本。Codex 先确认仓库身份、修订、本地修改、权限和检查点，再执行限定范围内的动作。
9. 保存它的结果报告、commit/build 引用及测试证据，用于回传交接。

### Codex → Work，逐步操作

1. 让 Codex 为同一现有项目准备结果交接或新任务交接。
2. 包含实际修改的文件、完整 SHA 或产物修订、已执行检查、限制、待决事项和下一步动作。说明修改处于本地、已提交或已发布状态。
3. 如果已授权把约定修改发布到指定分支，则仅发布该范围并核验远端修订。否则，通过可用渠道提供受控产物。Work 并不能自动读取本地 Mac 路径。
4. 打开现有 Work 项目，连接相关仓库或附加确切产物，然后粘贴交接。
5. Work 在审查或继续之前读取实际来源并检查输入修订，并应明确报告无法访问的文件。
6. 单独记录验收，不要与交付及执行混为一谈。报告某个 build 已存在，并不等同于产品验收。

### 可复制的交接文本

使用前替换所有方括号字段：

```text
在 [Work/Codex] 中继续现有项目 [项目标识/名称]。
工作语言：[语言/代码]。产品语言：[语言]。
仓库：[URL]。分支/子目录：[分支/路径]。
输入修订：[完整 SHA 或确切产物修订]。
任务标识和阶段：[标识/阶段]。
检查点：[确切且可访问的来源]。
需求和已接受决策：[确切来源]。
设计参考与形象：[确切来源，如适用]。
预期交付物和验收：[具体结果/检查]。
授权范围：[允许修改或发布的内容]。
已完成工作和证据：[事实与引用]。
待决事项、阻塞或不确定外部影响：[详情/无]。
下一步动作：[一项具体动作]。

先核验项目身份、修订、可用工具及权限。保留每项已接受的需求和决策。
不要重新初始化产品。区分交接已准备、交付已验证、接收、执行、结果和验收。
继续实际可行且已获得授权的工作。
```

## 9. 聊天中断后恢复

在同一项目中新开聊天，让它恢复最后一个已验证检查点。如果尚无法访问，请提供检查点来源。继续前，应核对任务、需求、源修订、当前文件及实际外部结果。

```text
根据最后一个已验证检查点及实际来源，恢复这个已有任务。
保留需求、决策、权限、已完成结果及不确定外部影响。
核验当前修订及下一步动作的负责人。
重复部署、付款、消息或其他外部动作前，检查上一次尝试是否已经真正完成。
继续当前可执行且已获授权的工作，并记录新的检查点。
```

聊天卡住并不能证明它最后的操作失败。恢复时必须先检查真实结果，再重试可能造成重复的动作。

## 10. 更新版本时不丢失已有项目

### 先阅读版本记录

每个发布版本都应说明修改内容、受影响用户、前提条件、安装步骤、项目采用步骤、验证、已知限制和回滚方式。常规流程发生变化时，通用指南也必须更新。不要仅依赖一个版本号。

共享版本 5.0.0 将构建器与三个产品家族统一到一个可见套件版本，新增共同的自适应工作方式、领域研究与综合、视觉形象处理，以及共享的 Work↔Codex 路线。历史协议和运行时 schema 版本仍然独立。没有真实迁移就把旧 schema 改名为“5.0.0”，会破坏兼容性，而不是使项目现代化。

### 已有 Agent Systems 2.3 / Game 4.3 项目

1. 保存当前项目检查点、已接受需求、决策、设计母版、源修订、工具套件版本及已知外部影响。
2. 记录每项技能或项目代理实际从哪里加载。清点个人和项目本地副本；不要假定修改一个全局目录就会修改所有项目。
3. 使用前文适用的 Work 或 Codex 路线安装目标套件。保存来源版本和安装凭证。
4. 重新打开现有项目，在下一项依赖动作之前执行只读兼容性审查。
5. 让总监或构建器比较当前项目状态与新工作流程。仅在确有需要时明确提出原生状态刷新或工作流程升级。保留产品行为、已接受选择及未知影响。
6. 预览确切修改。如果需要状态迁移，使用受支持工具及其真实 `--help`；将预览绑定到源状态哈希、目标套件哈希和授权来源。应用已审查且获得授权的计划，不要编造历史批准。
7. 重新检查每项受影响需求及当前阶段的验收标准。执行一项小型真实延续任务，并保存证据。
8. 在产品检查点中记录已采用的工具套件版本。保留迁移记录，让下一次聊天能够解释这一过渡。

Game 5.0.0 提供已审查的工作流程升级路线，用于 4.2.0/4.3.0 项目，同时保持运行时 schema 2.0.0。其使用取决于真实项目状态及工具支持的输入。App 和 ChatBot 项目同样需要审查各自状态和兼容性；不能仅因为套件共享一个版本，就把它们送入游戏迁移流程。

### 以前通过构建器创建的代理

更新构建器不会重写它以前创建的代理。这些代理可能包含项目专属规则、工具、知识和视觉形象。应在各自项目内进行清点，比较旧来源、本地修改及建议新来源。保留原始所有权和安装证据。如果缺少这些证据，请准备明确的采用对比及计划；不要伪造旧凭证。针对代理的实际职责执行回归案例，并单独记录已采用版本。

可复用仓库不包含私有产品代理源包。单个项目的更新应保存在该项目受控来源和迁移记录中，而不是安装到所有人的全局技能里。

### 保留视觉形象

现有 Codex 图标、图标路径、颜色和图标字节必须在常规更新中保留。新版本并不意味着要重新设计已有技能或产品。尚无形象的新技能可以获得适当的系统或项目风格。Work 可能自行管理服务头像；应将其宿主显示行为与便携 Codex 形象分开。保留已选产品及游戏设计的原始文件，而不仅是一段文字描述。

### 谨慎回滚

对于 Codex 套件安装，使用确切安装日志：

```bash
python3 kit/portable/update_skill_suite.py rollback --journal /absolute/path/from-apply/journal.json
```

回滚会检查备份并保护之后发生的未知修改。它只撤销该日志所代表的技能安装，不会撤销产品数据迁移、部署、消息、购买或其他外部动作。Work 恢复应使用受支持的技能管理路线及保存的旧来源。产品状态回滚需要单独经过审查的恢复程序。

## 11. 确保未来更新完整

每次工具套件变更时，都应更新本仓库中的规范来源、受影响需求、分发包内容、版本记录、迁移步骤、验证证据，以及所需指南和翻译修改。保留以前的版本记录。从已检查的来源重新构建分发包和完整性元数据；不要发布从过期宿主缓存组装的压缩包。

根据当前 `--help` 和维护文档运行仓库检查与打包命令。发布后确认远端 commit。“已保存到本地”“已提交”“已发布”“已安装”“已加载”和“已被项目采用”是不同状态。如果权限阻止发布，请保留已完成工作并报告未同步的确切修订。

仓库规则只有在未来代理于具备所需权限的环境中读取它时才会生效。它不是监听所有其他聊天和电脑的全局监听器。未来开始技能管理任务时，应先连接本仓库并读取其 `AGENTS.md`、需求及最新版本记录。单独的定时同步服务需要自己的真实运行时和授权；套件不会默默创建这项服务。

## 12. 故障排查

| 现象 | 接下来检查什么 |
| --- | --- |
| Work 无法读取仓库 | 核验 GitHub 账号、该确切私有仓库的授权及所选连接；让它读取一个已知文件。 |
| 本地克隆要求认证 | 使用平台凭据流程配置本地 Git 授权。Work 的连接与之独立。 |
| 保存后没有显示技能 | 刷新或重新打开 Skills 页面，然后使用新的项目聊天检查真实来源发现情况。 |
| 同一技能显示两个副本 | 审计个人和项目根目录中的稳定名称。保留本地修改并解决确切重复来源；不要删除无关技能。 |
| 更新器报告变更偏差或冲突 | 保存本地 diff，并将列出的文件与选定来源比较。使用经过审查的合并协调计划。 |
| 文件检查通过，但代理行为仍像以前 | 核验宿主实际加载的来源，然后运行一项小任务；仅有文件完整性还不够。 |
| Work 看不到 Mac 上修改的代码 | 发布获授权范围或附加确切产物；仅有本地路径不会赋予访问能力。 |
| 新聊天丢失了决策 | 继续前恢复检查点及完整需求来源，并更新保存的上下文。 |
| 第一个可运行版本省略了约定设计或语言 | 核对需求台账；在计划中保留这些需求，并列明其实现和验收步骤。 |
| 无法部署、提交商店或进行设备检查 | 说明确切缺少的账号、工具、设备或访问能力，并继续独立准备工作。不要声称无法执行的检查已经通过。 |
| 代理声称启动了另一个会话 | 要求提供已核验的启动/接收引用。交接文件只能证明实际观测到的状态。 |
| 想要持续运行的任务 | 确认存在真实调度器、执行器、凭据、存活检查及恢复路线。仅安装技能不会提供这些能力。 |

## 13. 官方文档及证据范围

宿主界面及各账号可用能力可能变化。安装或连接服务时，请查阅实际界面及最新官方文档。本指南于 2026 年 11 月 7 日核对的产品行为参考如下：

- [Build skills — ChatGPT Learn](https://learn.chatgpt.com/docs/build-skills)：可复用技能结构、本地发现与安装概念。
- [Plugins — ChatGPT Learn](https://learn.chatgpt.com/docs/plugins)：插件目录、连接与分发概念。

本仓库分发可复用套件及其受控安装流程。公共市场插件、商业许可证、永久托管运行时、第三方付费工具和凭据属于单独交付内容，除非某个发布版本明确提供并验证了它们。营销概念展示工作流程和预期用途；最终宣传主张必须与已验证能力和证据相符。
