# Commercial product maintenance contract

The complete owner instruction is [the versioned source contract](COMMERCIAL_PRODUCT_CONTRACT.uk.md).
Its original SHA-256, verbatim clauses, implementation destinations and C01–C28
are retained in [the requirement registry](commercial/requirements.json).
This file is the English entry for product maintenance. The owner authorized
an implemented and verified local commercial release candidate. It does not
authorize payment processing, public listings, publication of legal terms,
contract acceptance, new spending or repository visibility changes.

## One canonical product

Use [the product descriptor](../commercial/product.json) and the existing
[component record](../releases/current.json) as sources. Versions, core IDs,
license terms, editions, support, checksums, disclosures and channel exports
must come from these sources. The seller's edition and price configuration
is in the offer file. Preserve the original component names and all applicable
working functions, data, icons, settings, host entry points and earlier acquired
rights. The original source packages retain their supported import route.

A buyer obtains a complete local package, its versioned license document and
a trustworthy delivery receipt. Payment and download services do not execute
the local agent logic. An unavailable store never disables acquired local
rights or edits the buyer's projects. Original toolkit resources reused in
generated agents retain their applicable license; do not misrepresent client
ownership of the entire reusable toolkit.

## Changes to an installed product

For each change, identify the affected product/component version and buyer
journey. Preserve unknown drift. Storage, runtime dependencies, host capability
or configuration changes require compatibility rules and a recovery path.
Keep journals and state outside discovery. Preflight and hold a single writer
for a buyer lifecycle action; reconcile interruptions before resending.
Uninstall only files owned by the exact installation, preserving user projects
and later local edits. Rollback must identify preceding runtime and data schema.

Licensing, setup, delivery or updater changes require the affected buyer-path
checks; a typo needs document/link checks. A complete release candidate needs
all C01–C28 observations, with actual artifact identity and source commit.
Readiness records distinguish implementation, bytes, native discovery,
real task, platform execution, signing, owner acceptance and public sale.
An unavailable environment remains unverified with an exact next step.

## Release procedure

Build from a clean identified commit. Validate the actual package, signature,
source inventory, notices, editions, seller-free runtime, docs and exports.
Run normal buyer receipt → staged package → install → discovery → useful
task → update → recovery. Separately preserve an existing installation,
unrelated skills and local changes. Repeat the build to compare exact bytes.
Never use an earlier proof for changed bytes.

Keep issuance keys, private purchase records, credentials, account inventories
and raw customer data outside the repository and releases. Collect only the
information needed for delivery/support. Disclose host/model/API costs,
untested platforms, channel limitations and any external publication blockers.
Update current instructions, localization, manifests, support materials,
release checklist and maintenance guidance with each affected workflow.
