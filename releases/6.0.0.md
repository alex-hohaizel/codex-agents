# Agent System 6.0.0

This major release preserves the 33 stable core skill names and their installed icon identity while strengthening evidence admission, context continuity and professional artifact production. Native format versions and product IDs are independent of the suite number. Existing projects are never reset by installation.

## What changes

- Evidence registration rejects supplied stale subject/proof bindings instead of silently rebinding old observations. Foundry source identity includes the actual operating closure. App/ChatBot/Game retain their existing domain guards.
- ChatBot integrated evidence includes the normative contract digest; code/integration readiness requires the corresponding actual proof. Team writes use a shared lock, atomic persistence and revision conflict checks.
- Critical JSON readers reject duplicate keys/nonfinite values. Game normative toolkit claims match6.0.0; native game-model 4, handoff 1 and runtime 2 formats remain distinct. Mac filesystem fixtures preserve guards while testing the actual filesystem capability.
- Every core bundle carries the same reviewed production/context resources and a deterministic context compiler. The standard tracks defining reference mechanisms, composition, identity, functional depth and actual medium acceptance. Generated6.0 children require 12 common resources; historical 5.0 children are not retroactively certified6.0.
- App platform and participation rules follow the accepted project profile. Explicit preferred language is respected. Known vendor compatibility guards are preserved and expanded; vendor caches are not modified.
- A supported Codex host instruction profile and twelve bounded role profiles provide the same source/quality obligations for direct entry. File installation, actual loading and successful behavior remain separate observations.
- Optional `atelier-orchestrator` 1.0.0 coordinates approved product tasks; it remains separate from the 33-core updater. Agent Atelier 0.1.0 supplies the local workbench, explicit bindings, real Codex jobs, context/evidence, skills management and recovery.

## Compatibility and scope

Read [the migration](migrations/6.0.0.md) before dependent work. A stricter gate may require a new observation or explicit toolkit adoption; old acceptance is not invented. Existing requirements, persona, accepted masters, pending tasks and unknown outcomes remain preserved. Work live audit/update/installation is deferred to a separate owner task; source-bundle availability does not establish Work parity.

The local service uses loopback-only access and the user's existing supported Codex authentication. New charges, production effects and unrelated product migrations are not implied. Existing desktop chat adoption requires exact identity/cwd, an idle handoff and current scope; a local service lease cannot fence an independent desktop writer.

## Verification

Final verified results, source/package hashes, actual Codex/installation observations and limitations are recorded in `governance/RELEASE_6_VERIFICATION.json`. Until that record is finalized, this branch is a release candidate. Synthetic tests are scoped to their fixtures; no universal creative certification or absence of all future regressions is claimed.
