# Adopt repository 1.3.0 / Orchestrator 1.1.0 / Agent Atelier 0.2.0

This compatible feature release adds universal task routing and a source-backed Codex portfolio. The33-core suite remains6.0.0. Native project IDs, formats, requirements, accepted identity, settings, permissions and unfinished work must remain preserved.

## Before

1. Select the exact reviewed repository revision. Read its release record and actual capabilities. Locate the current service, installed optional orchestrator and every affected ownership/source record; do not infer installation from repository presence.
2. Save the optional skill's complete before-copy, source hashes and UI/icon/settings bindings outside discovery roots. Reconcile unknown local modifications before replacement. Preserve original SVG/PNG bytes, icon paths, color, stable selector, invocation policy and dependencies.
3. Reconcile active/paused/unknown service or native jobs. Retain service backup and command receipts. Keep the same service data directory. Backups and projections of this service are not product-database or provider-effect backups.

## Update

1. Update only the optional `atelier-orchestrator` through the supported manager or documented reviewed local update route. Version1.1.0 adds routing/maintenance references and self-contained helper dependencies. The main updater still manages only the33core; reinstalling them for this release is unnecessary.
2. Stop the local service using its launcher. Obtain the verified source without overwriting unknown work. From `apps/agent-atelier/`, use the pinned lockfile: `npm ci --ignore-scripts`, then `npm run build`. Start with `node launcher/atelier.mjs start` and inspect `status`/`doctor`. Do not change account permissions, model defaults or login auto-start as part of this update.
3. Verify the same saved project bindings/history and service data directory. New portfolio/route records are service-owned projections; do not rewrite native product state or initialize an unfamiliar format to make it appear compatible. Existing tasks remain historical records. Prepare a fresh task when changed skill, instruction, source or permission pins make an old capsule stale.
4. In the workbench, discover available Codex work and inspect pagination/coverage, sources and any inaccessible roots. Discovery is read-only candidate metadata. Inspect and explicitly connect the exact folder before preparing work against it. An existing active/unknown native writer remains a conflict; use only a supported idle handoff for continuation.
5. Review the intended result and its source/acceptance status, documented work, project-agent status and proposed next step. A model summary or source declaration is not owner acceptance. Describe an outcome in the universal entry, inspect the proposed route, then prepare and start only the approved bounded task.
6. Requests to create an agent and requests to execute its product retain separate scopes. Existing valid consent follows the same scope without repeated questionnaires. Maintenance requests require actual target/source/settings comparison, a reviewed diff and a before-copy. Protected native-state changes use the exact reviewed controller route; generic model file writes remain restricted.
7. Old `atelier.orchestrator-task/1` projections without routing fields remain readable as `legacy_not_declared`; they do not acquire new ready/executed/accepted status. New fields are additive to that derived record, not a migration of the native project. Instantiate a current projection from actual sources when the new workflow needs it.

For the known optional orchestration/maintenance sources, the panel provides a reviewed preview/apply/verify/rollback path. Inspect exact source/installed-tree hashes, preservation and conflicts before apply; retain the actual private before-copy/journal. Verify the full current tree, then refresh host discovery separately. Rollback requires that verified current hash and refuses newer unknown edits. A pending or outcome-unknown operation must be reconciled before new dependent work. Discovery covers available native history and explicit bindings, not an empty-project desktop registry.

## Verify

1. Check the optional installed source/file set, version, unchanged identity/settings and actual host discovery. A source byte check does not prove runtime behavior or icon display.
2. Run the focused routing/helper checks and relevant service tests. Verify legacy admission, missing capability, uncertain delivery, stale sources, active native writers and reviewed controller preconditions. A route checker does not choose a competent specialist or authenticate consent.
3. Prove a representative outcome through the universal entry without requiring internal skill names. For a complex case, inspect a real integrated final output against the initial brief/reference. Keep source, craft, runtime/device, independent review and owner acceptance distinct.
4. Inspect available native history and the work map. A completed native turn, an observed skill mention, an installed source and a received artifact must retain their different labels. Missing history/access is partial coverage, not an empty successful inventory.
5. Verify all seven UI catalogs and equivalent guide updates. Build/inspect both source bundles and exact remote source/CI after publication. Preserve raw account/project inventories and receipts privately; publish only sanitized reusable evidence.

## Rollback

1. Reconcile unknown effects and stop new dependent dispatch before stopping the service. A source rollback does not cancel native jobs or undo product/provider effects.
2. Restore only the reviewed optional source from its real before-copy after comparing current post-update hashes; later unknown edits/settings are conflicts. Retain the original icon identity and unrelated skills.
3. Use a compatible service binary/state pair or reviewed isolated restore. Older service versions do not understand new portfolio, routing and controller operations; do not issue those operations against them or treat hidden records as deleted. Preserve the existing data directory and actual backup rather than resetting projects.
4. No native product-format rollback or core6.0.0 reinstall is required solely by this release. WORK has its own actual manager/source/readback route and remains deferred; a filesystem journal cannot roll back its account entries.
