# Compatible 6.0.0 to 6.1.0 candidate migration

Target source: repository **1.4.0-rc.2**, suite **6.1.0**, optional Orchestrator **1.2.0**, maintenance **1.1.0**, service **0.3.0**. The complete passport remains in progress. These instructions do not themselves install or adopt the candidate. WORK live work remains deferred.

## Before

1. Select an exact reviewed source commit and read its current status and [release notes](../6.1.0.md). Preserve the actual 6.0.0 source, icons, bindings, colors, role/model settings, unknown local edits and existing installation journals outside discovery roots.
2. Restore native project requirements, accepted originals/identity, decisions, permissions, unfinished/deferred tasks and uncertain external outcomes. A toolkit update is not a product migration. Old proof remains bound to its old inputs.
3. Keep a healthy service baseline active while testing the candidate in a disjoint data directory and on another loopback port. Use a consistent SQLite online copy or supported service backup/restore, rather than copying only a live WAL database file. Never run two writers against one service data directory. Reconcile active or unknown jobs before maintenance.
4. Required unknown or failed affected proofs block adoption. Ordinary previously authorized work does not need another approval merely because a new version exists. New spending, downloads/training, publications or product effects retain their actual task-specific bounds.

## Steps

1. Validate the exact candidate's sources and relevant behavior. Read the portable updater help and audit the 33-core candidate. Keep plans and backups outside skill-discovery roots.

```sh
python3 kit/portable/update_skill_suite.py --help
python3 kit/portable/update_skill_suite.py audit --kit kit --plan /absolute/core-plan.json
```

2. Review every conflict and preserved visual property. Only after the affected candidate is admitted, use the exact plan and the journal returned by the supported updater. Do not fabricate an ownership receipt or force an unknown edit.

```sh
python3 kit/portable/update_skill_suite.py apply --plan /absolute/core-plan.json
python3 kit/portable/update_skill_suite.py verify --kit kit --journal /actual/returned/journal.json
```

3. Audit the host profile separately. Its current/previous managed-block comparison preserves outside text; an unknown edit inside the block requires reconciliation. The twelve role files keep their models/policies.

```sh
python3 scripts/install_host_profile.py audit --plan /absolute/host-plan.json
python3 scripts/install_host_profile.py apply --plan /absolute/host-plan.json --journal /absolute/host-journal.json
python3 scripts/install_host_profile.py verify --journal /absolute/host-journal.json
```

4. Update the two optional sources separately through their supported manager. Do not add them to the 33-core inventory. Preserve original UI metadata/icons and unknown local changes. Source presence and a successful local file replacement do not prove host discovery or task behavior.
5. For an admitted service update, preserve the actual service backup and receipts, build the exact candidate with the lockfile, reconcile jobs/controllers, stop only the owned healthy instance, then start and verify the new build against the same service state. No database-schema migration is required: `agent-atelier.db/1` and API version 1 remain. A changed source checkout does not rebuild an old ignored `dist/client` or restart a cached backend.

```sh
cd apps/agent-atelier
npm ci --ignore-scripts
npm run build
node launcher/atelier.mjs status
node launcher/atelier.mjs doctor
```

6. Open the owned instance through its launcher. Verify actual version, instance, source/build pins, projects, tasks, installed-versus-discovered skills and allowed controls. A plain loopback URL is not an owner login. Refresh supported native history after a cold start when its ephemeral discovery cache is empty.

## Verify

- Run meaningful source, unit, contract, legacy-package and actual-task checks for the changed paths. Check source/format, behavior, craft, runtime/device, independent review and owner acceptance separately.
- Reconcile raw originals with the requirement register independently. A verified declared binding cannot prove completeness or consent. Missing, changed, wrong-project or weakened required declarations must block preparation. Legacy no-manifest projects remain usable and visibly unverified.
- Exercise the real panel's current project, readable requirements, current/deferred context, observed work/agent sources, actual bounded task and recovery. Load additional native item pages rather than inferring complete history from metadata. Preserve empty/unavailable-history warnings.
- Verify source bundles, installed bytes, actual host discovery, running build and remote Git/CI separately. No average score compensates for a lost working function. Retain unknowns and exact next checks.

## Rollback

Use the actual updater journal and its supported rollback command. Compare current bytes to the known post-update bytes before restoring; preserve subsequent unknown edits. Host-profile rollback uses its own journal and does not require a live repository to restore recorded bytes. Service rollback requires a compatible saved source/build and reviewed service state; never replay an uncertain model/provider action. Restoring service records does not restore native products, chat history or reverse external effects.

## Existing projects

Existing native formats, IDs, accepted client sets, owner study restrictions and permissions are retained. Do not reinitialize a project to obtain a new workflow. For each generated agent, compare its actual source/settings with the target, preserve domain rules/persona/identity and local changes, then verify a bounded original task after actual discovery. New 6.1 child bundles have 15 operating resources; historical 6.0 has 12 and 5.x has 8. The new source does not retroactively certify those agents or adopt every private project.

The source-binding file is optional and derived. Add one only when useful and authorized within the project; pin actual sources rather than creating another mutable backlog. AI/data artifacts are instantiated only for applicable work. Training, provider, device and full-product claims still require their corresponding real evidence.
