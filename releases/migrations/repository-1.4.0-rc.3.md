The supported schema has no independent mode readback; setter success does not certify cold execution.

New preparations retain a private control archive and copy only the approved selected manifest to a separate owned `AgentAtelierExecutionInputs-<hash>` namespace. Existing narrow read rules target the exact selected skill subtree; no parent/control read or memory bypass is introduced. Before dispatch/resume verify canonical/archive/execution bytes, complete supplied selection membership, task ID and ownership. Existing TASK bindings reject empty inputs and equal-byte inputs stripped to legacy metadata. Actual old capsules with no new TASK keep their prior contract; no automatic migration or rebind is performed.

A missing/changed/extra execution member requires a new prepare, without silently rebuilding from a source or old proof. Explicit retention can clean only the task-owned derived namespace with its original binding; preserve unknown journals and other tasks. The existing service backup contains STORE JSON records/metadata only. Preserve archive bytes in a separate full filesystem backup before live replacement; store restore retains existing archive files and revokes old dispatch authority, rather than restoring missing execution copies. ## Rollback

Keep the prior source/build and actual service backup. Restore only the owned compatible service through its supported launcher/backup workflow, preserving subsequent unknown edits and reconciling uncertain jobs. API 1 and `agent-atelier.db/1` remain; no database migration is introduced. A service rollback does not reverse product effects or alter native chat/project state. Rejected experimental model outputs need no operational rollback because they were never activated; retain the unchanged owner/human-review route and original base/source files.

The immediate rollback procedure is limited to a failed start before any new 0.3.1 jobs, user edits or effects, verified from actual receipts; preserve all post-attempt data and journals. Old 0.3.0 does not enforce the new `memory_mode`/execution-transport contracts, so the same database schema does not prove compatible behavior or policy. After new tasks exist, do not blindly start old code or overwrite the database with a baseline: first reconcile with the new version’s supported tools, restore/revoke the affected capsules as appropriate and review compatibility independently, while retaining unknown outcomes and later work. Core/Orchestrator global sources are unchanged and are not rollback targets of this service patch.
