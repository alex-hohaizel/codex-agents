# Adopt Agent System 5.0.0 without losing project knowledge

Applies to fresh installations, earlier Agent 2.3.x / Game 4.3.x installations and already verified 5.0.0 installations. The repository edition is 1.0.0. A project's actual source and native contracts decide which steps apply; version labels alone do not establish compatibility.

## Before

1. Identify the actual project and its current repository commit. Save local changes without overwriting unknown work.
2. Restore the last confirmed checkpoint, complete requirements, approved decisions, language, design identity and unfinished work. Copy the continuity templates into the product's own documentation location if the project lacks an equivalent.
3. Record current skill source paths, suite version, project-agent ownership records, icon references and hashes. Keep backup and audit files outside skill discovery roots.
4. Choose and record the exact target `codex-agents` commit. Read its release notes and guide in the selected language.

## Steps

1. **Already verified 5.0.0:** retain the installation; verify the recorded source and move to step 5. This repository edition adds distribution/documentation and does not require replacing unchanged skill bytes.
2. **Fresh or older Codex installation:** from `kit/`, run `python3 portable/update_skill_suite.py --help`, then `python3 portable/update_skill_suite.py audit --kit . --plan ../agent-system-plan.json`. Confirm the manifest lists the expected 33 stable names and 5.0.0 versions. Inspect blockers, duplicates and unknown drift.
3. Apply only the ready exact plan with `python3 portable/update_skill_suite.py apply --plan ../agent-system-plan.json`. Retain the actual journal path returned by the command. Do not add a force option to bypass an unexplained conflict.
4. Run `python3 portable/update_skill_suite.py verify --kit . --journal /actual/path/from-apply/journal.json`. Verify canonical core and visual preservation. In Work, use the supported personal-skill installation/update workflow described in the language guide; repository reading alone is not installation.
5. Open the existing product project and perform a read-only compatibility intake. Compare the saved project state with the newly installed instructions. Preserve project IDs, requirements, decisions and native schema versions. A supported family-specific workflow upgrade may be required before dependent work.
6. For a generated project agent, compare its old and target sources and its local customizations. Preserve its icon and exact ownership evidence. Do not install every project agent globally or fabricate an ownership receipt.
7. Record the selected interaction language and exact toolkit commit in the project's own context file. Transfer the same records if switching between Work and Codex.

## Existing projects

Game projects with supported 4.2.0/4.3.0 workflow state use the family's reviewed workflow-upgrade path and retain the runtime schema `2.0.0`. Read the actual script `--help` and produce the source-state hash, target-suite hash, impact preview and required authority before applying. Other native contracts need their own actual compatibility check; do not substitute a game migration command.

For an agent designed using older constructors, reconcile its requirements and generated contracts before choosing whether to update instructions, implementation or both. A constructor upgrade is not permission to replace the product. Deferred requirements remain in the plan and retain explicit status.

## Verify

1. Record file installation, host discovery, domain smoke and owner acceptance as separate results.
2. In a new session for the same project, ask the selected constructor or director to report its actual source and version. Give one small real task with known input and a concrete acceptance criterion.
3. Confirm the result uses the correct language, preserves requirements and identity, and updates the checkpoint. Test only the domain surfaces affected by the migration.
4. Save the toolkit version/commit, migration result and evidence in the product repository. A successful source hash check alone does not establish project adoption.

## Rollback

1. Stop dependent changes and reconcile any external action whose result is uncertain.
2. For Codex skill files, use `python3 portable/update_skill_suite.py rollback --journal /actual/path/from-apply/journal.json`. Keep the verified backups; do not unpack old archives over active roots.
3. Preserve later unknown edits if rollback reports a conflict. Restore project instructions/state only from the project's own reviewed backup or reversible change.
4. A skill rollback does not undo database migrations, deployments, messages or other external effects. Record the remaining work and resume from the last confirmed checkpoint.
