# Maintain the agent-system repository 1.1.0

Treat https://github.com/alex-hohaizel/codex-agents as the owner's designated release and documentation home. This instruction persists across subsequent skill-management tasks. The owner has authorized ordinary relevant maintenance and publication there; preserve repository visibility and do not add paid services or deploy products without applicable authorization.

1. At the start of each relevant task, read the current repository AGENTS.md, governance/UPDATE_CONTRACT.md, governance/requirements.csv, releases/current.json, and applicable release/migration records using the GitHub connection or an authorized checkout. Prefer confirmed repository state over cached copies. If unavailable, continue independent authorized work, preserve a publication-ready change and mark publication blocked.
2. Keep the actual request scope. Small fixes do not need a new product lifecycle. Publish related source, requirements, constructor references, release notes, package inputs, affected guides and complete translations in the same task. Read repository tool implementations/help before use. Do not claim a release complete until remote read-back succeeds.
3. Distinguish repository revision, toolkit suite version, generated-agent version and native product schema. Declare each affected version and why. Preserve stable skill names and local icons, bindings, colors and class. Never rename a schema merely to match a skill version.
4. Document exact previous-to-next compatibility. Preserve active product requirements, agreed design identity, memory scope, accepted decisions, permissions, task status and unknown external outcomes. Installation and adoption into existing projects are separate. Provide sequential migration, validation and rollback steps for Work and Codex; explicitly state when no native-state change is required.
5. Respect the selected language, persist it in project context, and carry it through handoffs. English is the documentation source; advertised translations cover every step and prompt, retain commands/identifiers, and record the English source hash. Never call a summary a full translation.
6. Produce evidence for source integrity, behavior, archives, translation parity and visual preservation as relevant. File hashes do not prove host discovery, a running session, device tests or product acceptance. Record distinct statuses.
7. Exclude private product data, secrets, chat histories, personal installation receipts and account-specific packages from the reusable core. Publish approved generic sources. Keep original notices and do not choose a commercial license for the owner.
8. Report concise results with repository commit/artifact links, changed versions, tests, migration required and remaining blockers. If a local update succeeded but repository publication did not, state both statuses and retain the diff.

Initial baseline: 33 reusable skills at 5.0.0; this optional maintenance skill is separate from that count. Initial repository documentation revision: 1.0.0. Discover future versions from the repository rather than assuming these numbers remain current.

Read [publication-checklist.md](references/publication-checklist.md) when preparing a release.

For an AI/data, context, design or panel update, restore the exact approved scope and use the existing sufficient owner and methods first. Before adoption compare actual baseline and candidate on a relevant authorized real task, retaining every accepted working function, quality, identity, setting, permission and deferred obligation. Reject any demonstrated regression; missing required evidence stays open and cannot be averaged away. A typed record or different reviewer name is not execution, human consent or independent review. Keep source, package, installation, discovery, runtime and owner acceptance separate.
