# Codex Agent System maintenance

Use the current canonical repository, its [publication checklist](references/publication-checklist.md), and the actual authorized destination. For a narrowly scoped fix, read the relevant source and checks. For a release, read the active branch, current component record, requirements, update contract, and installation and recovery instructions. Use the actual GitHub revision rather than a cached branch pointer.

1. Keep the original scope and record the affected components, accepted behavior, stable identities, and existing local changes. Distinguish the repository edition, core suite, optional skill, role definitions, service and product schema. Version only what changed. Record the exact installed source and recovery instructions.
2. Preserve original project data, decisions, required and deferred work, settings, paths, permissions, icons and colors. Existing generated agents have their own source, settings, project adoption and rollback. Work installation and local Codex installation use different supported workflows.
3. For a material change, compare the affected baseline and candidate on an authorized representative task. Check functional behavior, artifact quality, role/runtime evidence and independence as applicable. Retain old evidence with its exact inputs. Reject a confirmed loss of an accepted function, identity or permission.
4. Verify the package and its build provenance before applying it. Compare the managed local destination with the known predecessor, stage the update, preserve the recovery journal, and verify the actual installed files. Use a fresh Codex session to confirm discovery and a bounded task. A missing optional install is a separate scope; do not infer ownership or overwrite drift.
5. Preserve each advertised guide's meaning, commands and exact references. Keep canonical instructions in English and honor the user's interaction and output language. Keep raw account data, secrets, product records, private chats and installation receipts outside reusable packages.
6. Publish the authorized reviewed sources, requirements, release notes, installation and recovery instructions, guide changes and validated packages to the actual destination. Confirm the source revision remotely. If a write loses its response, reconcile its target before sending again. If publication cannot proceed, preserve the prepared revision and distinguish local verification from remote publication.

Report source integrity, package provenance, installation, fresh discovery, actual task behavior, product adoption and owner acceptance at their actual scopes. The current record identifies the stable release and outstanding gates. This maintenance workflow does not authorize new spending, license or visibility changes, unrelated production actions or unattended updates.
