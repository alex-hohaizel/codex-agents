# Permanent repository contract

This repository, `alex-hohaizel/codex-agents`, is the release and documentation home for the owner's reusable agent system, constructors, skills, requirements and Work/Codex packages. Read this file, `governance/UPDATE_CONTRACT.md`, `governance/requirements.csv`, `releases/current.json`, and the applicable migration before changing or distributing them.

## Completion rule

For every future relevant change, publish the authorized verified change here in the same task. Update source files, release notes, version metadata, requirements traceability, installation instructions, exact translations and packages together as applicable. Never say the update is complete when only a chat, local installation or archive has changed. If repository write access fails, keep the prepared changes and report the exact unpublished scope. Do not invent a successful synchronization.

## Preserve the owner's work

- Keep the canonical 33-skill 5.0.0 baseline and its stable names unless an intentional suite change is declared. Repository documentation revision and skill suite version are separate.
- Preserve existing local icon files, bindings, colors and system/project classes. New items may receive appropriate new graphics; routine updates must not redesign existing items.
- Preserve every accepted requirement, design identity, persona, business rule, decision, permission and unfinished task when adopting new skills into a project. Keep deferred requirements visible.
- Never infer installation, a running subagent, another host session, a device test, a completed deployment or product acceptance from the existence of a file. Record each actual result separately.
- Never publish project secrets, credentials, private chats, product databases or account-specific project packages as part of the reusable core. Generic templates are allowed.
- Keep English as the default guide. Maintain complete, equivalent guides for every advertised language; code, stable names and schema keys remain unchanged. Respect `preferred_language` in project context and all handoffs.

## Every release

1. Discover actual sources, changes, previous version, installation owner and project state. Read current repository requirements before editing.
2. Classify impact and version deliberately. Write an exact source-to-target migration or an explicit reason that no state migration is needed.
3. Include first installation, update, existing generated-agent adoption, Work/Codex handoff and rollback consequences. Record unknown state rather than fabricating history.
4. Run relevant integrity, behavior, translation, icon-preservation and packaging checks. Use actual apply journals for local preservation claims.
5. Update guides in all advertised languages and the change log; preserve step IDs and commands. Regenerate hashes only after source changes are reviewed.
6. Build the distribution from approved files. Verify archives and repository read-back, then report commit, artifacts, tests and remaining limits.

The owner's request authorizes ordinary reversible maintenance and publication here. It does not authorize public visibility changes, commercial license selection, paid services, production deployment or changes to unrelated product repositories. Follow existing task authorization without asking for the same permission twice.

## Reading order for a new session

Read `START_HERE.md`, the guide for the chosen language, `governance/QUALITY_MODEL.md`, and `releases/current.json`. Apply the quality dimensions relevant to the actual task; do not impose unrelated product features or claim a certification. For an active product, also read its native checkpoint, requirements, decisions, toolkit lock and handoff. A repository link alone is not a host installation or cross-session memory channel.

## Bounded execution and recovery

For long artifact or publication tasks, read [the resumable-work contract](governance/RESUMABLE_WORK.md). Persist the confirmed baseline, current stage, input/output digests, completed checks, unresolved outcomes and exact next action outside chat before starting the next expensive phase. Give the owner a short progress update at stage boundaries. Keep tool responses concise; store full inventories and logs in task files.

For the current campaign, read its active README and run `python3 -B marketing/campaign/build_campaign.py`, then `python3 -B marketing/campaign/check_campaign.py`. The compatible resumable runner, where used, must follow the active campaign rather than a deleted draft. Resume skips only stages with matching inputs and verified outputs. Generation, validation, packages, publication, remote read-back and delivery each need actual evidence. If an external write response is lost, reconcile the destination before another write. These controls protect completed work but do not repair or guarantee the host's conversation infrastructure.
