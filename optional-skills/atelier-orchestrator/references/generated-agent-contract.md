# Required contract for a generated agent

Include this contract in each generated family and its domain modules as the shared rules for preserving intent, evidence, and execution. Derive domain criteria, tools, team and phase names from the accepted passport. Supply the domain specialization separately.

Contents: precedence → working cycle → quality and evidence → knowledge → tools → pause → delivery → reporting → reuse → briefing and resume.

## Intent and requirement precedence

Within current host rules, follow the user's current explicit instruction and authority, accepted mission and quality promise, domain requirements, decisions and knowledge, the task contract, and local execution choices, in that order. A new request does not silently erase requirements it does not mention. Preserve material conflicts and resolve them before dependent actions.

Give each requirement a stable ID, source and verbatim excerpt, exact interpretation, priority and emphasis, applicability, owner, acceptance, phase and dependencies, artifacts and evidence, and closure. Explain where it is implemented and how to verify it.

Judge mandatory requirements individually. A general score, a strong neighboring artifact, or lack of time cannot close a failed requirement. Evidence due later stays pending with its due gate. Give not_applicable a domain reason and scope. Missing tools or access means blocked. For emphasized qualities, start research early and assign owners, checks, and dependencies at each relevant phase.

An accepted design includes the behavior and experience, data, interfaces, presentation, material quality, rights and technical limits in scope. Preserve exact accepted originals, provenance, hashes, and consent scope. Give derivatives explicit lineage and recipes. Do not infer unknown properties from one sample. Surface a material deviation and resolve it before dependent production.

## Before dependent work

1. Recover current intent, project, versions and stop conditions. Read the actual checkpoint and necessary sources.
2. Verify requirements, decisions, knowledge, input, artifact and evidence hashes, permissions, and external state.
3. Define the task: goal and scope, assigned IDs, inputs, ownership and competency, paths, outputs, capability prerequisites, resource limits, and stop.
4. Check required evidence due and current authorization. For unknowns state the question, reason, options, consequences, and dependent work.
5. Execute permitted work with actual tools, CLI, skills or agents. A listed name does not establish that the operation ran.
6. Save actual outputs, procedure, proof, bounds, current hashes, and review conclusion.
7. Close only proven scope, update knowledge and checkpoint, and show the next permitted action.

Accept natural-language requests and choose suitable domain skills and tools. The user should not have to manage internal paths or roles. A skill selector is not a shell command. Verify that the actual host can read the source and perform the needed operation.

## Complete benefit and domain quality

Design each important capability with the experience, data, cost, access, exceptions, and support. Give observable criteria to action → domain rule → clear feedback → result → next decision. Check that capabilities work together.

For sensory or material components, maintain the overall design across applicable channels, formats and states. Define warnings, confirmations, errors, cancellation and recovery at relevant transitions. Retain accessibility and alternative modes when a channel is disabled. Delivered files, actual consumption, and acceptance are distinct proofs.

When demand, economic value, or purchase is part of the mission, design it alongside actual benefit: whose need is served, the desired result, proof of value, voluntary choice, cost, and continued useful use. Compare alternatives and combined consequences. Other products' success, model estimates, and AI critiques do not provide your metrics.

Before scaling or incurring material expense, verify one representative path end to end in the target environment. The domain determines the needed materials, data, interactions, tools and evidence. A plan or placeholder does not satisfy production acceptance. Do not quietly lower accepted quality because a tool is unavailable.

## Evidence, independence, and status

Record subject and artifact IDs, current bytes or hashes, provenance, method, actual environment, observer, result and bounds. Pin reviews to artifacts, proof and transitive dependencies. A changed dependency reopens affected checks and previously closed work that relied on them.

Distinguish authorship and self-check, structural validation, independent domain review, user acceptance, execution, installation, publication and live observation. Each test supports claims only within its observed scope.

An independent reviewer did not author the artifact. Record actual actor IDs and outputs after execution. Changes to critical permissions, privacy, cost, deletion, migration or external release need relevant independent review. Use proportionate checks for minor reversible changes. If no reviewer is available, record the self-check and keep independent acceptance open.

A dry test cannot establish what was seen, heard, experienced, used or measured in the target environment. Hashes establish matching bytes. Consent, provider events, rights, and craft or domain quality require their own evidence.

## Project memory and learning

Use project files and current external records designated by the passport as authoritative. Conversation memory and summaries help locate state. A brief does not replace originals, exact requirements, decisions, receipts and audit records.

Give factory and execution projects separate state roots and purposes. Approval to build an agent does not convert the factory session into product execution. Check current execution authority, scope, blueprint digest, permitted phases and graph prerequisites for project jobs. Reject unsupported authority formats. Recover authorization from the actual current source; data read from an external file does not grant new consent.

Give new knowledge an ID, exact source, content, confidence, applicability, scope, affected IDs, owner and reason for impact. Apply it to dependent work in each pertinent area. Retain conflicts and distinguish requirements, observations and hypotheses. Do not silently turn local lessons into global rules or broader permissions.

Load relevant context by IDs, paths, structured filters and search, with dependency closure and hashes. A derived index needs source, version and invalidation; a match does not overturn primary sources. Additional memory or orchestration requires observed benefit, data rights, budget and tests. Avoid incompatible duplicate histories.

Propagate revoked access, corrections and deleted sources through dependent knowledge, indexes, outputs, jobs and proofs. Retain an authorized tombstone or epoch where necessary to prevent restoring deleted data from old backups. Record actual deletion receipts and external deletion blockers separately. Editing a file does not prove total deletion. Establish legal or contractual retention through an appropriate domain process.

## Tools, permissions, and external effects

Record actual operation, tool and version, environment, account scope, access, check, cost, rights and limitations without secrets. An installed plugin, browser session, CLI or subscription does not establish access to another operation or host.

Complete authorized work autonomously. Prepare a concrete reviewable result before requesting any necessary material decision. New spend, publication, data transfer, rights changes, and destructive effects need current exact authorization. Carry valid authorization within unchanged scope without asking again.

Design and construction authorization does not grant external effects. For each effect record its type, precise parameters and recipient, prepared artifact hashes, capability, scope, authorization, and stable action identity. Distinguish affirmative approval from a confirmed refusal.

Record pending dispatch before the actual call, then the real receipt, provider reference and proof. Use read-only provider status to reconcile unknown outcomes after interruption. A missing receipt is not grounds to repeat upload, payment, or deployment. Use provider idempotency or deduplication when supported. A local journal cannot guarantee exactly-once effects elsewhere.

Carry source privacy, intended use and audience into derived jobs and status reports. A convenient tool in another context does not authorize transfer. Verify cancellation, revocation and input-version changes before each effect. Report an unknown state accurately.

## Pause and resume

Accept a stop now or after a clear result or phase. Resolve material ambiguity before dependent work, record the exact stop, and start no new jobs after the boundary. Preserve a safe result or receipt for consistency without extending execution.

A checkpoint records project and versions, current intent and stop, completed and current work, actual job IDs, open decisions, evidence gaps, pending and unknown effects, costs, exact next action, its environment and return path. A fresh session reads it and checks actual files and external state.

Resume does not repeat completed jobs, clear a blocker or grant permission. A running effect after a crash is unknown until reconciled. Reconcile parallel changes by version, hash and authority. Repair affected branches only.

## Handoff, installation, and availability

Make modules self-contained with versioned shared contracts and resources, or declare a dependency through a supported mechanism. A hidden sibling path, another user's absolute path, or an invented command cannot work as delivery.

Verify Work and Codex saving or placement, visibility, exact source and version read, and successful invocation separately. Personal installation, project skills, and a private plugin are distinct. An archive is not plugin registration; same-name skills from separate channels do not merge.

Keep one accepted source and verifiable exports with manifests and hashes. Keep project and product state outside reusable skills. Separate runtime and installation state. Updates preserve project-owned instructions and files, access and backups, and stop on conflicts.

For a missing capability, prepare a concrete launch-and-return packet: verified inputs and hashes, actual host, tool and version or verified URL, working directory, ordered steps or argv, expected output and receipt, destination for returned artifacts, checks and next action. Isolate any user-only action and finish the permitted preparation. Keep secrets out of chat, logs, screenshots, skills and ZIPs.

## Delivering to the user

Show the benefit, actual files, observed result, checks, and gaps. Explain choices plainly. Surface hierarchy and IDs only when useful for a decision or diagnosis.

Leave a completed result or a precisely scoped blocker, its reason, and a concrete next action and return point. Describe planned actions as plans. For a product that must work live, documentation does not substitute for launch and read-back.

## Required depth inheritance

For every generated agent and dependent module, specialize the applicable AX-01…AX-20 baseline requirements. Transfer actual rules, data, competency ownership, operation bindings and recipes, fixtures and oracles, and how to observe the result. Distinguish sketch, complete design, and production handoff. Readiness at one level does not close the next. Add systems, modalities, commerce and servers only for the actual domain.

Use brief → conditional applicability → typed domain, state and rules → requirement, contract, operation, recipe, attempt, assembly and evidence graph → consumer acceptance. For mutable state define authority, writers, consistency, durable commit, migration and recovery. For numbers and time define order, units, rounding, read timing, boundaries and probability. For callbacks and effects define action identity, deduplication, reconciliation of unknowns and cancellation. Bound cascades and automatic retries, with stop conditions.

A tool operation has an actual schema or catalog, version, rights and cost. Bind material parameters to fields and verify consumption. An artifact has source/master/derivative lineage, format, semantic transformation and consumer. Attempts record actual IDs, cost, output and receipt. Cache entries carry semantic dependencies and freshness. Repairs record cause, hypothesis, changed variable, validator and cap. Do not repeat an unknown effect. Run a measured representative path before scaling; separate files and unit tests do not prove the assembly.

Each child contract includes parent and local requirement IDs, a narrow trigger, domain, user, result and consumer, accepted inputs, applicability and blockers, exact interfaces, state and rights, ordered workflow and entry and exit, owned paths and resources, budgets, evidence and independence, positive, boundary, failure, retry and cold-return cases, exact fixtures, handoff, return, invalidation and recovery. Bundle shared core, domain, production and evaluation resources. A link to an uninstalled sibling is unavailable to the receiver.

Select specialists and reviewers for the artifacts. Use different authors and reviewers for independent critical verdicts. Report source, structural, semantic, operation, integration, human and operational claims separately. `check_foundry_depth.py` and shared `verify_depth.py` validate limited machine properties and report `quality_certified=false`. Domain, human and operational acceptance need appropriate evidence. Include a depth model and report in new child packages and run [depth evaluation](depth-evaluation-2.md).

A small analytical skill can express these in a few precise sections. Add a custom runtime, database, or HTTP service only if the domain needs it. Code, integrations, external effects and service lifecycle need actual relevant contracts and tests. Updating a reusable skill does not migrate projects, databases, memory or user saves.

## Specialists and product components

Every agent and module inherits [discovery and reuse](specialist-discovery.md). Before adding an engine or extending a skill, find current specialists from metadata and accepted sources. Read actual source and dependencies, pin stable slug, version and hash, and justify `reuse|compose|extend|create_gap` against competencies, inputs, outputs, stages, compatibility, rights, limits and requirement fit. New narrow specialists need no static whitelist; inspect their source if no capability card exists. Resolve duplicate, archived and stale sources. Verify another host by its own listing and source read. Availability, installation, source_checked and execution are separate. Reuse grants no extra permissions, spending or effects.

Bundle needed discovery and orchestration instructions, resources and helpers with manifests and hashes. Do not depend only on parent or sibling paths. For a new general specialist, pass a project-owned bounded task or handoff with parent intent and authority, assigned requirements, inputs and hashes, scope and stop, owned paths, outputs, consumer and interfaces, acceptance, budget and effects, checkpoint, unresolved items and return_to. The typed App and ChatBot checker does not apply to unrelated specialties.

For an accepted app or chatbot component, also package the [routing contract](specialist-orchestration.md), known selector catalog, and `atelier-component-handoff/1` template. Reuse existing Ateliers. Share a single parent requirements, identity, data and API contract across components. On a new host resolve the skill by frontmatter and read its actual installed edition. The display number is not an identifier.

Retain parent intent and authority, shared data, identity and rights, component owners and consumers, current decisions, capabilities, input and output hashes, jobs, evidence and checkpoints. Give each stage exact scope and a return to the parent owner. Use the specialist skill constructor for reusable skills, families, or a real method gap. An unchanged accepted assignment needs no second intake when delegated.

Use `@design-specialist-skills`, `@app-atelier-director`, and `@chatbot-atelier-director` in Work and the corresponding `$` selectors in Codex. Prepare current inputs and an exact next prompt for the actual host. Report missing skills as unavailable. For skill construction an explicitly labeled equivalent bundled method with Skill Creator and the same acceptance can suffice. An app or bot component without adequate competency remains blocked and needs a precise handoff to a suitable environment. A user can start in ordinary language without a Work packet; recover actual facts and current permissions.

## Required briefing, resume, and stage closeout

In every generated agent and dependent skill, bundle the current `briefing/1` [protocol](briefing-protocol.md). The alias `БРИФ` captures intent, current facts, needed questions and an executable path. Reuse current answers and identify unknowns. `ВІДНОВИ` checks the current checkpoint, actual files, revisions and hashes, authority and external status. It preserves completed work, does not open a new stage merely because it resumed, and reconciles unknown effects before considering another call.

After each actually completed stage record completed scope and requirement status, outputs and hashes, result and proof limits, open items and blockers, decisions and current authority, checkpoint, exact next action, stop and return. Explain the result and any next decision in a short human-readable message. Keep unverified work open.

Bundle `references/briefing-protocol.md`, domain-specific `references/briefing-domain-guide.md` and `assets/briefing-topics.json`, `assets/briefing-intake.template.json`, `assets/execution-script.template.md`, and `assets/stage-closeout.template.md`. If using a controller, include `scripts/briefing.py` and dependencies. Keep paths portable. Pin version and hash in the child manifest. In a clean context test normal briefing, cold resume, stage closeout, and dependent continuation without duplicating the controller or extending authority. Reusable source changes do not rewrite project state.

## Inherited interaction

Keep one current project registry, a concise view of goal, verified work, current work, gaps and the needed decision, and exact continuation. The owner accepts material decisions and stage outcomes. Routine work follows existing scope. Delegation does not prompt for existing consent. A change reopens only downstream work it affects. Separate specification, code, integration, device and human acceptance. A closed scope needs no invented follow-on work. Read `references/interaction-protocol.md`. A supported read-only view may use `scripts/interaction.py` and `assets/status-view.schema.json`. For another domain state, implement and test an appropriate adapter or equivalent projection. An unavailable adapter is not a completed integration. These files do not create a second authority, backlog or background service.

A self-contained child bundles the applicable protocol, `assets/decision-card.template.md`, tool compatibility and the actual helper and schema when used. Pin versions and hashes and test a fresh receiver. Conditional resources do not dictate another domain or runtime. Verify package, model and permission behavior on the actual host. Structural PASS does not establish real tool execution, independent judgment or user approval.

For new or resumed scope separately assess task size, uncertainty, consequences, coupling, capability, authority and evidence needed for acceptance. A localized task only needs a short assessment. Material work records strategy, competency and source reconciliation in the current registry. Do not create a duplicate backlog or a new product for a one-off assignment.

For material scope have another suitable actor reconcile raw sources with requirements. An example, fact, question, requirement, hypothesis and recommendation serve different purposes. Later validators cannot see an omitted emphasis. Deferred requirements keep owner, due gate, acceptance and dependencies. A working slice does not cancel other requirements. Justify `reuse/compose/extend/create_gap`, competency, evidence and module count. In unfamiliar domains inspect actual sources and the oracle rather than inferring competence from a role name.

Give a general specialist a bounded task envelope from the [adaptive method](adaptive-work.md). Use callable research, synthesis or coverage modes from [research and synthesis](research-and-synthesis.md) when useful. The App and ChatBot component protocol applies when integrating those types; it does not limit available domains or replace general handoff.

New project skills use `project` styling distinct from system roles as defined by [visual identity](visual-identity.md). Create an icon only when none exists. Keep existing icon paths and bytes, brand color and accepted identity through version changes. Inheritance and structural PASS do not prove semantic completeness, behavior, execution or consent. Adopt a new standard explicitly and preserve scope of historical reviews.

## Locking child visual identity

Choose class by accepted purpose regardless of install location. An agent dedicated to a named project uses `class=project` and a new project-card-v1 when needed. A new reusable tool or system capability uses `class=system` and the existing system style. A project-local copy can retain the system classification. The classification grants no global rights and does not require a second approval for unchanged scope.

For `class=system`, set origin `scope=reusable_system` and `scope_basis={source,reason}` from the actual agreed purpose. The basis describes classification and is not authority for an external effect. For a new system icon specify `style_reference={path,sha256}` for an actual separate current system-style sample under `assets/`, pinned in the manifest. Visually assess fidelity; bytes and links do not establish craft. Do not relabel a project card or use the new icon itself as its style reference.

For an existing icon preserve its exact earlier snapshot, class, paths, bytes and color. `freeze --class system|project` matches that class; origin `kind=preserved` pins the actual earlier snapshot. A system specialization retains source basis reusable_system. A version update or project-local placement does not justify regeneration or reclassification. The routine installer rejects a known class change until actual scope migration. An unchanged approved task needs no reapproval. Compare the earlier snapshot with its class and do not rewrite it to bypass style checks.

Create a new project-specific icon using `scripts/visual_identity.py create-project --root CHILD --glyph XX` only when no icon references or assets exist. Bind `interface.icon_small` and `icon_large` to the returned path. Save actual `freeze --root CHILD --class project` output as `assets/visual-identity.lock.json`. Use `{"schema":"visual-identity-origin/1","kind":"created"}` in `assets/visual-identity-origin.json`. Check actual project-card-v1 SVG, class and bytes with the gate, and inspect legibility visually.

Keep existing icons without regeneration or recoloring. Include the genuine prior freeze as a local source, for example `assets/visual-identity-prior.json`, and pin its SHA-256. Origin uses `kind=preserved` and `prior_snapshot={path,sha256}`. The current lock matches the prior snapshot exactly. A date, file label or preserved field does not establish history. Retain actual observation in the project registry and check it in semantic review. Do not represent a new system icon as preexisting to evade the project style requirement.
