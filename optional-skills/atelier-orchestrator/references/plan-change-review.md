# Review a change to the current plan

Use this coordinated route when changed requirements cross ticket, dependency,
ownership or evidence boundaries. Keep the direct route for narrow, local work.

1. Resolve the authoritative before and after revisions, changed decision and
   permitted effect. Locate the matching, reviewed repository checkout of
   Codex Agent System and open its `docs/technical/TICKET_CHANGE_REVIEW.md`.
   The preview commands are repository tools; do not assume the installed skill
   bundles them. If the tools or true before view are unavailable, identify the
   missing evidence, and carry out only the manual review the available sources
   support.
2. Capture both ticket views and compare their pinned contents. Separate an
   edited source file from a changed requirement, direct ticket impact, a
   dependent task, and prior proof that does or does not bind. Continue
   unaffected authorized work.
3. Ask the product owner or product specialist to interpret the decision and
   compare adjustment, rollback and scope changes. Give architecture and UX
   work only to their affected owners. Use a separate reviewer for consequential
   changes; hand over the decision and exact source paths, affected IDs,
   proposed criterion changes, prior proof and permitted operations. Ask that
   reviewer to look for missing dependencies, evidence and conflicting work.
4. Build a verified draft and actionable handoff. Keep accepted and active
   work in its recorded state. Present the before/after, historical proof,
   what can continue, proposed changes and fresh acceptance checks. Report if
   a reviewer did not run or if semantic support remains uncertain.
5. Adopt changes only with the applicable exact authority, via the project’s
   own write route. Recheck source, decision and readiness before handing work
   to a builder. Record a new native revision and fresh evidence as appropriate.
   An impact result or a valid draft does not authorize execution or acceptance.

For a project that owns its backlog as the ticket projection, the repository
guide `docs/technical/TICKET_REPLAN.md` gives the reviewed file adapter.
Prepare its exact proposal and ask the relevant specialist to confirm intent.
Apply only through the actual decision channel and read back the receipt.
If the previous result is uncertain, use its existing operation ID to reconcile.
Prepare the Builder handoff for a ready ticket only after current readback.
Send the scoped task and exact handoff hash to the native role or fresh session.
Obtain its actual return and an independent domain verdict before acceptance.
Pause and external tracker writes still use their owning system's verified route.

For two independent Builders, bind each contribution to an exact base and
its own linked Git worktree. Use the repository guide
`docs/technical/TICKET_WORKTREES.md` to prepare worktree identity, capture
a confirmed interruption, and recheck the inputs in the receiving session.
Keep operating-system write permission scoped to the selected files.
Validate the worker commits, integrate in a separate coordinator worktree,
and verify the combined behavior before accepting the result.

For a project that tracks work in GitHub Issues, use the repository guide
`docs/technical/TICKET_GITHUB.md` to check issue identity and compare the
observed status, dependencies, and sub-issues with the local projection.
A missing or uncertain provider response leaves its part of the review open.

For coordinated acceptance, use `docs/technical/TICKET_QUALITY_GATE.md`.
Ask QA to map the applicable criteria to risk-prioritized checks and record
the actual behavior against the pinned candidate. Resolve missing artifacts,
unknown effects, and held prerequisites before treating the scoped gate
as passing. Send the evidence to the owner through the project's acceptance
or release route.

After delivery, use the "Close the cycle and retain the lessons" section of
`docs/technical/TICKET_WORKTREES.md`. Recover the exact commits, acceptance
and unresolved work before discussing causes. Turn a verified finding into a
follow-up with one responsible owner and an observed success condition.
Carry it through the project's actual planning route.

For a sprint that outlives a backlog revision, use the "Keep a sprint plan
while the backlog changes" section of `docs/technical/TICKET_TREE.md`.
Read the recorded membership and current dispositions separately. Review new
prerequisites, retired work and expanded group membership before proposing a
revised sprint. Use the project decision to record the chosen scope.

When product requirements and architecture are authored separately, use
`docs/technical/TICKET_PRODUCT_SPEC.md` to capture both Markdown companions
against native requirements and actual decisions. Review changed criteria
and the impact on dependent tasks. Use a fresh reviewer for the new bundle.
